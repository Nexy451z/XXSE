## 0. 結論

**12 件すべて「通常の配信イベントクエスト」ではない。判定は 12 件とも「没データ疑い」。**

* 11 件（q1111009〜q1111019）は、romfs 内 30 ファイルが共有する**空のクエスト雛形**の複製。タイトルは開発者自身が付けた「予備」。
* 1 件（q1120013）は「予備枠」という名の**部分的に実装された枠**（ターゲットと報酬だけ入っていて、モンスター配置が無い）。

判定の核は「タイトルが予備」「30 ファイルが完全同一テンプレート」「報酬・モンスターがダミー参照」の 3 点で、
いずれも**実測**。ただし「配信予定だったが未完成」か「単なる未使用枠」かの区別は**不明**（§7）。

## 1. 手法と表記

* `mhnx` の 4 サブコマンド（arc-list / arc-mib / arc-gmd / check）の出力を全 12 件分保存（`out\group4\<id>.{mib,gmd,list,check}.txt`）。

  バイト単位の差分・payload ハッシュ比較はこの経路でしか取れないため。
* 表記:
  * **【実測】** = この環境のファイルを読んで測った値

  * **【不明】** = 判断材料が足りない

> 注意: `mhnx` の `arc-mib` が出す「報酬枠1/2/3」「クエスト種類」「村ランク」などのラベルは mhnx 側の解釈。

## 5. 特筆すべき発見

### 5.1 romfs の 30 ファイルが「完全同一の雛形」

`.mib` と `.gmd` を除く全エントリの payload ハッシュを署名にして全 romfs クエストを分類した【実測】:

* 署名 `8e4838f7f438` を共有するファイル = **30 件**:
  q1010006, q1010007, q1010176, q1010177, q1011014（タイトル「欠番」）, q1011045-1011053（Ｇ級予備４〜１２）,
  q1110008, q1110009, q1110114, q1110115, q1111008-1111019（本担当の 11 件を含む）
* この 30 件は、ハンター用／オトモ用・下位／上位／G 級の**全バリエーションの空き枠**を 1 つの雛形で埋めたもの。
  本担当の 12 件のうち **11 件がこの 30 件に属する**。
* 逆に q1120013 の署名は全 1,855 件中**この 1 件だけ**（＝兄弟が居ない単発の枠）。

### 5.2 サイズの量産パターンは「雛形の共有」で説明できる

依頼メモにあった「33,786 / 33,790 が多数」は、この雛形共有の現れ【実測】:

| サイズ | 件数（本担当 12 件中） | 対応する雛形 |
|---|---|---|
| 33,790 | 7（1111009-1111015） | ニャンターＧ級予備（`.gmd` 186 B 版） |
| 33,786 | 4（1111016-1111019） | 同上・タイトルが 3 バイト短い版（`.gmd` 183 B） |
| 33,281 | 1（1120013） | 予備枠（エントリ 11 個・別系統） |

サイズ差 4 B の内訳も実測で説明できる（タイトル文字列の UTF-8 長差 3 B ＋ 圧縮後の差）。

### 5.3 "Invalid Message" は雛形の目印になる

`.gmd` の依頼主が `Invalid Message` のクエストは romfs 全 1,855 件中 **32 件だけ**。内訳は
§5.1 の 30 件 + q1010160（タイトル「未使用」）+ q1011038（アマツマガツチ（強化）＝実クエスト）【実測】。
→ 「32 件しかない」こと自体は根拠にならないが、**本担当の 12 件中 11 件がこの集合に入る**ことは、
「実クエスト用に書かれたテキストを持たない」ことの傍証になる。

* 1111xxx は **1111001〜1111007（7 件）**までしか入っておらず、**1111008 以降（＝予備シリーズ）は全部未導入**。
* 1120xxx は **1120001〜1120012 の 12 件が全部入っていて、1120013 だけが無い**。
* インストール済みクエストの実サイズは 1,821 / 1,998 / 2,372 / 2,808 / 2,925 B など（＝1.7〜3.5 KB 級）。

→ 「未導入」は配信漏れというより、**そもそも配信対象になっていない ID**（配信済みの通し番号の外側）であることを示す【推測、根拠は上記の実測】。

### 5.6 ラングロトラ（ID 62）の同定方法と限界

「ターゲット種類 1 × ID 62」14 件のうち 13 件で `.sem` 名の `em062` と .gmd の「ラングロトラ」が一致し、
残る 1 件が q1120013（配置なし）だった【実測】。ID→モンスター名の対応表を直接持っていないため、
この同定は**相関に基づく推定**であって、ゲーム内テーブルを読んだ確定ではない【不明要素あり】。

### 5.7 「異常値」に見えるが根拠にできないもの（実測ベースライン）

依頼メモのチェック項目のうち、今回の 12 件では**当てはまらない/当てはめると誤る**ものを明示する。

配信済みイベント 223 件（`arcs\event\`）の実測分布:

| 指標 | 配信 223 件での出現数 | 本担当 12 件 | コメント |
|---|---|---|---|
| 報酬金 z2 = 0 | **31 件（14%）** | 11 件（1120013 は 4,500） | 単独では異常の根拠にならない |
| mib の報酬枠 rem1/2/3 が全部 0 | **150 件（67%）** | 12 件全部 | **このフィールドは報酬の有無を表していない**。根拠に使えない |
| quest_kind = 0（なし） | 104 件（47%） | 11 件 | 単独では根拠にならない |
| ボス 5 枠が全部ダミー | **34 件（15%）** | 12 件全部 | 採集クエスト等でも起きる。単独では根拠にならない |
| 制限時間 0 | 0 件 | 0 件 | 今回は該当なし |
| 復活回数 0 | 0 件 | 0 件 | 今回は該当なし |
| 参加条件が両方 0 | 41 件（18%） | 11 件 | 単独では根拠にならない |
| 支給品が全ゼロ（`supp_0000000` 相当） | **87 件（39%）** | 12 件全部 | 単独では根拠にならない |

→ 本レポートの判定は、これらの**個別フラグではなく**「タイトル（予備）× 30 件同一テンプレート × `.gmd` が
プレースホルダ文字列だけ × 報酬がダミー参照」の**組み合わせ**で下している。個別フラグを単独の根拠にしていない。

**テキストの空・文字化け**: 12 件とも該当なし。文字列は正しい UTF-8 で、内容がプレースホルダというだけ【実測】。

### 5.8 33 KB の正体（サイズの錯覚）

romfs の `.arc` は**データ部が 0x8000（32,768）から始まる**レイアウト【実測】:

* `arcs\quest\` 1,859 件中 1,855 件が先頭データ offset = 0x8000、4 件が 0x10000 / 0x18000。
* `arcs\uninstalled\` 48 件は 48 件とも 0x8000。パディングは全件ゼロ埋め。
* セーブから取り出した `arcs\save_event\` 175 件は **175 件とも「テーブル直後（32 B 境界）」から**データが始まる。

→ 33,790 B のうち **32,036 B はゼロのパディング**。実データは 1,022 B、ヘッダ+テーブルが 732 B【実測】。
このため「33 KB だからセーブに入らない」は**サイズの錯覚**であり、§6 の通り詰めれば 1.7 KB になる。

## 6. 導入可否

### 6.1 上限 5,112 B の正体【コード】

`crates/mhnx-core/src/dlc.rs`:

* `QUEST_SLOT_SIZE = 0x1400` = 5,120 B（1 スロット）
* `QUEST_MAX_PAYLOAD = QUEST_SLOT_SIZE - 8` = **5,112 B**
* スロットの形式は `{ s32 quest_id; s32 size; u8 raw_arc[size]; }` = **`.arc` の生バイトをそのまま置く**。
  追加の圧縮層は無い（＝「圧縮後 5,112」ではなく「`.arc` そのものが 5,112 B 以内」）。

### 6.2 実測: 33 KB はそのままでは入らない / 詰めれば入る

実セーブのコピーに対して `mhnx install` を実行した結果【実測】:

```
$ mhnx install <copy> q1111009.arc          (33,790 B)
error: quest payload too large for a slot: value 33790 out of range

$ mhnx install <copy> q1010001.arc          (3,034 B, インストール済み ID)
installed quest 1010001 into slot 59 of ...        ← 3 KB 級は通る
```

さらに、パディングを除去してデータ部をテーブル直後に詰めた `.arc` を自作し、`mhnx info` / `check` で
構造が壊れていないことを確認した【実測】:

| ID | romfs | テーブル末尾 | 実データ | **詰めた後** | 再圧縮(zlib -9) した場合 |
|---|---|---|---|---|---|
| 1111009〜1111015 | 33,790 | 732 | 1,022 | **1,758 B** | 1,767 B（増える） |
| 1111016〜1111019 | 33,786 | 732 | 1,018 | **1,754 B** | 1,764 B |
| 1120013 | 33,281 | 892 | 513 | **1,409 B** | 1,420 B |

* 詰めた後のほうが**再圧縮するより小さい**（元の zlib ストリームが既に十分圧縮されているため）。
  → **「再圧縮が必要」という前提は、今回の 12 件については当てはまらない**。必要なのは再圧縮ではなく**パディング除去（再レイアウト）**。
* 1,758 / 1,754 / 1,409 B は上限 5,112 B に対して十分小さく、**実際に配信されているクエスト（1.7〜3.5 KB）の中に収まるサイズ**【実測】。

### 6.3 実測: サイズ以外に「追加できない」壁がある

詰めた `.arc`（1,758 B）を、ID が未登録のセーブコピーにインストールしようとした結果【実測】（長い空白は詰めて引用）:

```
$ mhnx install <copy> compact/q1111009.arc
error: parse error: this save does not have that quest yet. Only a quest the save already lists can be
       updated: the game decides what to show from a catalogue indexed flag, and a free slot number cannot
       address that flag. Install the quest once by other means, then use this tool to change its contents.
```

* つまり **このツールは「既に入っているクエストの差し替え」専用**。空きスロットへの新規追加は、
  「カタログ索引フラグ」が必要で、スロット番号からは決められない（`dlc.rs` 冒頭のコメントと一致）。
* 本担当 12 件は**全部この状態（セーブに ID が無い）**なので、`mhnx` でそのまま入れることはできない【実測＋コード】。

### 6.4 仮に入れられたとしても

* A/B グループ: ボス 0 体・ターゲット 0（達成条件なし）。ゲーム側でクリア判定が成立しない、
  または読み込み時に異常になる可能性が高い【推測】。**実機で試していないので断定しない**。
* 1120013: ターゲットはラングロトラ 1 頭だがボス配置が無いので、出現しない＝クリア不能になる公算【推測】。
* いずれも「入れて遊べるクエスト」にはならない。

### 6.5 結論

| 観点 | 結果 |
|---|---|
| サイズ（5,112 B 制限） | **問題にならない**。パディング除去で 1,409〜1,758 B。実測で構造も壊れない |
| 再圧縮の必要性 | **不要**（むしろ再圧縮すると数十 B 増える） |
| ツールでの導入 | **不可**。`mhnx install` は既存 ID の差し替え専用で、セーブに無い ID は拒否される（実測） |
| 中身 | 空（ボス 0・ターゲット 0・報酬ダミー）。導入しても遊べない見込み【推測】 |
| 総合 | **導入する価値は無い**。ただし「自作クエストの雛形（33 KB → 1.7 KB への詰め方の見本）」としては有用 |

## 7. 不明点・断定しなかったこと

1. **「没データ」か「配信予定で未完成だった枠」か**は区別できない。開発者が将来の配信用に確保した枠を
   そのまま romfs に残した可能性は排除できない【不明】。
2. **実機での挙動**（導入した場合にフリーズするか、単に選択できないか）は検証していない【不明】。
3. `.arc` ヘッダ +0x08 の値が romfs = `0xFFFFFFFE`（1,859 + 223 + 48 件すべて）、
   セーブ内 = `0x00000000`（175 件すべて）と**食い違う**【実測】。
   セーブへ入れる際にこの値を 0 にすべきかは判断できない【不明】。mhnx は値をそのまま保持する実装。
4. `.mib` の `mob_slot` 13 B の内部構造は未解析（1120013 だけ非ゼロ）。モンスター ID を含むかは不明【不明】。
5. ターゲット ID 62 = ラングロトラ は 13/14 の相関による推定（§5.6）。ゲーム内テーブルでの確定はしていない。
6. 「予備」枠が**ゲーム内で選べない**ことの直接証拠（カタログ側の実データ）は読んでいない。
   §5.5 はセーブの収録 ID からの推測。
7. 失敗条件が「報酬金ゼロ\r\nタイムアップ」と正常形なのは、雛形の既定値なのか意図的な設定なのか不明。
