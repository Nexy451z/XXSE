## 2. 分かったこと（根拠つき）

### 2.1 nameidx は GMD の添字ではない（総当たりで否定）

#### やったこと

1. romfs 配下の**単体 .gmd 388 個**をすべて解析し、ファイルごとの文字列件数を集計した。
2. romfs 配下の **.arc 12,829 個（合計 8.87 GB）**を走査し、タイプハッシュ `0x242BB29A`（.gmd）を持つ
   エントリ **3,865 個**を zlib 展開してすべて解析した（＝ゲームが持つ .gmd の全量。単体ファイルとの重複を含む）。
3. nameidx の最大値 796 を含むので、**797 件以上の文字列を持つ表**を全部列挙した。
4. さらに、2.2 節で復元した 205 件のクエスト名を、**全 .gmd の全文字列と完全一致で照合**した。

#### 結果

| 検査 | 結果 |
|---|---|
| 797 件以上の文字列を持つ .gmd | **7 個だけ**。すべて素性が判明している表 |
| その 7 個の 577..796 番目がクエスト名か | **すべて違う**（防具名・アイテム名・称号・オトモ装備・依頼文） |
| 205 件のクエスト名が .gmd に存在するか | **0 / 205**（1 件も無い） |

797 件以上の .gmd は次の 7 個（table と arc の重複を除いた実体）:

| ファイル | 件数 | 中身 |
|---|---|---|
| armorSeriesData_jpn.gmd | 12,870 | 防具シリーズ名＋説明 |
| itemData_jpn.gmd | 5,982 | アイテム名＋説明 |
| GC_Title_1_jpn.gmd | 2,618 | ギルドカード称号 |
| otArmorData_jpn.gmd | 2,108 | オトモ防具 |
| otWeaponData_jpn.gmd | 1,018 | オトモ武器 |
| activityData_jpn.gmd | 920 | 依頼テキスト（dummy を大量に含む） |
| weapon00MsgData_jpn.gmd | 822 | 武器名＋説明 |

**結論: nameidx 列を「GMD の添字」と読む仮説は成立しない。添字先が存在しない。**

### 2.2 クエスト名は .arc の中にあった（205/205 復元）

クエスト名は共有の GMD テーブルではなく、**各クエストの .arc 内 .gmd（文字列 0 番）**にある。

```
arc\quest\q<7桁ID>.arc
  +- entry "quest/questData/questData_<ID>_jpn"  (type 0x242BB29A) = GMD
       strings[0] = クエスト名  strings[1] = 依頼主  strings[2] = 依頼内容 ...
```

| 検査 | 結果 |
|---|---|
| カタログ 205 件の ID に対応する q<ID>.arc が romfs にあるか | **205 / 205 存在** |
| .gmd からタイトルが取れたか | **205 / 205** |
| .gmd のキーが questData_<ID> で ID と一致したか | 205 / 205 |
| .mib の quest_id(+0x0C) が ID と一致したか | 205 / 205 |

**→ 205 件すべてのクエスト名を復元した（付録 A）。**
名前が重複するのは ID が重複している 1020001（位置 0,41,42,43,44）と 1110113（位置 188,202）だけで、
これは「名前の供給元が ID 単位で、カタログ位置単位ではない」ことの証拠でもある。

> 注意: ここで取れるのは **romfs 同梱版 .arc** の名前。セーブに入っている配信版 .arc とは別物
> （サイズ 33 KB 対 1.8〜3.9 KB、2.5 節）。名前としては一致するが、データとしては別。

### 2.3 nameidx 列の正体 — エントリごとの通し番号（推測を含む）

#### 観測 1: 位置と厳密に単調対応する

```
position 0   -> 577      position 44  -> 621
position 45  -> 637      position 204 -> 796

  nameidx = 577 + position              (position <  45)
  nameidx = 637 + (position - 45)       (position >= 45)
```

例外は 0 件（205/205）。

#### 観測 2: 同一 ID でも nameidx は別の値になる（＝名前の索引ではない）

| 位置 | ID | nameidx | 名前（.arc から復元） |
|---|---|---|---|
| 0 | 1020001 | **577** | イベント：タマミツネ討伐 |
| 41 | 1020001 | **618** | イベント：タマミツネ討伐 |
| 42 | 1020001 | **619** | イベント：タマミツネ討伐 |
| 43 | 1020001 | **620** | イベント：タマミツネ討伐 |
| 44 | 1020001 | **621** | イベント：タマミツネ討伐 |
| 188 | 1110113 | **780** | サンリオ・ひとぐでしようニャ |
| 202 | 1110113 | **794** | サンリオ・ひとぐでしようニャ |

名前が同じ 6 組が、6 個の違う番号を持つ。**名前の索引なら同じ値にならなければならない。**
したがってこの列は名前の索引ではなく、**エントリ（＝カタログ位置）ごとに振られた通し番号**である。

#### 観測 3: 穴はカテゴリ境界にだけ、ちょうど 15 個

```
チャレンジブロック   577 ......... 621 | 622 ... 636 | 637 ......... 796   イベントブロック
                     45 個（使用）        15 個（未使用）  160 個（使用）
                     <------- 60 -------->
```

チャレンジ側の番号帯は **577..636 = 60 個**ぶん確保されているが、エントリは 45 個しかない。
イベント側は 160 個ぶんの番号を 160 個のエントリが隙間なく使う。
**番号帯はブロックごとに独立に確保され、使われなかった分が穴として残る**形になっている。

依頼票の「622..636 の 16 個」は数え違い。622 以上 636 以下は **15 個**（636 − 622 + 1 = 15）。
実データの差集合を数えても 15 になる。

#### この列の意味（推測）

観測 1〜3 を満たす読み方は 2 つ。どちらも**この 1 個のセーブと 1 個のバイナリからは決められない**。

| 読み方 | 内容 | 評価 |
|---|---|---|
| (A) 設計時の通し番号（登録順・配信順） | 開発側がクエストを登録した順の番号。チャレンジ 60 枠・イベント 160 枠を確保し、使わなかった枠は欠番のまま | **推測**。穴の位置と幅がこの読み方とよく合う。2.7 節の「MHX リストの拡張」とも整合 |
| (B) 共有の名前テーブルの索引（テーブルは本作に同梱されていない） | 元は名前表があったが MHXX Switch の romfs には入っていない | **否定的**。2.1 節のとおり名前テーブルが存在しない。さらに同一 ID が別番号を持つ事実と矛盾する |

> **実装上の帰結: nameidx 列は使わない。** 並び順は position そのもの。
> quest_id → position → bit はカタログの ID 列だけで引ける（親文書の結論どおり）。

### 2.4 装備枠 41..44 のプレースホルダ

| 位置 | ID | nameidx | マスクビット | ビット値 | 装備枠 41..44 の中身 |
|---|---|---|---|---|---|
| 41 | 1020001 | 618 | 41 | **0** | 全 0（id=0, size=0） |
| 42 | 1020001 | 619 | 42 | **0** | 全 0 |
| 43 | 1020001 | 620 | 43 | **0** | 全 0 |
| 44 | 1020001 | 621 | 44 | **0** | 全 0 |

分かること:

* カタログ上は「実在する 4 エントリ」として並ぶ（ID が 0 ではない）。
* しかし装備枠は空、マスクビットは 0、対応する .arc は q1020001.arc 1 個だけ。
  つまり**ゲームがこれらを実クエストとして扱う経路が無い**。
* nameidx は 618..621 で、位置 40（617）の続きをきれいに埋めている。
  番号を振る処理は 45 枠ぶん回っており、41〜44 枠に「中身が無い」状態が残ったと読める。

**推測（由来）**: 45 枠 = 実クエスト 41 + 未使用枠 4 という配列を先に確保し、
中身が決まらなかった 4 枠に先頭エントリ（1020001）の ID がそのまま残った、という説。
「0 で埋める」ではなく「先頭要素のコピーで埋まる」のはテンプレート配列を複製して
一部だけ書き換える作り方の典型だが、**裏づけは無い**。

**反証しておく**: 「41..44 は将来 1020030..1020033 用の予約枠」という読み方も成り立つが、
romfs に存在するのは q1020030.arc と q1120013.arc だけで 4 個そろわない（3 節の未解明 3）。

### 2.5 空き枠への新規追加に必要なもの（実測）

#### 2.5.0 セーブ側の入れ物

```
DLC セクション = 36 + 0xB280
  +0x0000      0x34 B  ヘッダ（一部未解明、2.5.5 節）
  +0x0034      0x18 B  24 バイトのマスク（未解明、112 ビット）
  +0x004C      0x1C B  導入済みマスク（本件の主役、175 ビット）
  +0x45F4      205 x 0x1400 B  クエスト枠   { s32 id; s32 size; u8 data[size] }
  +0x1049F4     45 x 0x800  B  クエスト装備枠 { s32 id; s32 size; u8 data[size] }
  合計 0x11B1F4 (= 0x126474 - 0xB280) で第 1 スロット基点に一致
```

#### 2.5.1 マスクのビットを立てるだけでよいか → **いいえ。2 点セット**

| 必要 | 根拠（実測） |
|---|---|
| 1. マスクの該当ビットを立てる | ビット = position（0..40）または 64 + position − 45。実セーブで 175/175 一致（親文書） |
| 2. **空きクエスト枠に配信版 .arc を書く** | ビットが立つ 175 件すべてに対応する枠が存在し、枠の id とカタログ ID が一致。ビットだけ立って枠が無い状態は実セーブに 1 例も無い |

逆（枠はあるがビットが 0）も 1 例も無い。**ビットと枠は 1:1 で対応している。**
ビットだけ立てても、ゲームが読むクエスト実体が無いので一覧には出ない見込み。

#### 2.5.2 クエスト枠の「位置」に制約はあるか → **無い**

| 実測 | 値 |
|---|---|
| 枠番号とカタログ位置の対応 | バラバラ（例: 位置 133 → 枠 0、位置 45 → 枠 59、位置 0 → 枠 180） |
| 空き枠の分布 | 135..159（25 個）と 200..204（5 個）＝**配列の途中に穴が空く** |
| 同じ ID が 2 枠に入っている例 | 0 件 |

枠は「ID で引くフリースロット」であって、カタログ位置を写した配列ではない。
（カタログ位置を写しているのは**装備枠のほう**。2.5.3 節）
参照実装 quest.c も、枠を先頭から走査して quest_info[0] == id で照合するだけで位置を使っていない。

#### 2.5.3 装備枠が絡むクエストは装備枠も必要か → **チャレンジ枠（位置 0..40）だけ必要**

| 実測 | 値 |
|---|---|
| 装備枠の数 | **45 個**（0x1049F4 から 45 x 0x800。セクション末尾と一致） |
| 装備枠の索引 | カタログ位置そのもの（位置 k の枠に位置 k の ID） |
| 中身のある枠 | 40 個（位置 0..24, 26..40）。すべてマスクビットが立っている |
| 空の枠 | 位置 25（1020020 が未導入）と 41..44 |
| 記録形式 | { s32 id; s32 size; u8 data[size] }。data の先頭 4 バイトにも同じ ID |
| size の値 | 102xxxx 系 = **942 B**、112xxxx 系 = **169 B** |

**位置 45 以降（イベント 160 件）には装備枠が存在しない**（配列が 45 個で終わる）。
よってイベントクエストの追加に装備枠は不要。チャレンジクエスト（位置 0..40）は
ビット + クエスト枠 + 装備枠の 3 点セットになる。

**ただし装備枠の data（942 B / 169 B のブロブ）は romfs から作れない。**
どのクエスト .arc のどのエントリにも含まれていない（q1120001.arc の 11 エントリを全展開して照合、不一致）。
手元の 15 個のセーブ（バックアップ・変換版）にもビット 25 が立つものが無い。
→ **位置 25 の 1020020 だけは、装備枠データを持つ別セーブが無い限り追加できない。**

#### 2.5.4 記録サイズの上限（重要）

| 実測 | 値 |
|---|---|
| クエスト枠 1 枠 | 0x1400 = 5,120 B。data に書けるのは **0x13F8 = 5,112 B まで** |
| このセーブの記録サイズ | 1,733 〜 3,453 B（全 175 件） |
| 記録の中身 | **配信版 .arc のファイルそのもの** |
| 配信版 .arc と mhxx_quetool\quest\*.arc の一致 | 比較できた 135 件中 **134 件がバイト一致**（1 件だけ 1010165 が 11 B 違い） |
| romfs の arc\quest\q*.arc のサイズ | **33,036 〜 395,156 B**（1 件も枠に入らない） |
| questtool の .arc サイズ | 1,811 〜 3,881 B（枠に収まる） |

**romfs の q*.arc はそのままでは枠に入らない**（最小 33 KB > 5,112 B）。
入れられるのは「配信版」の .arc だけ。両者はサイズだけでなくエントリ構成も別物。

#### 2.5.5 未解明のヘッダ（追加時のリスク）

同じセーブの別版（save_backups\20261019_150128\0\system、マスクが全 0）と比べると、
DLC セクション先頭 0x34 バイトは**導入 0 件のセーブでは全部 0**、導入 175 件のセーブでは次の値だった。

```
+0x00 00 7a 00 00   +0x04 00 00 00 00   +0x08 00 00 00 fc   +0x0C 00 00 00 00
+0x10 0f 00 00 00   +0x14 ff ff 9d ff   +0x18 ff ff ff 7f   +0x1C 1a 00 00 00
+0x20 1f 00 00 00   +0x24 f0 ff ff ff   +0x28 ff ff ef ff   +0x2C 07 fc ff ff
+0x30 ff ff ff ff
```

+0x1C = 26、+0x20 = 31、+0x10 = 15 という小さい整数が並ぶ。26 は本セーブの未導入実件数と一致するが、
**サンプルが 1 個しかないので偶然と区別できない**（親文書が警告している「件数一致の罠」と同じ）。
追加実装では、この 0x34 バイトを**書かない**（既存値をそのまま残す）のが安全。

* 2 エントリは**別々のビット**（207 と 221）を持ち、**どちらも 0**。
* .arc は q1110113.arc が 1 個だけ。名前も同一。
* nameidx が 780 と 794 で違う（2.3 節 観測 2 の証拠のひとつ）。

**推測**: 配信時に同じクエストを 2 枠に登録してしまった重複（開発側のミス）。
ゲームは position 単位に列挙するので、両方のビットが立つと**同じクエストが 2 回出る**可能性が高い。
実装では**片方（188 = ビット 207）だけを立てる**のを既定にし、202 は触らないのが安全。
どちらが正しいかは、どちらかが立っているセーブが 1 つも無いため決められない。

### 2.7 MHX（3DS）との比較

MHX 側のバイナリはこの作業場に無い（rom は MHXX の NSP のみ）。
比較に使えたのは参照実装 refs\mhx_data_manager\source\quest.c（v2.3.0）で、
**ゲームから読んだ表ではなく作者が手で書いた ID リスト**である点に注意。

#### 2.7.1 マスクの組み方は両者で同一

| | MHX（参照実装） | MHXX（実測） |
|---|---|---|
| マスクの位置 | セクション +0x34、20 B | セクション +0x4C、28 B |
| チャレンジ | 20 件 → ビット 0..19 | 45 件 → ビット 0..44 |
| パディング | 12 ビット（20 → 32） | 19 ビット（45 → 64） |
| イベント開始ビット | **32**（= ceil(20/32)x32） | **64**（= ceil(45/32)x32） |
| イベント | 120 件 → ビット 32..151 | 160 件 → ビット 64..223 |
| クエスト枠の基点 | +0x45D4 | +0x45F4 |

**両方とも「チャレンジを 32 ビット境界に切り上げ、その次の語からイベント」**。
親文書の「+19 は u32 語境界への切り上げ」という推測は、MHX 側の +12 と規則が一致することで
**構造的に裏づけられた**（推測から傍証ありへ格上げ）。

さらに、セクション先頭からクエスト枠までの伸びは 0x45F4 - 0x45D4 = +0x20 で、
「+0x34 に 24 B の新フィールドが入り（+0x18）、マスクが 20 B → 28 B に増えた（+0x8）」合計と**厳密に一致**する。
**推測**: MHXX でマスクが +0x34 から +0x4C へ移り、空いた +0x34 に別の 24 B マスクが入った。

#### 2.7.2 MHXX のカタログは MHX のリストの拡張

| 検査 | 結果 |
|---|---|
| MHX チャレンジ 20 件 == MHXX チャレンジ位置 0..19 | **完全一致（順序も）** |
| MHXX チャレンジ位置 20..40 | 1020015..1020029（15）+ 1120007..1120012（6）＝ MHXX で追加された 21 件 |
| MHX イベント 120 件のうち MHXX カタログにも居るもの | 103 件 |
| その 103 件の順序の逆転 | **19 / 5,253 組**（99.6 パーセントが同じ順序） |
| MHX に居て MHXX カタログに居ないイベント | 17 件（1010007, 1010008, 1010177, 1010178, 1010179, 1010180, 1010181, 1010182, 1010183, 1010184, 1010185, 1010186, 1010187, 1110009, 1110114, 1110115, 1110116） |
| MHXX カタログに居て MHX リストに居ないイベント | 56 件（主に 1011xxx 系） |

→ MHXX の 160 枠は **MHX の 120 件をほぼそのままの順序で先頭に置き、新しい件を差し込み/追加し、
落とした件もある**もの。カタログはゲームごとに手で維持されている登録リスト（推測）。
これは 2.3 節の「nameidx = 登録時の通し番号」説と整合する。

### 2.8 カタログ末尾は「予備」「欠番」だった（追加可否が変わる）

## 4. 実装への提案

### 4.1 データを持たせる（低リスク・すぐできる）

1. gamedata.rs の DLC_CATALOG の隣に **nameidx 列**と**205 件の名前**を追加する（付録 A をそのまま定数化）。
   - `pub const DLC_CATALOG_NAMEIDX: [u32; 205]`
   - `pub const DLC_CATALOG_NAMES: [&str; 205]`
   - dlc-list / GUI の一覧に「未導入でも名前が出る」ようになる。
2. **名前解決は .arc 経由が正**。GMD の共有表を探すコードは書かない（存在しない）。
   導入済みならセーブの枠から .gmd を読む、未導入なら romfs の q<ID>.arc から読む、の 2 経路。
3. position → bit の式は現状のままでよい（本レポートで再確認、例外 0）。nameidx は**使わない**。
4. 1110113 は position 188 に正規化するヘルパを 1 つ入れる（重複 ID は「最初の位置」を返す規則を明文化）。

### 4.2 追加インストール（実装するなら）

```
install_event_quest(save, id):
  1. position = catalogue.index_of(id)           # 無ければ拒否
  2. position in 41..44        -> 拒否（プレースホルダ）
  3. id == 1110113             -> position 188 に正規化
  4. position < 45             -> 装備枠が要るので 4.3 の判断へ
  5. bit = bit_of(position); 既に 1 なら「置換」経路に回す
  6. arc = 配信版 .arc（questtool 等）。len(arc) > 0x13F8 なら拒否
  7. 空き枠 index を 1 つ選ぶ（先頭から。位置の制約は無い）
  8. 枠に {id, len, arc} を書き、その後にマスクのビットを立てる
  9. DLC ヘッダ +0x00..+0x34 は触らない（既存値を保持）
 10. CRC/チェックサムは既存の save 書き込み経路に任せる
```

ガードとして推奨:

* **ビットを立てるのは必ず枠を書いた後**（途中失敗で「ビットだけ立って枠が無い」状態を作らない）。
* position 41..44 は API で明示的に拒否（1020001 が来ても位置 0 に解決させる）。
* 枠のサイズ上限 0x13F8 を必ず検査（romfs の .arc = 33 KB 以上を弾く）。
* 1 回の操作で立てるビットは 1 個まで。

### 4.3 26 件の「今すぐ追加できるか」

（合計 26 件。上の 3 行で全部。1020020 は「追加できない実クエスト」に含まれる）

### 4.4 試験手順（実機確認）

1. セーブを複製する（save_backups に日付ディレクトリで）。
2. 1 件だけ追加する。**最初は 1010002（位置 46 / ビット 65）**がよい（配信版 .arc があり、位置が先頭寄り）。
3. ゲームの「イベントクエスト」一覧に出るか、名前が正しく出るか、開始できるか、クリア後も壊れないかを見る。
4. 出ない場合の切り分け: (a) ビットは立っているか、(b) 枠の id/size は正しいか、
   (c) ヘッダ +0x00..+0x34 が要るか（比較用に「追加前のセーブ」を残す）。
5. 装備枠が要る側の確認は、**別のセーブで 1020020 が導入済みのものを探す**のが先。
