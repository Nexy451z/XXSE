## 4. 特筆すべき発見

### 4.1 33 KB の正体はパディング（サイズの 94.8 %）【実測】

全 12 ファイルで、**エントリテーブル末尾から最初のデータまでがゼロで埋まっている**。

| | 9 エントリの 11 件 | q1011038 |
|---|---:|---:|
| ファイルサイズ | 33,772〜33,792 B | 33,446 B |
| 最初のデータオフセット | **0x8000 (32,768)** | **0x8000 (32,768)** |
| エントリテーブル末尾 | 732 B | 1,052 B |
| ゼロ埋めバイト数 | **32,036 B** | **31,716 B** |
| ゼロの割合 | **94.8 %** | **94.8 %** |
| 実際のデータ部 | **1,004〜1,024 B** | **678 B** |

- ヘッダの `flags`（+0x08）は **0xFFFFFFFE**。3DS 版の配信 .arc（`docs/quest_format_spec.md` の 141 サンプルでは 0）とは異なる値で、**Switch 版 romfs の配置（32 KB 境界）由来**と見られる【推定】。
- 中身と無関係なゼロが 94 % なので、**ファイルサイズの比較には意味がない**（§4.2 の「量産データ」判定もこれに注意）。

### 4.2 「量産データ」の正体 = ID 以外まったく同じ【実測】

未導入 48 件のサイズ分布: **33,790 B ×11 / 33,786 B ×7 / 33,789 B ×6 / 33,792 B ×2 / 33,793 B ×2**（28 件が 33.7 KB 台に密集）。

本担当の 12 件では **33,789 B が 6 件**（1011045〜1011050）そろっており、依頼文の例示（33,786 / 33,789 / 33,790）と一致する。
しかし重要なのはサイズではなく**中身**:

| 比較 | 結果 |
|---|---|
| q1011045 と q1011046 の .mib | 249 B 中 **2 バイトだけ**違う（+0x0C = クエスト ID、+0xE9 = `(id)_jpn` の数字 1 桁） |
| q1011045 と q1011046 の .gmd | 183 B 中 **2 バイトだけ**違う（資源名の ID 1 桁 + クエスト名の全角数字 1 文字） |
| .sem / .esl / .rem / .sup / .qdp / .qdl の 6 資源 | **完全一致**（sha256 が 11 件すべて同一） |
| q1011045 と q1011014 の .qdl | **完全一致**（.qdl は ID を持たない） |
| q1011045 と q1011014 の .mib | 5 バイト差（+0x0C ID / +0x1F tt1 / +0x4D p5 / +0xE8-9 名前） |

→ **「同サイズ＝量産データ」ではなく、「同一テンプレートの ID 差し替え」が量産の実体**。
11 件は 1 つの雛形から ID を機械的に振ったもので、それぞれ独立に作られたデータではない。

### 4.3 予備・欠番は romfs 全体に 31＋1＋2＋1 件ある【実測】

romfs のクエスト .arc **1,859 件すべて**の .gmd から名前を復元して数えた。

| 名前の型 | 件数 | 例 |
|---|---:|---|
| 「〜予備〜」 | **31** | ハンター下位予備１/２、ハンター上位予備１/２、ハンターＧ級予備４〜１２、ニャター下位予備１/２、ニャンター上位予備１/２、ニャンターＧ級予備１〜８ |
| 「欠番」 | **1** | q1011014 |
| 「予備枠」 | **2** | q1020030, q1120013 |
| 「未使用」 | **1** | q1010160 |
| dummy を含む名前 | **250** | q0090030〜q0090300 帯が 249 件、残り 1 件は q0000000（§4.4） |

- **インストール済み 175 件の中に「予備」「欠番」「未使用」は 0 件**【実測】。つまり予備・欠番は**そもそも配信対象にされていない**。
- 予備の連番は「下位１,２ → 上位１,２ → Ｇ級４〜１２」で、**Ｇ級予備１〜３ は romfs に存在しない**（本レポートで名前を復元した 223 件の中には無い）。理由は不明。

### 4.4 「本物のデバッグ遺物」は別の ID 帯にいる【実測】

romfs には**紛れもないテスト用クエスト**が存在する。ただしそれは本担当の 12 件ではなく、**q009xxxx 帯と q0000000** である。

- q0090030〜q0090300: クエスト名が文字列そのまま **dummy data**（q009 帯だけで **249 件**、romfs 全体では **250 件**。一部は **dummy**）
- q0000000: dummy data
- q0090030「ドス砂漠テスト」/ q0090033「シュレイド城テスト」/ q0090034「ラスボス砦テスト」/ q0090038「登場条件テスト②敵を倒した時」/ q0011365「闘技場での最終テストっチャ！」

→ **Capcom は「テスト」と名乗るデータを romfs に残している**。本担当の 12 件はこの帯に属さず、名前も「予備」「欠番」「アマツマガツチ（強化）」で、テスト用の命名規則（dummy / テスト）とは別系統。
**したがって 12 件を「デバッグ用」と判定する根拠は無い**（判定を「デバッグ疑い」ではなく「没データ疑い」にした理由）。

更新版 `main.bin` に **205 エントリ（ID, 通し番号）の表**を発見した（`0x1589D70`〜`0x158A3D8`、8 バイト × 205、重複 2 件を含む実ユニーク 200）。本担当 12 件の登録状況:

## 5. 導入可否

### 5.1 サイズ（実測）

**「33 KB だから 5,112 B の枠に入らない」は成り立たない。** 次の 2 つを実測した。

1. `mhnx arc-repack`（圧縮し直すだけ）→ **出力は元と同サイズ**（33,446〜33,792 B）。**縮まない**。
2. パディングを落として `dataStart = align32(12 + 80 × エントリ数)` で**再構築**（ペイロードのバイト列はそのまま、zlib 圧縮レベル 9）→

| ID | 元サイズ | 再構築後 | 5,112 B に収まるか |
|---|---:|---:|---|
| 1010176 | 33,785 B | **1,752 B** | ○ |
| 1010177 | 33,786 B | **1,753 B** | ○ |
| 1011014 | 33,772 B | **1,739 B** | ○ |
| 1011038 | 33,446 B | **1,734 B** | ○ |
| 1011045〜1011050 | 33,789 B | **1,756 B** | ○ |
| 1011051 | 33,792 B | **1,759 B** | ○ |
| 1011052 | 33,790 B | **1,757 B** | ○ |

再構築後は `mhnx check` の指摘内容が**元ファイルと完全に一致**すること、展開したペイロードが**バイト単位で一致**することも確認した【実測】。

**この形式が正しいことの裏付け【実測】**: セーブ側に入っている 175 件（`arcs/save_event/`）は **175/175 が「ヘッダ flags = 0、dataStart = align32(12+80n)」**で、サイズは **1,733〜3,453 B**（中央値 2,199 B）。つまり **romfs の 32 KB パディングは romfs 配置の都合であり、セーブ枠の形式ではない**。

→ **サイズの壁は無い。12 件すべて技術的には導入可能**。必要なのは「再圧縮」ではなく「パディング除去＝再構築」。
（この 2 つは別物で、`arc-repack` だけでは 1 バイトも縮まない点に注意）

### 5.2 判定別の導入可否

| 判定 | 件数 | 技術的サイズ | 実用性 | 推奨 |
|---|---:|---|---|---|
| 予備枠 | 10 | ○（1,752〜1,759 B） | **× 入れても遊べない**（モンスター 0・報酬 0・成功条件 dummy・quest_kind = なし） | **導入しない** |
| 欠番枠（1011014） | 1 | ○（1,739 B） | **×** 同上 | **導入しない** |
| 不明（1011038） | 1 | ○（1,734 B） | **△ 動く可能性はある**（中身は実データ: 1 体・実報酬・HR13）。ただし依頼主／依頼内容／主なモンスターが **Invalid Message と表示される**（推定） | 試験導入の価値はあるが、UI に未設定文字列が出る前提で扱う |

**補足（exe 表の有無による制約）**

- 1010177 と 1011048〜1011052 は **exe の ID 表に無い**。セーブのビットを立てて .arc を書いても、**クエストカウンターの一覧に出ない可能性が高い**【推定。§4.5 と【資料】`review_questfields.md`】。
- 表にある 6 件（1010176 / 1011014 / 1011038 / 1011045〜1011047）は、少なくとも登録上は「出せる枠」。
- ただし予備枠 5 件（1010176 / 1011045〜1011047）は、**入れても空のクエストが一覧に増えるだけ**。

### 5.3 手順（実測に基づく）

1. .arc を `dataStart = align32(12+80n)`・ヘッダ flags = 0 で再構築（本レポートの `.work/uninst2/rebuilt/*.arc` が実例）
2. サイズが 5,112 B 以下か確認（12 件すべて 1,734〜1,759 B で余裕）
3. セーブのクエスト枠へ書き込み、対応ビットを立てる
4. 1011038 のみ、.gmd の 3 文字列を実テキストに差し替える（差し替えれば「通常イベント相当」として扱える可能性がある）
