# DLC セクションの実測値

DLC セクションは本体 `+0xB280` から始まり、**ちょうど第1スロット基点で終わる**。
ここを1バイトでも間違えるとキャラクタデータを壊すので、値は実データで確認している。

## レイアウト

| オフセット | 長さ | 内容 |
|---|---|---|
| `+0x34` | 24 B | 未解明のマスク（実測 112 ビット） |
| `+0x4C` | 28 B | 導入済みマスク（実測 175 ビット） |
| `+0x45F4` | 205 × 0x1400 | クエスト枠 `{s32 id; s32 size; u8 data[size]}` |
| `+0x1049F4` | 45 × 0x800 | クエスト装備枠 |

合計は `0xB280 + 0x45F4 + 205*0x1400 + 45*0x800 = 0x126474` で、
第1スロット基点と**完全に一致**する。テストで固定している。

## `+0x34`（24 バイト・未解明）

```
FF FF FF FF FF 7F 80 07 FF FF FF FF FF FF FF 1F 00 00 00 00 00 00 00 00
```

| 項目 | 実測値 |
|---|---|
| 立っているビット | 112 |
| ビット範囲 | 0 .. 124 |
| 立っていないビット | 47-54, 59-63, 125-191 |
| 3スロット間 | **同一**（セクションはキャラ共通） |
| system と system_backup | **同一** |

`+0x4C` の**部分集合ではない**ので、別の意味を持つフラグ群。
クエスト数が 166→175 に増えても値が変わっていないことから、
クエストの導入状態を表すものではなさそうだが、**確証はない**。

### 検証して否定した仮説（+0x4C の順序）

| 仮説 | 結果 |
|---|---|
| ビット i = クエスト枠 i | 140/175 のみ一致 → **否定** |
| ビット (i+45) = クエスト枠 i | 111/175 のみ一致 → **否定** |

構造として分かっていること:

| 項目 | 実測値 |
|---|---|
| 枠 0..44 に入っているクエスト | 45 |
| 枠 45..199 に入っているクエスト | 130 |
| マスクのビット < 45 | 40（＝装備カタログ） |
| マスクのビット >= 45 | 135 |
| 枠 45 以降でビットが一致した数 | 100/130 |

枠 0..44 は**装備ビットと重なる**ため、そこで一致するのは偶然である。
枠 45 以降だけを見ても 100/130 で、規則性は見えない。

---

### 検証して否定した仮説（+0x34）

「立っているビット数 112 が、導入済みの 101xxxx 系クエスト 112 件と一致する」ことに気付き、
次の対応を試した。**いずれも成立しない。**

| 仮説 | 一致 | 不足 | 余剰 |
|---|---|---|---|
| ビット = ID − 1010001 | ✗ | 85 | 43 |
| ビット = ID − 1010000 | ✗ | 86 | 44 |
| ビット = ID − 1010101 | ✗ | 57 | 11 |

件数が一致したのは**偶然**だった。112 という数字だけで索引を決めつけると誤る、
という点で `+0x4C` と同じ罠である。

## `+0x4C`（28 バイト・導入済みマスク）

| 項目 | 実測値 |
|---|---|
| 立っているビット | 175（＝導入済みクエスト数） |
| ビット範囲 | 0 .. 214 |

### 索引はスロット番号ではない

「ビット i = スロット i」と考えると矛盾する実例がある。

- ビット 205〜214 が立っているが、クエスト枠は 0〜204 しかない
- ビット 25 は立っていないのに、スロット 25 にはクエストが入っている

合計が 175 で一致するのは「1ビット＝1クエスト」だからで、**順序の証拠にはならない**。
（このファイルも以前は 166 ビットだった。クエストを増やせば増える。）

### ビット 0..44 は装備カタログの索引そのもの（検証済み）

45 個の装備枠とビット 0..44 を全件突き合わせたところ、**1ビットも違わず一致**した。

| 項目 | 実測値 |
|---|---|
| ビット 0..44 で立っている | 0-24, 26-40（40個） |
| 装備枠で中身がある | 0-24, 26-40（40個） |
| ビット25 | 立っていない ↔ 装備枠25が空 |
| ビット41..44 | 立っていない ↔ 装備枠41..44が空 |

つまり **ビット i ⟺ 装備枠 i に中身がある**。この範囲ではカタログ順＝配列順である。

残りのビットは導入済みイベントクエスト 135 件に対応し、40 + 135 = 175 で合計が合う。

### 装備枠はクエスト ID を持つ

各枠の先頭 4 バイトがそのクエストの ID である。

| 枠 | 先頭 u32 | 内容 |
|---|---|---|
| 0 | 0x000F9061 | 1020001 |
| 1 | 0x000F9062 | 1020002 |
| 14 | 0x00111801 | **1120001**（ここで系統が変わる） |
| 20 | 0x000F906F | 1020015（**戻る**） |
| 25 | — | 空 |
| 41..44 | — | 空 |

使用中の 40 枠すべてについて、その ID のクエストは実際にセーブへ導入済みだった。
並びは ID 順でも連番でもなく、**ゲーム側のカタログ順**である。

`mhnx equip-list` で一覧、`mhnx equip-export` で取り出せる。

カタログ順であることは分かっている（0〜40 が装備カタログ45件に対応）が、
**カタログの並び順を復元する手段がない**ため、このツールはマスクを一切書かない。
既存クエストの差し替えはビットを変えないので安全に行える。

## 未解明

| 項目 | 状態 |
|---|---|
| `+0x34` の意味 | 24 バイトのマスク。112 ビット。意味不明 |
| カタログの並び順 | 復元不可。別構成のセーブかゲームデータが必要 |
