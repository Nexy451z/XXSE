3. **判定は「期待 / 実測 / 判定」の 3 列で残す**（7 章のテンプレ）。

### 1.2 CFW 種別と起動モードの確認

**この検証は emuMMC 上で行う【推奨】。** sysNAND で行う場合、失敗時の影響が本体そのものに及ぶ。
emuMMC なら SD 上のコピーが壊れるだけで、本体 NAND は無傷。

1. 本体設定 → 本体の更新情報を開き、**version の末尾 1 文字**を読む
   - 末尾が **E**（`AMS x.y.z` の後ろに E が付く）→ emuMMC で起動している（このまま進めてよい）
   - 末尾が **S** → sysNAND。**一旦 CFW を抜け、hekate から emuMMC で起動し直す**
2. 起動時に hekate のメニューが出る構成なら、`Launch` → `Atmosphere (EMUMMC)` を選ぶ
3. SD の次のファイルで構成を確認する【要確認: 実際の SD で読むこと】
   - `sd:/atmosphere/package3` … Atmosphere 本体（無ければ CFW 構成が違う）
   - `sd:/bootloader/hekate_ipl.ini` … 起動エントリ（emuMMC の有無）
   - `sd:/atmosphere/contents/` … ここに mod を置く（5 章）

> **注意**: 起動モードを間違えると、編集したセーブが「別の NAND のセーブ」に反映されず、
> 「効かない」と誤判定する。実験前に必ず 1.1 の #6 を埋める。

### 1.3 オフライン固定（BAN 回避・再現性のため）

- 機内モード、または exosphere / 90DNS で任天堂へ接続しない。
- 本検証は**オフラインで完結する**（【事実: 実セーブには配信クエスト 175 件の実体が入っており、
  既存のイベントクエストはオンライン無しで一覧に出る。1.7 のベースラインで確認する】）。
- 追加したクエストを「配信」する必要は無い。**セーブに直接書く**のがこの検証の方法。

### 1.4 セーブのバックアップ（3 段構え）

#### B1: いま手元にある正解（PC 側）

```powershell
$SRC = "$env:APPDATA\Ryujinx\bis\user\save\0000000000000001"   # Ryujinx 側の現物
$BAK = "C:\anyWorkspace\nx\mhxx\save_backups\verify_20261020"
New-Item -ItemType Directory -Force $BAK, "$BAK\0", "$BAK\1" | Out-Null
Copy-Item "$SRC\0\system"        "$BAK\0\system"        -Force
Copy-Item "$SRC\0\system_backup" "$BAK\0\system_backup" -Force
Copy-Item "$SRC\1\system"        "$BAK\1\system"        -Force
Copy-Item "$SRC\1\system_backup" "$BAK\1\system_backup" -Force
Get-ChildItem $BAK -Recurse -File |
  ForEach-Object { "{0}  {1}" -f (Get-FileHash $_.FullName -Algorithm SHA256).Hash, $_.FullName }
```

期待（現物の実測値【事実】）:

| ファイル | サイズ | SHA256 |
|---|---|---|
| `0\system` | 4,726,188 | `D06B72520E379F462D49098E55C270BA48B203C10A9DBF39A1F8EE7E410C112A` |
| `0\system_backup` | 4,726,188 | `702FAFC7D809D85DAD8E6AAEB5EC609DE67B5AB3E3727EF95FA17E3353AA33AF` |
| `1\system` | 4,726,188 | `0\system` と同一 |
| `1\system_backup` | 4,726,188 | `0\system_backup` と同一 |

**重要な事実**: `0` と `1` は完全なミラー（同ハッシュ）、`system` と `system_backup` は**別内容**。
実体は 2 種類。書き戻すときは **4 ファイルとも同じ新しい内容で揃える**（【事実: 現物のハッシュ比較】）。

#### B2: 実機側のバックアップ（Checkpoint もしくは JKSV）

1. ゲームを完全終了する（ホーム → ゲームにカーソル → X → 終了）
2. hbmenu から Checkpoint を起動 → MHXX を選ぶ → `Backup`
3. 出力先は既定で `sd:/switch/Checkpoint/saves/0100C3800049C000/<名前>/`【要確認: アプリの設定画面に実際のパスが出る】
   - JKSV なら `sd:/JKSV/...`
4. そのフォルダを **PC へ丸ごとコピー**する（ここが実機検証の「正解」）

#### B3: 二重化

- B2 のフォルダを PC と SD の**別名フォルダ**に 1 つずつ残す（例: `verify_20261020` と `verify_20261020_KEEP`）。
- `verify_20261020_KEEP` は**検証中に絶対触らない**。ここを触ると戻せなくなる。

### 1.5 復元手順

1. ゲームを完全終了
2. 書き戻したいバックアップのフォルダの中身を、**編集後の `system` と `system_backup` で上書き**する
   （Checkpoint はフォルダ内のファイルをそのまま書き戻す。`system` だけ差し替えて `system_backup` を古いまま残さないこと）
3. Checkpoint → MHXX → 復元したいバックアップを選ぶ → `Restore`
4. ゲームを起動し、1.7 のベースラインが戻っていることを確認する

代替（Checkpoint が失敗する場合）:

- JKSV で同じ操作
- 最悪の場合は 本体設定 → データ管理 → セーブデータの削除 → ゲーム起動（新規作成）→ Checkpoint で復元
  （**必ず B3 の控えがある状態で行う**）

### 1.6 壊れたときの戻し方（症状別）

| 症状 | まず疑うもの | 戻し方 |
|---|---|---|
| 起動時に「セーブデータが壊れています」 | セーブ編集（実験 1/2） | 1.5 の復元。SD の mod は無関係なので触らない |
| ゲームは起動するがクエスト一覧が空／重い | セーブの DLC セクション | 1.5 の復元 |
| クエスト選択でフリーズ→再起動 | 追加した枠のペイロード | 1.5 の復元（枠を消すだけではビットが残るので**必ずファイルごと戻す**） |
| 起動直後にブラックアウト（romfs 実験後） | LayeredFS の差し替えファイル | `sd:/atmosphere/contents/0100C3800049C000/romfs/` を**丸ごと削除**（元ファイルは無傷） |
| hbmenu が起動しない | SD の破損／CFW 構成 | SD を PC でチェック。`atmosphere/contents` を一時退避して切り分け |
| 本体が起動しない | CFW 構成（本検証の範囲外） | hekate からペイロード再送。**本検証は NAND を触らないので原因になり得ない**（【事実: 変更は SD 上のファイルとセーブデータのみ】） |

> **鉄則**: 追加クエストを「枠だけ消す」戻し方はしない。`dlc::uninstall_quest` は枠を 0 埋めするが
> **マスクビットは消せない**（【事実: `crates\mhnx-core\src\dlc.rs` 665–675 行のコメント】）。
> 中途半端な状態を作らず、**バックアップのファイルごと戻す**。

### 2.2 手順（2 案のどちらか）

**案 B: CLI でダウンロードオトモを 1 匹消す**

## 3. 実験 1: 追加クエストが一覧に出るか

### 3.1 対象と根拠

| 項目 | 値 | 根拠 |
|---|---|---|
| クエスト ID | `1010002` | 依頼の指定 |
| カタログ位置 | **46** | 【事実: `gamedata::DLC_CATALOG[46]` を数えた結果】 |
| マスクビット | **65** = `64 + (46 - 45)` | 【事実: イベント側の式（`dlc::bit_for_position`）と実セーブ 175/175 一致】 |
| 書き込み先の枠 | **135** | 【事実: `add_quest` は「size == 0 の先頭の枠」を選ぶ。空きは 135..159 と 200..204】 |
| 配信版 .arc | `save_editor\mhxx_quetool\quest\q1010002.arc`（3,653 B） | 【事実: 枠上限 5,112 B に収まる。romfs 版は 35,258 B で**入らない**】 |
| クエスト名 | `サンリオ・ひとぐでしようぜ` | 【事実: `mhnx arc-gmd`】 |
| 内容 | 下位 / 制限時間 50 分 / 復活 3 / **納品 3** / 参加条件なし（ソロ可） | 【事実: `mhnx arc-mib`（`quest_kind 大連続(3)`, `rank1 下位(1)`, `cond1 なし`）】 |

> **なぜ romfs 版を使わないか**: romfs の `q1010002.arc` は 35,258 B で、クエスト枠 5,120 B に物理的に入らない
> （【事実: 実測サイズ】）。セーブの DLC 枠に入るのは「配信版」（quetool 側の再圧縮版）だけ。

**この実験で確かめる仮説（1 文）**:
「マスクビット 65 と、ID が一致するクエスト枠が 1 つあれば、ゲームは一覧に出す」

- 対立仮説 A: 一覧はビットではなく**枠の位置**で決まる
  （実セーブでは位置とカタログ位置がバラバラなので弱い【事実: 位置 133 → 枠 0、位置 45 → 枠 59 など】）
- 対立仮説 B: 一覧は **exe 側の固定表**だけから作りビットを見ない
  （これだと既存 175 件と未導入 26 件の区別がつかず矛盾する【推定】）

### 3.2 PC 上で作る

```powershell
Set-Location C:\anyWorkspace\nx\mhxx\mhnxeditor
$M   = ".\dist\mhnx.exe"
$W   = "C:\anyWorkspace\nx\mhxx\mhnxeditor\.work\verify\e1"
$ARC = "C:\anyWorkspace\nx\mhxx\save_editor\mhxx_quetool\quest\q1010002.arc"

New-Item -ItemType Directory -Force $W | Out-Null
# 実験 0 を通したセーブを入力にする（実験 0 の変更はそのまま残してよい）
Copy-Item "<バックアップ>\system"        "$W\system.before"        -Force
Copy-Item "<バックアップ>\system_backup" "$W\system_backup.before" -Force

& $M add-quest "$W\system.before" $ARC "$W\system.after"
& $M check-save "$W\system.after"
& $M dlc-list "$W\system.after" | Select-String "1010002"
```

**期待する出力（実測どおり）**（【事実: このマシンで実行した出力】）:

```text
added quest 1010002 to slot 135 (mask bit 65), wrote C:\...\system.after
the input save was not modified

  info  ok                   問題は見つかりませんでした
  (176 download quest(s) installed)
  slot 135  id 1010002    3653 B  サンリオ・ひとぐでしようぜ
```

`slot` が 135 以外になった／`mask bit` が 65 以外になった場合は**そこで中止**する
（セーブの状態が想定と違う＝以降の期待値が全部ずれる）。

### 3.3 差分の検証（PC 上で必ず行う）

期待する差分は **2 か所だけ**。それ以外が変わっていたら中止。

| 場所 | ファイル絶対オフセット | 変更前 → 変更後 |
|---|---|---|
| マスク（bit 65 = 枠 8 の bit 1） | `0xB2F8` | `0xFD` → `0xFF` |
| クエスト枠 135 のヘッダ | `0xB8498`（id） / `0xB849C`（size） | `0` → `1010002`、`0` → `3653` |
| クエスト枠 135 のペイロード | `0xB84A0` から 3,653 B | 配信版 .arc のバイト列 |
| 未解明領域 | `0xB2C8`..`0xB2E7`（DLC+0x24..+0x43） | **変化なし（不変であること）** |
| ファイルサイズ | 全体 | `4,726,188` のまま |

検証スクリプト（そのまま貼ってよい）:

```powershell
$a = [System.IO.File]::ReadAllBytes("$W\system.before")
$b = [System.IO.File]::ReadAllBytes("$W\system.after")

"size same      : {0}" -f ($a.Length -eq $b.Length)
"mask 0xB2F8    : 0x{0:X2} -> 0x{1:X2}" -f $a[0xB2F8], $b[0xB2F8]
"slot135 id     : {0} -> {1}" -f [BitConverter]::ToInt32($a,0xB8498), [BitConverter]::ToInt32($b,0xB8498)
"slot135 size   : {0} -> {1}" -f [BitConverter]::ToInt32($a,0xB849C), [BitConverter]::ToInt32($b,0xB849C)

$sec = 0xB2A4
$same = $true
for ($i = 0x24; $i -le 0x43; $i++) { if ($a[$sec+$i] -ne $b[$sec+$i]) { $same = $false } }
"unknown +0x24..+0x43 unchanged: {0}" -f $same

$idx = for ($i=0; $i -lt $a.Length; $i++) { if ($a[$i] -ne $b[$i]) { $i } }
```

## 4. 実験 2: 支給品の差し替えが反映されるか

### 4.1 対象と根拠

| 項目 | 値 | 根拠 |
|---|---|---|
| 装備枠 | **slot 0**（クエスト `1020001`） | 【事実: `mhnx equip-list`】 |
| レコード | **rec 0**（武器種 14 = **太刀**） | 【事実: `review_questequip_full.md` §2.3（1020001 の 5 値 = 14,19,21,10,13 が依頼文の武器種列挙と順序一致）】 |
| 支給品リスト | A（ボディ +0x53、24 枠 × 3 B） | 【事実: レイアウト実測】 |
| 現在値 | `A[0] = item 1724 ×2`（支給専用秘薬） | 【事実: `mhnx equip-items 0`】 |
| 差し替え先 | `item 1722 ×1`（支給専用閃光玉） | 同じ支給専用系で、アイコンも個数も変わる |
| 書き込み位置 | ファイル絶対 **1,113,363**（`0x10FD13`） | 【事実: `equip-set` の差分実測（0xBC 0x06 0x02 → 0xBA 0x06 0x01）】 |

**この実験で確かめる仮説（1 文）**:
「クエスト装備枠（セーブ）の A リストが、ゲーム内の支給品として使われる」

**重要な裏づけ**: `1020001` の .arc 内の `.sup` は `supp_0000000`（**中身が空**）

つまりこのクエストの支給品は `.sup` からは作れず、**セーブの装備枠以外に供給元が無い**。
「もし反映されなければ装備枠が支給品の供給元ではない」という強い切り分けになる。

### 4.3 差分の検証

| 場所 | オフセット | 変更前 → 変更後 |
|---|---|---|
| A[0] の item 下位 | `0x10FD13` | `0xBC` → `0xBA` |

| それ以外 | — | **変化なし**（実測で差分は 2 バイトのみ） |

```powershell

$idx = for ($i=0; $i -lt $a.Length; $i++) { if ($a[$i] -ne $b[$i]) { $i } }
"changed {0} byte(s): {1}" -f $idx.Count, (($idx | ForEach-Object { "0x{0:X}" -f $_ }) -join ", ")
"item/count: {0:X2} {1:X2} {2:X2} -> {3:X2} {4:X2} {5:X2}" -f $a[0x10FD13],$a[0x10FD14],$a[0x10FD15],$b[0x10FD13],$b[0x10FD14],$b[0x10FD15]
```

期待: `changed 2 byte(s): 0x10FD13, 0x10FD15` / `item/count: BC 06 02 -> BA 06 01`

## 5. 実験 3: 村クエストの差し替え（romfs / LayeredFS）

> **この章は `docs\review_romfs_patch.md`（作成中）の結論と突き合わせて使う。**
> 同ファイルが未作成の段階でも進められるよう、判断に必要な実測を本章に直接書いてある（5.1）。
> 5.8 のチェックリストで結論が一致しているかを必ず確認すること。

### 5.1 前提（実測）

| 事実 | 値 | 根拠 |
|---|---|---|
| 更新（v1.5.1）の NSP 構成 | NCA 4 本: 5,632 B / **61,876,224 B** / 203,776 B / 145,920 B | 【事実: NSP の PFS0 ヘッダを直接解析】 |

### 5.3 3A: テキストだけ差し替えて「どのファイルが読まれるか」を決める

最初に**ゲームロジックを変えない変更**で経路を確定させる。ここを飛ばすと、失敗したときに

4. できた .arc を `sd:/atmosphere/contents/0100C3800049C000/romfs/nativeNX/arc/quest/q0000101.arc` に置く
5. ゲームを再起動し、**村クエスト一覧**の表示を見る
6. 一覧が変わらなければ、そのクエストを**受注画面まで進めて依頼内容**を見る

| 観察 | 解釈 | 次にやること |

| 一覧は変わらないが、受注画面の依頼内容が変わる | 一覧は vq.arc、実データは q0000101.arc | 5.5（3B）で vq.arc を差し替える |

### 5.4 3C: 支給品を差し替える（村クエスト側の供給元の確認）

### 6.2 なぜ本体とセーブは壊れない設計なのか

1. **NAND を触らない**。変更は「SD 上のファイル」と「セーブデータ」だけ【事実: 手順に NAND 書き込みが無い】
2. **セーブは必ずコピーに対して編集**し、`add-quest` / `equip-set` は**入力ファイルを書き換えない**
   （出力先を別に指定する。実測ログに `the input save was not modified` と出る）【事実】
3. **書き込み前に元ファイルを `.bak` へ退避**する仕様が GUI/実機ともに入っている【事実: README「書き込み前のバックアップ」】
4. **LayeredFS は重ね合わせ**なので、元の romfs ファイルは物理的に無傷。差し替えファイルを消せば完全に元通り
5. **変更が局所的**: 実験 1 は 1 バイト（マスク）+ 1 枠、実験 2 は 3 バイト。他クエスト・キャラ・アイテムには触れない【事実: 差分実測 3.3 / 4.3】
6. **未解明領域（DLC+0x24..+0x43）を書かない**。`add_quest` も `equip-set` もこの範囲を触らない【事実: 差分検証で不変を確認】

| 禁止 | 理由 |

| sysNAND で検証する | 失敗時の影響が本体に及ぶ |

## 8. 優先順位とバッチ計画

### 8.1 起動のまとめ方

**原則**: 1 回の起動で確かめるのは**同じ系統の変更だけ**。セーブ編集と romfs 差し替えは混ぜない。

| 起動 | 載せる変更 | 確かめること | 中断条件 | 目安 |
|---|---|---|---|---|
| **Boot 1** | セーブ: 実験 0（所持金/オトモ）+ 実験 1（`1010002` 追加） | ①編集セーブが読まれる ②一覧に新しいクエストが出る ③情報画面が正しい | ①が FAIL → 以降すべて中止 | 20 分 |
| **Boot 2** | セーブ: Boot 1 の状態 + 実験 2（支給品 3 B） | ④`1010002` を開始できる ⑤闘技大会 `1020001` を太刀で開始し、支給品BOX が変わる | ④で落ちる → 実験 2 は別起動に分ける | 25 分 |
| **Boot 3** | romfs: 3A（`q0000101.arc` のテキスト） | ⑥村クエスト一覧の表示が変わるか（＝置き場所の確定） | ⑥が「どこも変わらない」→ 5.6 の切り分けへ | 15 分 |
| **Boot 4** | romfs: 3C（`.sup` の支給品） | ⑦村クエストの支給品BOX が変わる | — | 20 分 |
| **Boot 5**（任意） | romfs: 3B（`vq.arc` のテキスト） | ⑧一覧テキストの供給元 | Boot 3 で確定していれば不要 | 15 分 |

- **Boot 3 以降はセーブを触らない**。セーブは Boot 2 の結果（または実験前）のままでよい。
- 合計 **約 1.5〜2 時間**（うち復元・記録が半分）。

### 8.2 優先順位（時間が足りない場合）

1. **実験 0**（これが無いと他が判定できない）
2. **実験 1**（依頼の中心。追加が通れば今後の機能追加の前提が変わる）

- セーブ破損表示が**復元しても直らない**
