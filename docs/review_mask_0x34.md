# 未知マスク DLC+0x34（24 バイト）の調査

対象セーブ（**読み取りのみ、書き込みなし**）:
`C:\Users\haruk\AppData\Roaming\Ryujinx\bis\user\save\0000000000000001\0\system`

* ファイル長 4,726,188 B / 本体ヘッダ 36 B / 本体 4,726,152 B
* `body[0x0C]` = 0xB280（DLC セクション）→ ファイル絶対位置 0xB2A4
* セクション長 = 0x126474 − 0xB280 = 0x11B1F4（クエスト枠 + 装備枠の終端が第1キャラ基点と一致、再確認済み）
* 計測は Python で生バイトを直接読み、CLI（`dist/mhnx.exe save-info dlc-list`）は突き合わせのみに使用

---

## 0. 結論（先に）

1. **意味は特定できなかった。** 「112 件」という件数に合う候補（ハンター系クエスト 112 件、等）はあるが、
   下の §3 のとおり**全て実データで反証**された。件数一致は根拠にしない。
2. 一方で**構造の事実**は確定した（§1）。とくに
   **「24 バイト枠のうち実際に値が入るのは先頭 16 バイト（128 ビット）だけ**」「**左側に境界が無い**（+0x24 から連続して非ゼロ）」
   の 2 点は、これまでの「+0x34 から 24 バイトのマスク」という枠取り自体が**人為的な切れ目**であることを示す。
3. **導入済みクエスト状態との相関は統計的に検出できない**（§3-H）。重なり 102 ビット、独立なら期待 102.08。
   つまり「クエスト数が 166→175 に増えても変化しない」という観測と整合する。
4. 24 バイト = 192 ビットという枠の大きさは、**MHXX の DLC クエスト総カタログ数 192（チャレンジ 41 + イベント 151）と一致**する（§2）。
   ただしこれは「枠の大きさが一致する」だけで、**中身がそのカタログの導入状態である証拠にはならない**（§3 で否定）。
   この一致をどう扱うかは §5「推測」に分離した。

## 1. 実測した構造（事実）

### 1.1 セクション先頭の非ゼロ範囲（実測）

セクション相対で、`+0x00`〜`+0x45F3` を走査した結果（非ゼロバイトは合計 1,198 個）:

```text
+0x001          1 B
+0x00B          1 B
+0x010          1 B      (u32 = 15)
+0x014..0x01C   9 B
+0x020          1 B      (u32 = 31)
+0x024..0x043  32 B   ← 連続非ゼロ。ここに +0x034 が含まれる
+0x04C..0x051   6 B
+0x054..0x066  19 B   ← 導入済みマスク（+0x4C..0x67）の後半
+0x068..0x069   2 B      (u16/u32 = 0x418A = 16778)
+0x06A..0xAF7   全部ゼロ
+0x0AF8..0x0D68  文字列を含むレコード群（後述）
+0x0D69..0x1D97  全部ゼロ
+0x1D98..0x233E  名前・挨拶を含むレコード群
+0x233F..0x45F3  全部ゼロ
```

### 1.2 +0x34 の 24 バイトの中身（実測）

```text
+0x34  FF FF FF FF FF 7F 80 07 FF FF FF FF FF FF FF 1F 00 00 00 00 00 00 00 00
```

| 項目 | 実測値 |
|---|---|
| 立っているビット | **112** |
| 立っている範囲 | 0 .. **124** |
| 立っていないビット | 47–54（8）, 59–63（5）, **125–191（67）** |
| 非ゼロのバイト | **先頭 16 バイトのみ**（+0x34..+0x43）。**+0x44..+0x4B は 8 バイト全部 0** |
| u32 × 6 | `FFFFFFFF`, `07807FFF`, `FFFFFFFF`, `1FFFFFFF`, `00000000`, `00000000` |
| u32 ごとの立っている数 | **32, 19, 32, 29, 0, 0** |
| u64 × 3 | 51, 61, 0 |

**読み取れること**: ゼロは「ワード 1（ビット 32–63）の 13 ビット」「ワード 3 の上位 3 ビット」「ワード 4・5 の 64 ビット」に集中している。
ワード 0・2 は 32/32、ワード 3 は 29/32 で、**ワード 1 だけが 19/32**。

### 1.3 24 バイトは単独構造ではない（質問 5 への回答の根拠）

* **左境界が無い**: 非ゼロは `+0x24` から始まり `+0x43` まで連続する（32 バイト）。
  `+0x24` のバイトは `F0`（下位 4 ビットが 0）で、そこから `+0x43` まで 1 バイトもゼロが無い区間がある。
  つまり **+0x34 という切れ目はデータ側に現れていない**（MHX のマスク位置 0x34 から引き写した人為的な境界）。
* **右境界はある**: `+0x43` の次 `+0x44..+0x4B` が 8 バイト連続ゼロで、その次が `+0x4C` の導入済みマスク。
* **+0x4C 側の右端**: 28 バイトの最終バイト（+0x67）は `00`。よって導入済みマスクの有効域は 0..214。
* したがって「+0x34 から 24 バイト」は、**(a) 16 バイトのマスク + 8 バイトの予備**、
  **(b) +0x24 から 32 バイトの構造の後半 24 バイト**、のどちらかとして読むのが自然。
  この 2 つは「ビット 0..127 が有効」という点で一致するので、以下の検証は 128 ビット前提でも 192 ビット前提でも同じ結果になる（§3 は両方載せた）。
* セクション内には他種のデータも同居する（事実）: `+0xAF8` に ASCII `MHXX`、続いて UTF-8 で
  `ハチミツセット` / `ハンター支援セット` / `MH頂上` / `MH頂上大会支援セット` / `MH頂上大会記念セット` / `MHXX限定パック` / `新米ハンター強化セット`
  等のセット名が並ぶ（0xAF8–0xD68 は 0x68 バイト刻みの 6 ブロック。名前 + 作成者 + アイテム列という並びは**推測**）、
  `+0x1D98..+0x233E` に `ナナコｘｘ` / `笑顔の店員` / `近くて便利なセブンに行くニャ` / `ジョイルポ` / `カリオケ` 等の名前・挨拶レコード群。
  → このセクションは「配信クエスト + 配信アイテムセット + 配信オトモ等」の共有ブロックで、
  先頭 0x68 バイトがそのヘッダ部。**+0x34 はそのヘッダ部の一部**。

### 1.4 3 ファイル間の一致（自行確認）

`0/system`, `1/system`, `0/system_backup` の 3 つで `+0x34`（24 B）と `+0x4C`（28 B）を実測:

```text
0/system            0x34: ffffffffff7f8007ffffffffffffff1f0000000000000000
1/system            0x34: ffffffffff7f8007ffffffffffffff1f0000000000000000
0/system_backup     0x34: ffffffffff7f8007ffffffffffffff1f0000000000000000
```

3 ファイルで完全一致（0x4C も一致）。**差は無い**ので差分解析はできない。

## 2. 前提の再検証（+0x4C のモデルが正しいことの確認）

+0x34 を読む前に、比較対象である +0x4C の意味がどこまで確定しているかを実測で確かめた。

| 項目 | 実測 |
|---|---|
| +0x4C 下位（ビット 0..40）と装備枠 0..44 の中身 | **40/40 完全一致**。ビット 25 のみ 0 ↔ 装備枠 25 が空（= 1020020 が未導入） |
| 装備枠 41..44 が空 | ビット 41..44 も 0（矛盾なし） |
| ビット 64..214 | 151 枠・**135 ビット**。導入済みイベントクエスト **135 件**と同数で、単射対応する |
| ビット 45..63 | 全部 0（パディング） |
| ビット 215..223 | 全部 0（パディング。最終バイト +0x67 = 0x00） |

カタログ規模（`docs/quest_format_spec.md` の ID 体系 + `questID_memo.txt` 由来の範囲で機械集計）:

| 区分 | ID 範囲 | カタログ数 | 本セーブの導入数 |
|---|---|---|---|
| ハンター 下位 | 1010001–1010006 | 6 | 4 |
| ハンター 上位 | 1010101–1010176（6 個欠番） | 70 | 66 |
| ハンター G | 1011001–1011047（2 個欠番） | 45 | 42 |
| オトモ 下位 | 1110001–1110008 | 8 | 6 |
| オトモ 上位 | 1110101–1110113 | 13 | 10 |
| オトモ G | 1111001–1111009 | 9 | 7 |
| 訓練（チャレンジ） | 1020001–1020029 | 29 | 28 |
| 訓練オトモ | 1120001–1120012 | 12 | 12 |
| **イベント計** | | **151** | **135** |
| **総計** | | **41 + 151 = 192** | **175** |

* イベント 151 = +0x4C のビット 64..214 の枠数（151）と一致。
* チャレンジ 41（装備枠は 45 枠だが、ID を持つのは 41 枠。41..44 は ID 無しの予備枠）= ビット 0..40 の枠数と一致。
* **41 + 151 = 192 = 24 バイト × 8 ビット**（+0x34 の枠の大きさ）。
  一方、装備枠 45 で数えると 45 + 151 = 196 でバイト境界に合わない。

**注意（重要）**: 「枠の大きさが 192 で一致する」ことは**件数一致と同じ種類の弱い証拠**である。
この一致から「+0x34 は 192 件カタログのマスクだ」と決めると、このプロジェクトで 3 回踏んだ罠を 4 回目に踏む。
実際 §3 で、192 枠・151 枠・121 枠いずれの読みでも中身が合わないことを示す。

### 2.1 補足: イベント領域の順序は「ID 昇順」ではない（実測）

ビット 64..214 の 151 枠に対し、ID 昇順カタログを素直に当てると **120/135 しか一致しない**（15 個ずれ）。
ずれ方の例: 空きビットは 16 個あるが、その位置を「未導入 ID」で埋めると
`k=19,20`（ビット 83,84）のように **連続した空き**が「導入済み ID 1010114 と 1010115 の間」に来て矛盾する。
→ カタログ順は ID 昇順から局所的にずれている（配信順など）か、未配信のプレースホルダ枠を含む。
**この順序は本セーブからは復元できない。**

## 4. 質問への回答

### Q1. この 24 バイトは何の集合か

**特定できなかった。** 一方で、次の 3 点は実データで言い切れる。

1. **クエストの導入状態ではない**（A3/A4/A6/A10/A11/A13 と G/H で否定。相関は偶然期待値と同水準）。
2. **クエスト枠の使用状態でもない**（A1/A2。空きの 13 ビットはすべて「クエストが入っている枠」を指す）。
3. **装備枠の中身でもない**（A5/A8/A9 は自明一致のみ。かつ 0..46 が全部 1 なので装備枠 25・41–44 の空きと矛盾）。

残る候補（**推測**、検証は §6）: 192 ビットという枠の大きさが DLC カタログ総数 192 と一致するため、
「カタログ 192 件に対する別種のフラグ（配信済み・受信済み・閲覧済み等）」の可能性は残る。
ただし 175 件が導入済みである以上、「導入」以外のフラグで 112 件だけが立つ理由は本セーブからは説明できない。

### Q2. 47–54 と 59–63 が空いている理由。装備枠の空き（25, 41–44）と関係あるか

* **装備枠の空きとは無関係（実測）**: 空きビット集合 {47..54, 59..63} と装備枠の空き {25, 41..44} の共通要素は **0 個**。
  逆に、装備枠が空いている 25・41・42・43・44 のビットは **すべて 1**。
* **クエスト枠の空きとも無関係（実測）**: 47..54 と 59..63 のスロットは **13/13 すべてクエストが入っている**。
* 構造として言えるのは「ゼロはワード 1（ビット 32..63）に集中している」ことだけ（ワード 1 = 19/32、他は 32/32・32/32・29/32）。
  ワード 1 の内訳は「0..14 が 1（15 個）／15..22 が 0（8 個）／23..26 が 1（4 個）／27..31 が 0（5 個）」。
* 理由は**不明**。ただし「8 個 + 5 個の連続したゼロ」は、疎なフラグではなく**何かの区切り**（未使用域・別カテゴリの境界）を示唆する（**推測**）。

### Q3. ビット 125..191 が全部 0 なのは何を意味するか

* **実測**: ビット 125..191 の 67 ビットがすべて 0。ビット 125・126・127 も 0。
  非ゼロは先頭 16 バイト（+0x34..+0x43）に限られ、**+0x44..+0x4B の 8 バイトは完全にゼロ**。
* したがって **実効幅は 128 ビット**と考えるのが自然（24 バイト枠の後半 8 バイトは予備/未使用）。
  「192 ビットあって上位 67 ビットが 0」と読むことも可能だが、その場合 192 = カタログ総数という枠の一致を
  「上位 67 件が未マーク」と読むことになり、175 件導入済みという事実と矛盾する（§3 A12）。
* **上限説（128 件で打ち止め）は否定できないが、証明もできない**。索引空間が 128 件だとすると、
  0..124 に 112 件、125..127 が未使用という「端が揃った」形になる（**推測**）。

### Q4. 114〜124 のビットが立っているのは何に対応するか

* これらは**ワード 3（ビット 96..127）の連続 29 ビット（96..124）の一部**。
  ワード 3 は 29/32 で、0 なのは 125・126・127 の 3 ビットだけ。つまり 114..124 は特別ではなく、
  「96 から 124 まで連続して立っている領域の末尾」。
* 装備枠が 45 までしかないことは無関係（装備枠の索引はビット 0..40 で、114..124 はそこから遠い）。
* 無理に意味を当てると（いずれも**推測**で証拠なし）:
  * 昇順カタログ読みなら 114..124 は 1010174–1010176 と 1011001–1011008 付近
  * 192 枠フラット [チャレンジ41 → イベント] 読みなら イベント 73..83 番目
  * どちらも「対応している」証拠は無い（§3 のとおり、どの読みも全体では破綻する）。
* 付随して: ワード 3 の 29 という数は訓練クエスト 29 件（1020001–1020029）と一致するが、
  **件数一致は証拠にしない**（このプロジェクトで 3 回踏んだ罠）。実測でもワード 3 の位置に訓練クエストの索引は無い。

### Q5. 近傍のバイトから見た位置づけ

* `+0x28..+0x33`（= ワード 0x28,0x2C,0x30）は `FFEFFFFF`, `FFFFFC07`, `FFFFFFFF` で、**+0x24 から続く連続非ゼロ帯の一部**。
  `+0x24` = `F0`（下位 4 ビットが 0）、`+0x2C` = `07 FC` と、内部にもゼロはあるが、バイト単位の途切れは無い。
* `+0x68` = `8A 41 00 00`（u32 = 16778 = 0x418A）。そのあと `+0x45F3` まで**全部ゼロ**。
  CRC/チェックサム説は検査したが一致しなかった（単純な CRC32/CRC16/総和 × 6 範囲では 0x418A も 0x7A00 も出ない）。
* 結論: **単独構造ではなく、0x00–0x68 の共有ヘッダ部の一部**。しかも +0x24 からの 32 バイト帯の後半である可能性が高い。
  よって「+0x34 から 24 バイト」という現在のドキュメントの枠取りは、
  **MHX のマスク位置（0x34）に引きずられた人為的な境界**である可能性がある（**推測**、ただし左境界が無いことは実測）。

## 5. 推測（証拠と分離して明記）

* （推測）24 バイト = 192 ビットという枠の大きさが、MHXX DLC の総カタログ数 41 + 151 = 192 と一致する。
  もしこれが構造的な対応なら、このフィールドは「カタログ 192 件に対する 2 枚目のマスク」であり、
  +0x4C が「導入済み」、こちらが別の状態（配信/受信/閲覧など）を持つことになる。
* （推測）ゼロがワード 1 とワード 3 上位・ワード 4/5 に集中する形は、カテゴリ単位の区切りと整合する。
* （推測）3 キャラ・バックアップで完全一致し、クエスト導入で変化しない（ユーザ観測）ことから、
  **ゲームが頻繁に書き換えない値**（レガシー/引き継ぎ情報、あるいは配信パック側の状態）である可能性が高い。
* いずれも**仮説であり、本レポートの事実ではない**。

## 6. まだ分からないこと

1. 索引空間の正体（何の 128/192 件か）と順序。本セーブ 1 本からは復元できない。
2. 47–54・59–63 のゼロの理由。
3. `+0x10` = 15、`+0x1C` = 26、`+0x20` = 31 の意味（ヘッダ内の小さい u32 3 個）。
4. `+0x00` = 31232（0x7A00）、`+0x68` = 16778（0x418A）の意味。CRC/総和では説明できなかった。
5. `+0x24` から始まる 32 バイト帯のうち、前半 16 バイト（+0x24..+0x33）の意味。

## 7. 次に試すべきこと（反証可能な形で）

いずれも「一致件数」ではなく**変化するか否か**で判定できる設計にしてある。

1. **差分実験（最優先）**: ゲーム内（Ryujinx）で配信クエストを 1 件削除 → セーブ → `+0x34` を比較。
   * 変化なし → 「導入状態ではない」が確定（ユーザ観測 166→175 の逆方向の確認になる）。
   * 変化あり → 変化したビット位置と、削除したクエストのカタログ位置を突き合わせる（順序が直接判明する）。
2. **別セーブとの比較**: 新規キャラ作成直後のセーブ、または別プレイヤーのセーブで `+0x34` を実測。
   * 全セーブで同一 → 定数（ゲームが書かない領域）→ ツールは触らないのが正しい。
   * セーブごとに違う → 何かに相関。クエスト数・アイテムボックス・プレイ時間との相関を機械的に調べる。
3. **MHX(3DS) セーブとの比較**: MHX の `section+0x34` は 20 バイト・140 ビットで、チャレンジがビット 0..19、
   イベントがビット 32 以降というレイアウト（`docs/review_quest_injection.md` の参照実装 `quest.c`）。
   MHXX の `+0x34` が MHX 形式の名残ならビット 20..31 は 0 になるはずで、**実測は 12/12 すべて 1 なので否定済み**（§3 D）。
   ただし MHXX 側のカタログで同じレイアウトを組む（チャレンジを 32 ビット境界に置く等）変種は未検証。
4. **コード側からの裏取り**: `crates/mhnx-nro`/`docs/mp_ghidra.md` の知見を使い、
   ゲーム本体がセクション +0x34 をロード/ストアする箇所を探す（読み出し元が分かれば索引空間が分かる）。
5. **ペイロード特性との相関**: サイズは無相関と判明（§3 I）。次は `.arc` エントリ構成
   （`mib`/`gmd`/`sup`/`rem`/`qdl`/`esl` の有無）、「1人限定」フラグ、`questLink` の有無などで
   112 件が説明できるか。説明できなければ「カタログ 2 枚目マスク」説も落ちる。
6. **+0x10/+0x1C/+0x20 (15/26/31) の特定**: セクション内の他ブロック
   （配信アイテムセット 6 件 + 名前/挨拶レコード群）の件数と照合する。ここが説明できればヘッダ全体の意味が変わる。

## 8. 実装への影響（現状のツールの扱いは妥当）

* 本調査でも **`+0x34` に書き込む根拠は得られなかった**。`dlc.rs` がこの領域を一切書かない方針は維持すべき。
* 「既存クエストの差し替えはビットを変えないので安全」という既存の結論も、§2（+0x4C の検証）と矛盾しない。
* 追加で注意すべき点: セクション先頭 0x00–0x68 のヘッダには、クエスト以外の
  配信アイテムセット（`+0xAF8`〜）や名前レコード群（`+0x1D98`〜）も同居している。
  セクション全体をコピーする操作（DLC の丸ごと移植など）では、これらも一緒に移動することになる。
