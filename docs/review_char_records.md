## 0. 最重要: オフセットの基準（絶対か相対か）

**結論: 本レポートの「slot+XXXX」はすべて「スロット基点からの相対」。ファイル絶対値ではない。**

```
file   = [0x00..0x23] 36 B ヘッダ（CRC 等） + [0x24..] 本体 body（4,726,152 B）
body   = file[36:]                                   ← C# も Skip(36) している
slot_base(body 内絶対) = u32 LE @ body+0x10 / +0x14 / +0x18
        実測 0x126474 / 0x244C34 / 0x3633F4      stride 0x11E7C0
file 絶対 = 36 + slot_base + slot相対
```
- C# の `player.SaveOffset + Offsets.XXX` はまさに「slot_base + 相対」で、**本レポートの値と同一の意味**。
- 例（slot 0）: ギルドカード先頭 = body `0x126474+0xC71BD = 0x1ED631` = **file 絶対 0x1ED655**。
- 例（slot 0）: 闘技大会ログ = body `0x1EE855` = **file 絶対 0x1EE879**。
- 例（slot 0）: オトモブロック = body `0x14A02A` = **file 絶対 0x14A04E**。
- 例（slot 0）: セット配列 = body `0x127C43` = **file 絶対 0x127C67**。

> 既存の `docs\review_save_layout.md` も「body+0x…」で書かれているので、本レポートの数値と直接比較できる。ファイル先頭からの値と混同しないこと。

### 1.3 整合性チェック（「実測とセットで断定」の根拠）

1. **外見ブロックの完全ミラー**: `GC+0x019..0x047`（47 B）と `slot+0x23B48..0x23B76`（47 B）が **3 スロットすべてでバイト完全一致**。
   - ミラー関係: `GC = slot + 0x23B48 − 0x019 = slot + 0x23B2F`。
   - 検算: 0x23B53−0x23B2F = 0x24（カラー#1）✓、0x23B67−0x23B2F = 0x38（肌カラー）✓、0x23B7D−0x23B2F = 0x4E（名前は GC 側では +0x00 に別置き）。
2. **プレイ時間は 2 箇所で微妙にズレる**:
   - キャラ側 `slot+0x2248B` = 2,409,628 s / 2,363,516 s（既存資料の値と一致）
   - カード側 `GC+0x914` = 2,409,621 s / 2,363,483 s
   - 差は slot0 が 7 秒、slot1/2 が 33 秒 → **カード側は「最後にカードを更新した時点のスナップショット」**（推測。ただし常に「カード≦本体」であることと整合）。書き込み時は両方そろえる必要がある。
3. **HR も 2 箇所**: キャラ `slot+0x28` と `GC+0x16` が一致（967/999）。カード側だけ書き換えると不整合になる。

### 1.5 推測（明示）

- **推測**: `+0x024..+0x037` の 5 色は「防具 5 部位（頭/胴/腕/腰/脚）のカラー」。根拠は (a) 直後に個人カラー 4 種が並ぶ、(b) キャラ側 `0x23B53..0x23B66` と同一、(c) 5 という個数が防具部位数と一致。**部位との対応順は未検証**。
- **推測**: `+0x018` は「カードに表示する武器種」。値 7/4/1 は、0 始まりの 15 要素配列なら SwitchAxe/HBG/SnS、装備ボックスの型コード（7=大剣）なら大剣/腰/… となり**決め手に欠ける**。要 A/B 実験。
- **推測**: `+0x00C..0x015` はカード固有 ID／ハッシュ。slot ごとに異なるが役割不明。
- **断定**: C# の `SIZEOF_GUILDCARD=4986` は「たぶん」とコメントされているが、**闘技大会ログ末尾と一致することで 4986 が正しいことを実測で確認**した。

### 2.3 探索した方法と結果

1. **ビットフィールド走査**: slot0 の 1,173,440 B 全体から「8 バイト以上連続で 7 ビット以上立つ」区間を抽出 → 249 件。大半はアイテムボックス／装備ボックスのフラグで、**13 B（104 bit）の勲章らしき独立フィールドは特定できず**。
2. **13 B 窓のポップカウント走査**: 全オフセットで 13 B のポップカウント ≥ 90 を探索 → ヒットは `+0x2C75` 以降の 1 箇所のみ（`ff` 連続）。そこは**アイテムセット配列の後ろの未使用ギャップ**で、勲章として意味づける根拠が無い。
3. **ギルドカード内の非 0 領域**はすべて §1.4 で内容を説明でき、称号/勲章と思われるビット配列は見つからなかった。
4. `refs\SJ-site\MHGU\save-manager\scripts\main.js` は**スロット名/性別/HR/所持金/プレイ時間/シャウトのみ**で、ギルドカード・称号・勲章は扱っていない（grep 済み）。`refs\mhx_data_manager` は空。

### 2.4 残る候補領域（申し送り）

- **ギルドカードの §1.4 未確定領域**（`+0x920..+0x1223` の 2,304 B、`+0x080..+0x193` の 0x2C 配列）: ギルドカードは称号・勲章を**表示する**画面なので、ここが最有力。
- **slot+0x2A606 .. slot+0xC71BD の約 642 KB**: 密度マップ（`tools/_cr11.py`）で 0x071000〜0x0B4000 に中密度の塊が多数。
- **決定打**: ゲーム内で「称号を 1 つ解放」「勲章を 1 つ取得」して保存 → 差分。**本レビューではゲームを起動できない**ためここで止めている（本項目唯一の限界）。

### 3.2 タイム（u16 LE @ +0）は **1/100 秒（センチ秒）**

### 3.4 未確定: `+2` のパック u16（グレード＋武器種）

**断定できること（実測）**
- `+2` の u16 は空スロットでも非 0（0x6380 / 0x6140）で、**アリーナ種別（武器／オトモ）で既定値が変わる**。
- XOR を取ると両既定値の差は **bit9, bit7, bit6** の 3 ビット。bit9 は記録済みの武器アリーナ全件で 1、オトモ全件で 0。
- **参照実装の解釈は破綻している（断定）**: C# は「バイト +3 を上位、+2 を下位にした u16」の上位 3 bit をグレード、bit5..2 を武器種とするが、**実在する記録 16 件のうち 8 件でグレードが `011` = “-----”（未記録扱い）になる**。タイムが入っているのに未記録表示になるので、ビット配置が誤り。

**未確定**: 正しいビット配置は 1 セーブからは決定できない（可変要素が少なすぎる）。確定には「ゲーム内で 1 回クリアして S/A/B と武器種を変え、前後差分を取る」以外に確実な方法が無い。実測生値（`+2` の u16 LE）を次担当者向けに残す:

（観察メモ: bit8 は全件 1。上位 4 bit はタイムと弱く相関するが arena10 の 1 件が外れる。12 bit を小数部とする固定小数点として読むと 2.2〜7.2 に収まる、という別仮説もある＝いずれも**推測**。）

### 4.4 オトモで疑うべき 2 点

1. **装備中スキル `+0x030` が 17 体すべて 0**。装備中サポート技 `+0x028` は非 0 なので「スキルだけ別位置」の可能性が高い。

   - **本レビューでは確定できず**。ゲーム内でスキルを付け替えて差分を取るのが最短。
2. **レベル `+0x024` の +1 の有無**。C# は `+0x24 + 1` を表示するが、実測に `+0x24 = 73 / 99` のオトモが存在し、99 が上限（`#37`）と考えると **`+0x24` がそのままレベル**。C# の +1 は MHX 時代の名残の可能性。断定にはゲーム内表示との突き合わせが要る。

## 5. マイセット

### 5.1 発見: **slot+0x17CF に 170 B × 24 のセット配列**（確定）

| 項目 | 値 | 根拠（実測） |
|---|---|---|
| 基点 | **slot+0x17CF** | アイテムボックス終端 `0x278+5,463 = 0x17CF` の直後から UTF-8 のセット名が現れる |

| 枠数 | **24**（0x17CF + 24×170 = 0x27BF で終了、以降は別構造） | 実測。0..23 は名前が意味の通る文字列、24 以降は UTF-8 として壊れる |
| 名前 | **+0x000、UTF-8、NUL 終端（〜20 B 程度）** | `“剣士(汎用)”` `“－－－”`×多数 `“炭鉱”` を実測 |
| 中身 | **+0x02A から u16 LE ×32**（64 B）。以降 0 | record0 = `9,10,10,10,28,2,29,1,31,3,32,2,40,1,41,1,42,1,56,20,70,99,71,5,73,8,83,1,84,1,303,10` |

→ プレイヤーは実際に 2 セット作っている（#0 と #7）。**未使用でも名前は `－－－` が入る**（全 0 ではない）ので、「全 0 なら別位置」の判定に使える。

### 5.2 未確定

- **装備セットかアイテムセットか**。材料が割れている:
  - アイテムセット寄り: 中身が 32 個の u16 で、`(id, 数)` のペアとして読むと `(9,10)(10,10)(28,2)(29,1)(31,3)(32,2)(40,1)(41,1)(42,1)(56,20)(70,99)(71,5)(73,8)(83,1)(84,1)(303,10)` という「アイテム＋個数」に見える形になる。

- **装備セット（マイセット）本体**、**マイハウス関連**は未発見。§2.4 の候補領域に含まれる可能性が高い。

## 7. 実装提案（本ツール `mhnx.exe` への追加）

### 7.1 すぐ実装できるもの（実測で裏が取れている）

1. **`guildcard` サブコマンド（読み取り）** — slot+0xC71BD から以下を出力:
   名前(+0x00 UTF-16 12B) / HR(+0x16) / 外見 8 値(+0x19..0x20) / カラー 9 色(+0x24..0x47) /
   クエスト数 7 種(+0x85E) / カード ID(+0x8B0) / 武器使用数 3×15(+0x8BA,+0x8D8,+0x8F6) /
   プレイ時間(+0x914) / コメント(+0x878 UTF-16 56B)。
   - **書き込み時は必ず「キャラ本体側」も同時更新**: HR(`slot+0x28`)、外見(`slot+0x23B48..0x23B76`)、プレイ時間(`slot+0x2248B`)。カード側だけ変えると不整合になる（§1.3）。
2. **`arena` サブコマンド** — slot+0xC83E1 から 17×5 の `(センチ秒, packed)` を読み、タイムは **`/100` して `M:SS.cc` 形式**で表示。空判定は `time==0`。グレード/武器種は**未対応として「?」表示**にするのが誠実（誤ったグレードを出すより良い）。
3. **`palicoes --detail`** — 既に `palicoes` があるなら、`+0x28`(技8) `+0x38`(技16) `+0x48`(スキル12) `+0x100`(装備3) `+0x11A`(色4) `+0x60`(あいさつ) `+0x24`(Lv) `+0x26`(なつき) を追加。
4. **`sets` サブコマンド** — slot+0x17CF を 24 枠 × 170 B で列挙し、名前（+0x00 UTF-8）と `+0x2A` の u16×32 を表示。名前が `－－－` の枠は「未使用」ではなく「名前未設定の有効枠」として区別する。

### 7.2 実装しないほうがよいもの（現時点）

- **称号・勲章の編集**: 位置が未確定なので、誤ったオフセットに書くと**セット配列（0x17CF〜0x27BF）を破壊する**。C# の `0x1B8A` をそのまま使うと、まさにその事故になる（§2.2 で実証）。確定まで保留すべき。
- **闘技大会のグレード書き込み**: `+2` のビット配置が不明なため、タイムと矛盾する値を書く危険がある。読み取りのみ推奨。

### 7.3 検証用テストの提案

既存 `crates/mhnx-core/tests/` の流儀に合わせて:
- ギルドカード: `GC+0x19..0x47 == slot+0x23B48..0x23B76`（3 スロット）を恒等式として assert。
- ギルドカード: クエスト数 7 種と武器使用数 3×15 が「非 0 を含む」ことを assert（全 0 検出＝オフセットずれの検出器になる）。
- 闘技大会: 各アリーナ内の `time` が**非減少**であることを assert（順位順の不変条件。基点ずれを検出できる）。
- オトモ: 使用枠の名前が UTF-8 として妥当、`+0x11A` の α が 0xFF、`+0x28` の先頭 2 つが 0 でない、を assert。
- セット: 24 枠の各 +0x00 が「空でない UTF-8」であることを assert（`－－－` が既定）。
