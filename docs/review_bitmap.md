# 導入済みマスク（DLC+0x4C）の並び順 — 規則を特定した

担当: マスク並び順調査 / 作業ディレクトリ `C:\anyWorkspace\nx\mhxx\mhnxeditor`
対象セーブ: `C:\Users\haruk\AppData\Roaming\Ryujinx\bis\user\save\0000000000000001\0\system`（読み取りのみ、一切書き込んでいない）
解析スクリプトは `%TEMP%\mhxx_bit\` に置いた（リポジトリ内のファイルは本書以外変更していない）。

## 0. 結論

**ビット 45 以降は「別の並び」ではない。マスクは 2 つの独立したビットフィールドの連結で、
境界はビット 64。ビット 45..63 はパディング（実測 19 ビットすべて 0）。**

| 領域 | ビット | 枠数 | 索引の意味 |
|---|---|---|---|
| 装備クエスト（チャレンジ） | 0..44 | 45 | **ゲーム内 DLC カタログの位置 0..44 そのもの** |
| パディング | 45..63 | 19 | 未使用（実測すべて 0） |
| イベントクエスト | 64..223 | 160 | **カタログ位置 45..204 → bit = 64 + (位置 − 45)** |

規則（1 行で書くと）:

```
カタログ位置 p に対応するマスクのビット = p              (0 <= p < 45)
                                     = 64 + (p - 45)    (45 <= p <= 204)
```

カタログはセーブではなく **ゲーム本体の実行ファイル内**にある。
`out_update/image/main.bin` と `out_base/image/main.bin`（両者この領域はバイト一致）の
**イメージオフセット 0x1589D70**（update）/ **0x15E094C**（base）から
u32 ペア 205 組 = 1640 バイト:

```
(id u32, nameidx u32) x 205
  1020001,577 / 1020002,578 / ... / 1120012,617 / 1020001,618 / ...
  1010001,637 / 1010002,638 / ... / 1111009,796
```

この 205 組がカタログそのもの。先頭 45 組が装備クエスト（うち位置 41..44 の 4 組は
ID が 1020001 の重複＝プレースホルダ）、残り 160 組がイベントクエスト。

### 決定的な検証結果（実測）

| 検証 | 結果 |
|---|---|
| 装備カタログ 41 件（位置 0..40）で「ビットが立つ ⟺ その ID がセーブに入っている」 | **41/41 一致** |
| イベントカタログ 160 件（位置 45..204）で同上 | **160/160 一致** |
| 実在するカタログ項目の合計 | **201/201 一致（例外 0）** |
| プレースホルダ 4 件（位置 41..44） | 4/4 ビットが 0 |

偶然では起こらない。イベント領域だけを見ても、135 ビットが立つ 160 枠のうち
**どの 25 枠が 0 か**が完全に一致しており、無作為なら確率 1/C(160,25) = 1.1 × 10⁻²⁹。
装備側も独立に 41/41。両方を合わせて偶然一致する見込みはない。

### 副産物: マスクの「穴」の意味が確定した

ビットが 0 の位置 = 「カタログに存在するが未導入の項目」。このセーブでは次の 30 件。

- 装備 1 件: 1020020（カタログ位置 25 = ビット 25。装備枠 25 が空なのと一致）
- イベント 25 件（ビット **65, 83, 84, 93, 99, 103, 106, 127, 129, 140, 147, 150,
  155, 174, 198, 207, 215〜223** の 25 個）:
  1010002, 1010116, 1010117, 1010126, 1010132, 1010136, 1010139, 1010160, 1010162,
  1110006, 1110107, 1110110, 1010169, 1011014, 1011038, 1110113, 1010006, 1010176,
  1011045, 1011046, 1011047, 1110008, 1110113, 1111008, 1111009

（1110113 はカタログに 2 回出てくる。位置 188 と 202。ゲーム側テーブルの重複で、
 どちらをゲームが使うかはこのセーブからは決められない。両方ビット 0。）

## 1. 実測したマスクの構造（数値）

```
mask (28 B) = ff ff ff ff fd ff 01 00 00 fd ff e7 df 77 fb ff
              7f fd ef b7 f7 ff bf ff ff bf 7f 7f 00
```

u32 x 7（リトルエンディアン）と popcount:

| word | 範囲 | 値 | popcount |
|---|---|---|---|
| 0 | 0..31 | 0xfdffffff | 31（bit 25 のみ 0） |
| 1 | 32..63 | 0x000001ff | 9（bit 32..40 のみ） |
| 2 | 64..95 | 0xdfe7fffd | 28 |
| 3 | 96..127 | 0x7ffffb77 | 28 |
| 4 | 128..159 | 0xf7b7effd | 27 |
| 5 | 160..191 | 0xffffbfff | 31 |
| 6 | 192..223 | 0x007f7fbf | 21 |
| | | 合計 | **175** |

- 立っているビット総数 175 = 導入済みレコード数 175
- ビット 0..44 の立っている数 40 = 装備枠の中身がある数 40
- ビット 64..223 の立っている数 135 = 装備を持たない（＝イベント）クエスト数 135
- ビット 45..63 は **19 ビットすべて 0**

### パディングの理由（推測）

MHX 版のリファレンス実装 `refs/mhx_data_manager/source/quest.c` は
`get_bits()` で「チャレンジクエスト 20 件を word 0、イベント 120 件を word 1..4」に置く。
つまり **装備側は u32 語数に切り上げ、イベント側はその次の語から始まる**設計。
MHXX は装備 45 件 → 2 語（64 bit）必要 → イベントは word 2 = ビット 64 から。
実測のパディング 19 = 64 − 45 と一致する。この「なぜ」は推測だが、規則自体は実測。

### 205 という数字の一致（もう 1 つの傍証）

カタログ項目数 205 = クエスト枠数 205。MHX も カタログ 20+120=140 = 枠 140
（`quest.c` のループが `i < 140`）。両ゲームでこの 2 数が一致する。

## 2. 独立証拠: 装備枠 45 個がカタログ位置そのもの

`DLC+0x1049F4` の 45 枠（1 枠 0x800 バイト）は、**空き枠も含めてカタログ位置に一致**する。

| 項目 | 実測 |
|---|---|
| 中身のある 40 枠の先頭 u32 が カタログ位置 k の ID と一致 | **40/40** |
| 空き枠 | 25, 41, 42, 43, 44 |
| カタログ位置 25 の ID | 1020020（＝セーブ未導入、ビット 25 が 0） |
| カタログ位置 41..44 の ID | 1020001 x4（プレースホルダ、ビット 41..44 が 0） |

つまり装備枠は「カタログ位置をそのまま添字にした疎な配列」。
これはマスクのビット割り当てがカタログ索引であることを、マスクとは独立に裏づける。

## 3. 否定した仮説（実測値つき）

判定に使った基準: ある仮説がクエスト q に予測ビット b(q) を与えるとき、
「ビットが立っている」件数だけで評価すると**偶然水準との区別がつかない**（下の偶然水準列）。
そこで (a) 偶然水準（無作為配置の期待一致数）、(b) **位置の整合性**（穴を挿入できるかの構造判定）
の両方で見た。

| 仮説 | 実測一致 | 偶然水準 | 構造判定 | 結論 |
|---|---|---|---|---|
| **カタログ位置（本書の答え）** | **201/201** | 157 | 穴 30 個がすべてカタログの未導入項目と一致 | **採用** |
| ビット = ID 昇順の順位 + 64 | 120/135 | 113.9 | 穴を入れられない箇所が **12/134**（例: 1010114 と 1010115 の間に未知 ID が必要 = 整数が存在しない） | 否定 |
| ビット = スロット順の順位 + 64 | 120/135 | 113.9 | イベント 135 件は**スロット 0..134 に隙間なく**入っている。穴は 16 個あるので挿入不能 | 否定 |
| MHX カタログ 120 件 + MHXX 追加を末尾に | — | — | カタログは 160 枠。MHX 表に無い ID が 56 件あり 120+56=176 > 160 | 否定 |
| MHX カタログの順序を保存 | 90/104 が位置一致 | — | 位置と MHX 索引の**逆転が 19/5356 組**。最初のズレは 1010168（カタログ 134 vs MHX 索引 92） | 否定（ほぼ同じだが別物） |
| ビット = カタログ位置（+19 なし） | 106/135 | 101.8 | 境界がずれる | 否定（+0.8σ） |
| ビット = nameidx − 577 | 117/135 | 113.9 | 装備側しか合わない（イベント側は +19 ずれる） | 否定（+0.7σ） |
| ビット = 64 + (id − 1010001) | 46/57 | 48.1 | 範囲外になる | 否定（水準より悪い） |

「偶然水準」= 一致数の期待値（イベント領域なら 135 枠中 135 ビットで 113.9、
全マスクなら 224 枠中 175 ビットで 201 × 175/224 = 157.0）。

### 既に否定済みの 2 仮説は「偶然水準そのもの」だった（再確認）

指示どおり再検証はしないが、数値の意味だけ補足する。

| 既存の測定 | 偶然水準 | 解釈 |
|---|---|---|
| ビット i = スロット i → 140/175 | 175 × 175/224 = **136.7** | 偶然水準 +0.3σ。**信号なし** |
| ビット (i+45) = スロット i → 111/175 | 同上 136.7 | **水準以下** |
| 枠 45 以降で 100/130 | 130 × 135/179 = **98.0** | 偶然水準 +0.4σ。**信号なし** |

この 3 つは「惜しい」のではなく、最初から**何も示していなかった**。

### 「件数が一致する」罠の再確認

| 一致してしまう数 | 実体 |
|---|---|
| 175 ビット = 175 レコード | 1 ビット = 1 クエストという設計の結果。順序の情報はない |
| 135 ビット = イベント 135 件 | 上と同義 |
| 112 ビット（+0x34） = 101xxxx 112 件 | 無関係（既存文書で否定済み） |

## 4. まだ分からないこと

1. **プレースホルダ 4 件（位置 41..44）の意味**。ID はすべて 1020001、nameidx は 618..621。
   このセーブではビットが 0。「予約で永久に 0」なのか「たまたま未導入」なのかは
   1 個のセーブでは区別できない。別セーブでビット 41..44 が立つかを見る必要がある。
2. **nameidx 列（577..621, 637..796）の意味**。ゲーム内の別テーブル（クエスト名？）の索引らしいが、
   指し先は特定していない。622..636 の 16 個だけが飛んでいる理由も不明。
3. **1110113 の重複**（位置 188 と 202）。ゲーム側テーブルの不整合。どちらが有効か不明。
4. **+0x34（24 B, 112 ビット）** の意味は依然不明（本件とは独立）。
5. **書き込み側の未検証**。ビットを立てればゲームが認識するかは実機/エミュレータでの確認が要る。

## 5. 次に試すべきこと

1. **`dlc.rs` の「カタログが無いので追加インストール不可」という前提を撤回できる。**
   上の 205 組をコードに埋め込めば `quest_id -> catalogue position -> bit` が引ける。
   これで空きスロットへの新規追加が実装可能になる（ビットを書ける）。
   ただしビット書き込みの効果は未検証なので、まずは「既にビットが立っているクエストの
   差し替え」のままにし、追加は試験フラグ付きで。
2. **予測の実機検証**: 未導入 25 件（例 1010002 → ビット 65、1010006 → ビット 215）を
   1 件だけ入れて、ゲームの一覧に出るか確認する。出れば規則は完全に確定。
   ビット予測は付録の表に全件載せてある。
3. **装備枠 25 を 1020020 で埋める**試験。ビット 25 を立てる予測。
4. **別セーブでのプレースホルダ確認**（ビット 41..44 が立つことがあるか）。
5. **nameidx の解決**。これが分かると未導入クエストの名前も引ける。
6. `docs/dlc_layout.md` の「カタログの並び順は復元不可」という記述は本書の結果で
   古くなっている（親エージェント側で更新するか判断してほしい）。
