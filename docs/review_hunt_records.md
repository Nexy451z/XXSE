## 1. 位置の基準：ファイルオフセットと body オフセット

このセーブは 36 B の Switch コンテナヘッダを持つ。**ヘッダを除いた本体を基準にしたオフセット**（以下 body オフセット）で表すのが正しい。実測:

| ヘッダ項目 | 実測値 | 判定 |
|---|---|---|
| +0x14（名前 CRC） | `0x36B2EE74` = crc32("system") XOR 0xFFFFFFFF | 【実測一致】 |
| +0x1C（本体長） | `0x00481D88` = 4,726,152 = 実ファイル長 − 36 | 【実測一致】 |
| body +0x00 | `0xC6`（本体マーカー） | 【実測】 |
| body +0x04..0x06 | 1,1,1（3 スロットすべて使用中） | 【実測】 |
| body +0x10/+0x14/+0x18 | `74 64 12 00` / `34 4C 24 00` / `F4 33 36 00` → 0x126474 / 0x244C34 / 0x3633F4 | 【実測】 |

したがって **ファイル実オフセット = body オフセット + 36**。本レポートの表はすべて「スロット基点からのオフセット」（= body オフセットの差分）で書く。

### 2.1 仕様

### 2.2 「本当に値が入っているか」の検証【実測】

1. **全件 0 ではない**：137 件中 129 件が非ゼロ、合計 8,236、最小 1 / 最大 893。
2. **型違いの排除（u8 / u32 ではない）**
   - 255 を超える値が **8 件**ある：Brachydios 589、Vespoid 453、Melynx 257、Ioprey 893、Bullfango 256、Bnahabra 405、Altaroth 289、Jaggi 433。
     例: id 52 の実バイトは body `0x12C37A` に `4D 02` = 0x024D = 589。
     → **u8 では表現できない**ので、少なくとも 16 bit。
   - u32 説も否定できる。id 0/1 の実バイトは `18 00 0B 00`（= 24, 11）。u32 と読むと 0x000B0018 = 720,920 という意味不明な値になり、しかも隣の id 1 が消える。274 B / 137 = 2 B で割り切れることも u16 を支持する。
3. **隣接テーブルとの整合**：捕獲数テーブルは「捕獲 > 0 なのに討伐 = 0」の項目が **0 件**（正しいアライメントの場合）。2 B ずらすと 1 件発生する。
4. **意味的な整合**：小型モンスター（71–104 ほか）は討伐数が入り、捕獲数は**全件 0**（小型は捕獲できない）。大型のみ捕獲 > 0。これはテーブルの並びが正しいことの傍証。
5. **プレイ時間との整合**：669 時間で 8,236 討伐 = 12.3 体/時。桁として不自然ではない。

### 2.3 捕獲数テーブル（+0x5FB8）

- u16 LE × 137。非ゼロ 47 件、合計 730、最大 598（id 52 Brachydios）。
- **討伐数は捕獲を含まない**：id 52 は討伐 589 < 捕獲 598。もし「討伐数 = 討伐＋捕獲」なら捕獲 ≤ 討伐 が必ず成り立つので、この 1 件でその説は否定される【実測】。
- 小型モンスター 37 体は捕獲 0【実測】。

## 3. 狩猟サイズ記録（最小／最大／王冠）

### 3.1 形式

- 1 体 **4 B** = `+0` 最小 u16 LE、`+2` 最大 u16 LE。137 体で 548 B。
- 参照実装も同じ読み方（`Forms\EditGuildCardDialog.cs:147-148`。スピナーのラベルも "Largest Size (%)" / "Smallest Size (%)"（`Designer.cs:564, 586`））。

### 3.2 アライメントの証明【実測】

| 読み出し開始 | 解釈できる組 | 最小 ≤ 最大 | 判定 |
|---|---|---|---|
| 0x60CA − 4（1 レコード手前） | 78 | 78/78 | 順序は保たれるが、別モンスターに割り当たる。単独では排除できない |
| 0x60CA − 1（バイトずらし） | 78 | 78/78 | 上位バイトが全て 0 のため偶然成立。値は 256 倍で無意味 |
| **0x60CA（基準）** | **78** | **78/78** | **採用**（137 件すべて矛盾なし） |
| 0x60CA + 1（バイトずらし） | 91 | 13/91 | 78 組が破綻 → ここは値の切れ目ではない |
| 0x60CA + 2（バイトずらし） | 91 | 13/91 | 同上 |
| 0x60CA + 3（バイトずらし） | 78 | 77/78 | 137 件目が装備レコードを巻き込み破綻（id 136） |
| 0x60CA + 4（1 レコード後） | 78 | 77/78 | 同上 → 137 件を超える位置はあり得ない |

> 判別の決め手は **+1/+2 B の破綻（13/91）** と **+3/+4 B の 137 件目破綻**。−1/−4 は順序テストだけでは排除できないが、終端が装備ボックス先頭（0x62EE、独立検証済み）で 137 件 × 4 B ちょうどになることから決まる。

- **137 件であることの証明**：138 件目を仮定すると、その 4 B は装備ボックスの先頭レコード `47 01 1A 00`（id 327, level 26）を読み、「最小 0x0147=327 > 最大 0x001A=26」という矛盾になる。よって 137 件で確定。
- **末尾の境界**：0x60CA + 548 = **0x62EE** = 装備ボックス先頭。装備ボックスを 2000 件 × 36 B で読むと、空 1,211 件・非空 789 件、非空の ID はすべて 1..466 に収まり、さらに 0x62EE + 72,000 = **0x17C2E** = パルコ装備ボックス先頭（72 件、ID 22 など）と連続する【実測】。→ モンスター 3 テーブルの終端が 0x62EE であることは独立に裏付けられる。

### 3.3 単位は「1 = 1%」と推定【推測】

- 実測レンジ：最小 **25–103**（中央値 93）、最大 **108–160**（中央値 121.5）。100 を中心に上下へ広がる形で、MH のサイズ変動（最小冠〜最大冠）と一致する。
- 絶対値説（cm/10 等）は破綻する：Bulldrome の最大 150 が Rathian の 120 より大きいのは「%」なら自然だが、実寸なら Bulldrome（小型の体躯）が Rathian より大きいことになり不自然。
- 参照実装の UI ラベルも "%"（`EditGuildCardDialog.Designer.cs:564, 586`）。
- **ただし**「100 = 基準サイズ」の定義がゲーム内でどう表示されるかは実機でしか確認できない（§11-1）。

### 3.4 サイズ記録が 0 のモンスター（59 体）【実測】

| 群 | 体数 | id | 討伐計 | 解釈 |
|---|---|---|---|---|
| 小型モンスター | 37 | 71, 72, 73, 74, 75, 76, 77, 78, 79, 80, 81, 82, 83, 84, 85, 86, 87, 88, 89, 90, 91, 92, 93, 94, 95, 96, 97, 98, 99, 100, 101, 102, 103, 104, 134, 135, 136 | 6238 | 捕獲・サイズの対象外【実測】 |

| プレースホルダ（参照実装 "Unknown"） | 8 | 105, 106, 107, 108, 109, 110, 111, 133 | 21 | 正体不明。id 106 のみ討伐 21【実測】 |
| **合計** | **59** | — | **6342** | 137 − 59 = 78 体にサイズ記録あり |

- 小型モンスター 37 体は常に 0。
- 古龍・特殊個体など 14 体（Akantor / Ukanlos / Alatreon / Amatsu / Nakarkos / Lao-Shan Lung / Fatalis 系 3 / Furious Rajang / Savage Deviljho / Raging Brachydios / Chaotic Gore Magala / Frostpeak Gammoth）も 0。
  → **サイズ記録は「サイズ変動のある大型モンスター」だけに書かれる**と解釈できる【推測】。参照実装の `IgnoreList`（55 件）はこの集合の近似だが、**Fatalis / Crimson Fatalis / White Fatalis が IgnoreList に無いのに実セーブでは 0** という食い違いがある（§7.1）。

### 3.5 王冠（金冠／銀冠）

- このテーブルに**フラグの余地が無い**（1 体 4 B ちょうど、2 つの u16 で埋まる）。
- スロット全体（1,171,648 B）を走査し、「サイズ記録あり」の 137 bit パターンに一致するビットマップが存在しないことを確認【実測】。
- → **王冠は保存されておらず、サイズ値とモンスター別しきい値から実行時導出**【推測】。実機での確認が必要（§11-2）。

## 4. 並び順（ID 順か）

1. 参照実装の英語名リスト `MonsterHuntNames` は **137 件**、Rust 側 `gamedata.rs:561 MONSTER_HUNT_NAMES` と完全一致【実測】。
2. クエスト側の日本語モンスター列挙 `questfields.rs:161 ENUM_ICN_`（188 件、0 番は「なし」）と突き合わせると、**hunt index i ↔ ENUM_ICN_[i+1] が 0..104 の 105 件で一致**（辞書照合 44 件は自動検証、残りは目視）。例: 0=リオレイア、5=黒炎王リオレウス、21=ラージャン、52=ブラキディオス、71=アプトノス、104=ムーファ。
   → **先頭 105 件はゲーム内モンスター番号順**であることが実データで裏付けられた。
3. **105–111 は参照実装では "Unknown"**。奇しくも日本語列挙の 106–112 は「環境不安定／クロスマーク／アイルー顔／卵／鉱石／魚／骨」という**非モンスターのアイコン 7 件**で、個数が一致する。プレースホルダ枠と推定するが、**id 106 だけ討伐 21 が入っている**説明がつかない（§11-4）。
4. **112 以降は未検証**。日本語列挙では 120 がバサルモスで、参照実装の並び（112 = Basarios）とは 8 件ずれる。列挙側はアイコン列挙で Fatalis 系を持たないため、そのままでは比較できない。名前の対応は 112 以降「未確定」として扱うのが安全。

### 7.1 参照実装の注意点（実測に基づく指摘）

1. **符号付き読み取り**：`BitConverter.ToInt16` で討伐／捕獲を読んでいる（`EditGuildCardDialog.cs:136-137`）。32,768 以上で負値になり、そのまま書き戻すと `GetBytes((int)-1)` = `FF FF FF FF` の下位 2 B が入って 65535 に化ける。本セーブの最大は 893 なので実害は無いが潜在バグ。
2. **IgnoreList の不一致**：Fatalis / Crimson Fatalis / White Fatalis は IgnoreList に無いのに実セーブではサイズ 0（§3.4）。UI 上は編集できてしまう。
3. **全件書き戻し**：1 体だけ編集しても 137 体ぶんを丸ごと書き戻す。表示していない値も含めて上書きするので、外部で書き換えた直後にこのエディタで保存すると巻き戻る。
4. **3 スロット独立**：テーブルはスロットごとに存在する（§6）。UI は選択中スロットのみ扱う。

  - `mhnx hunts <file> [slot] --json`（親ツールが機械可読に食えるように）

## 9. 値の上限（型）の推定

| 項目 | フィールド型 | 実測レンジ | ゲーム内上限 |
|---|---|---|---|
| 討伐数 | **u16**（構造から確定。255 超の実値 8 件） | 1–893 | **未確定**（9999 か 65535） |
| 捕獲数 | **u16**（同上。最大 598） | 1–598 | **未確定** |
| 最小／最大サイズ | **u16** 各（"%" 前提なら実用上 0–999 程度） | 25–160 | **未確定**（理論値 65535） |

- 参照実装は 4 つとも **65535** を許す（Designer の Maximum）。「9999」を支持する直接証拠は無い。
- 傍証：このセーブの討伐テーブル直前に `0x270F`(=9999) が 18 個、`0x63`(=99) が 15 個並ぶ領域がある（body 0x5E5E–0x5EA5）。ただしこれは**別の構造**（おそらく上限値で埋められた別カウンタ）で、討伐数テーブルとは無関係。**上限の根拠には使えない**。
- 推定としては「u16 なので理論上限 65,535。ただし表示・内部計算が 9999 で飽和する可能性あり」とし、**書き込みは 9999 以下を推奨**（安全側）。

## 10. 書き換えリスク評価

### 10.1 チェックサム（実測）

| 検査 | 結果 |
|---|---|
| 36 B ヘッダ +0x14 | crc32(ファイル名) XOR 0xFFFFFFFF【実測一致】。中身のハッシュではない（既存検証 `docs/review_save_layout.md` の Claim 8 と同結論） |
| 36 B ヘッダ +0x1C | 本体長のみ【実測一致】 |
| body 全体 / スロット全体 / スロット先頭〜討伐テーブル の crc32 を探索 | **どこにも保存されていない**【実測】 |
| スロット末尾 | シャウトの UTF-8 テキストで終わり、CRC フィールドは無い【実測】 |
| `system_backup` との差分 | **ヘッダ +0x14 の 4 B のみ**（本体は同一）【実測】。過去状態のバックアップではない |

→ **討伐数・サイズを直接書き換えてもチェックサム更新は不要**と判断できる。参照実装も同様（書戻し後にヘッダを付け直すだけ、`MainForm.cs:197-206`）。

### 10.2 残るリスク

| リスク | 影響 | 対策 |
|---|---|---|
| ゲーム側の独自検証（未検証） | ロード時に「データが壊れています」等 | 1 体 1 項目だけ変えて Ryujinx でロード確認 → 段階的に |
| 最小 > 最大 を作る | 表示破綻・冠の誤判定 | 常に `smin <= smax` を強制 |
| サイズ記録の無いモンスター（古龍・小型）に値を入れる | 表示不整合の可能性 | 既存が 0,0 のときは書き込みを拒否（または強い警告） |
| 討伐数を上限超えにする | 表示飽和・カウンタ破綻 | 9999 以下を推奨 |
| 3 スロットの取り違え | 別キャラの記録を壊す | ヘッダ body+0x10/0x14/0x18 の基点で対象を明示。CLI はスロット番号の 0/1 始まりを統一 |
| 巻き戻し（エディタの全件書戻し） | 手動編集が消える | 編集は 1 経路に統一 |

### 10.3 実機受け入れの見立て

- 記録系の値（討伐数・サイズ）は**ゲームが読み出して表示するだけ**のデータで、進行フラグや所持品と違い他システムとの連動が薄い。直接編集の前例（参照実装 v0.09c がこのオフセットに書く）もある。
- したがって **受け入れられる可能性は高い**【推測】。ただし**この環境では実機／エミュでのロード試験は未実施**（§11-6）。

## 13. 付録 B：再現手順

読み取り専用。Node.js で直接バイトを読む（`run_code` 内で実行した内容）。

```js
const fs = require("node:fs");
const file = fs.readFileSync("C:\\Users\\haruk\\AppData\\Roaming\\Ryujinx\\bis\\user\\save\\0000000000000001\\0\\system");
const body = file.subarray(36);                 // 36 B コンテナヘッダを捨てる
const base = body.readUInt32LE(0x10);           // 0x126474
const KILLS = 0x5EA6, CAPS = 0x5FB8, SIZES = 0x60CA;
const n = 137;
const kills    = [...Array(n)].map((_, i) => body.readUInt16LE(base + KILLS + i*2));
const captures = [...Array(n)].map((_, i) => body.readUInt16LE(base + CAPS  + i*2));
const sizes    = [...Array(n)].map((_, i) => [body.readUInt16LE(base + SIZES + i*4),
                                              body.readUInt16LE(base + SIZES + i*4 + 2)]);
console.log(kills.reduce((a,b)=>a+b), captures.reduce((a,b)=>a+b));  // 8236 730
```
