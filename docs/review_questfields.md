### 1.2 exe 側: 配信クエスト 205 件の固定表【確定】

`out_update\image\main.bin` の **ファイルオフセット `0x01589D70`(VA `0x01589E70`)** に
8 バイト×205 件の表がある。

```
struct QuestCatalogEntry { u32 quest_id; u32 catalog_no; }   // 205 entries, 1640 B
```

* 先頭: `(1020001, 577)`、末尾: `(1111009, 796)`。
* `catalog_no` は **577〜796 を 1 ずつ**増える(621→637 に 15 個の穴、205 件/220 値)【事実】。
* 一意な ID は **200 件**。41〜44 番の 4 件は `1020001` の重複プレースホルダ【事実】。
* 内訳: **0〜44 番 = チャレンジ(闘技場)クエスト 45 件**、**45〜204 番 = イベント(配信)クエスト 160 件**【確定】。
* 205 という数はセーブのクエスト枠数 205 と一致する【事実】。

配列の先頭 6 件と 41〜48 番(生データ):

```

[14](1120001,591) ... [19](1120006,596)
[20](1020015,597) ... [40](1120012,617)
```

#### 1.2.1 実セーブによる決定的検証【確定】

実セーブ(`system`, 4,726,188 B)の DLC セクション(`body+0x0C` = `0xB280`)で検証した。

* クエスト枠 205 × `0x1400`、装入マスク 28 B(`section+0x4C`)。
* マスクのビット番号 `b` と表の添字 `k` の対応を

  ```
  b = k                    (0 <= k < 45)      … チャレンジ
  b = 64 + (k - 45)        (45 <= k < 205)    … イベント
  ```

  と置くと、**表の ID がセーブに入っているか ≟ ビットが立っているか** が

  | 範囲 | 一致 | 不一致 |
  |---|---|---|
  | イベント 160 件 | **160 / 160** | **0** |
  | チャレンジ 45 件 | 41 / 41 | 0 (残り 4 件はプレースホルダで装備枠も空) |

  さらに「セーブのレコード 175 件の ID は全部この表に含まれる」「表の範囲外に立っているビットは 0 本」も確認【事実】。

* 装備枠(`section+0x1049F4`, 45 × `0x800`, 先頭 u32 = クエスト ID)とも 41/41 で一致。

→ `docs/dlc_layout.md` の「カタログの並び順は復元不可」および
`docs/review_quest_injection.md` の U3「イベント側の対応表は不明」は **本表の発見で解消**した。

### 1.3 「定義」のうち何がテーブルに載っているか

| 情報 | どこにあるか |

## 3. `.mib` の未解明フィールドとテーブルの関係

### 3.1 結論: 対応関係は無い【事実】

205 表は 8 B/件(`id`, `catalog_no`)しか持たない。**`.mib` のどのフィールドも表から供給されない。**
`.mib` の値は全て `.arc` 側が唯一の情報源。

したがって「+0x09..+0x1C を表と突き合わせる」という作業は**成立しない**(表に対応する列が存在しない)。
ただし副産物として以下が判明した。

  ```
  mRemAddFrame_1, mRemAddFrame_2, mRemAddLotMax,
  ```

  である。`+0x55/0x56/0x57` が `mRemAddFrame_1/2`+`mRemAddLotMax` に、続く 12 B が

  フィールド幅(u8/u16)の確定には至っていない。**断定しない。**

## 4. 新しいクエスト ID は作れるか

### 4.1 配信クエスト(7 桁 ID) → **不可**【確定】

理由は二重ロック:

1. **列挙**: 205 件固定表(§1.2)。表に無い ID はセーブに入れても一覧に出ない。
   `review_quest_injection.md` の M2(自由枠への新規導入は不可視)を、表の実体で裏付けた。
2. **ビット割当**: マスクは 224 bit で、内訳が 45(チャレンジ)+ 19(未使用)+ 160(イベント)。
   新規 ID に割り当てられる空きビットは存在しない(45〜63 の 19 bit は未使用だが、
   表に対応エントリが無いので使っても意味が無い)。

可能なのは **既存カタログ項目の使い回し**(=現在の mhnxeditor の方式)。
その場合も **`.mib +0x0C` の ID は元のまま**にする必要がある(表の ID と一致しないと引けない)【推定・高】。

> 表を exe パッチで拡張する道は技術的にはある(205→N 件、ビットも再割当)が、
> セーブ側の 205 枠・装備枠 45/`0x800` の構造も同時に縛られるため、**現実的でない**。

### 4.2 拠点クエスト(3〜6 桁 ID) → **原理的に可能**【推定・高】

* 一覧の元は romfs の `vq/gq/gq2/tq.arc` という**ただの ARC コンテナ**。
  ここに `questData_<新ID>` と `questData_<新ID>_jpn` を 1 組追加すれば、
  一覧に載る可能性が高い(exe 改造不要)。
* 併せて `nativeNX\arc\quest\q<新ID 7桁>.arc` を用意する必要がある(`quest\q%07d` で開かれる)。
* ただし未検証点が 3 つある:
  1. 追加先のどの .arc に入れるべきか(vq/gq/gq2/tq のどれか)が ID 依存か、単に「どこかに入っていれば良い」か。
  2. ID の範囲に制約があるか(例: 村は 101–941、集会所は 10xxx のような規則)。
  3. 受注条件・ランクは `.mib` の値だけで決まるのか、一覧側の並び順に依存するか。
* 安価な検証手順(実機 1 回で判定可能): 28 件の「一覧に無いクエスト」のうち 1 件
  (例: 712)を `vq.arc` にコピーして一覧に出るか見る。出れば「一覧 = 集約 .arc」が確定。

### 4.3 ID の使い回しに関する注意【事実】

* `.mib +0x0C` と `q%07d.arc` のファイル名は **q#######.arc の全 1,855 本で一致**(§5.3 の集約 4 本は対象外)。
  → ファイル名だけ変えて中身の ID を変えないと、参照が全部ずれる。
* 逆に「中身の ID を変えてファイル名も変える」のは自由。**ID はファイル名と `.mib` の 2 箇所**。

## 5. `.arc` エントリ構成 — 必須 / 任意

### 5.1 実測: 1,855 本すべてが 8 種類全部を持つ【事実】

| 拡張子 | エントリ名 | 本数(1 クエストあたり) |
|---|---|---|
| `.mib` | `quest\questData\questData_<id>` | 1 |
| `.gmd` | `quest\questData\questData_<id>_jpn` | 1 |
| `.qdl` | `quest\questLink\questLink_<id>` | 1 |
| `.sem` | `quest\boss\setEmMain\b_*` | 1〜5(物理は重複除去後) |
| `.esl` | `quest\zako\emSetList\z_*` | 1〜3 |
| `.rem` | `quest\rem\rem_*` | 1〜5 |
| `.sup` | `quest\supp\supp_*` | 1 |
| `.qdp` | `quest\plus\questPlus_*` | 1 |

* 総エントリ数は **12〜16**(141 件の実測: 12=14 本, 13=33 本, 14=66 本, 15=19 本, 16=9 本)。
* `.qdl` の 15 枠は **1,855 本中 1,854 本で全枠が埋まっている**。唯一の例外は `q0090048.arc` の **slot 9(メイン報酬品2)だけが type=0・名前空**【事実】。
  → **slot 9 は空でもゲームは動いている**(公式データに実例がある)ので「メイン報酬枠 2 は省略可能」と言える。他の 14 枠に空の実例は無い。
* `.qdl` の参照名は **1 件の未解決もなく**、すべて同一 `.arc` 内のエントリに解決する【事実】。
  ただし `.qdl` の plus 枠だけは名前が `0000` のように**接頭辞なし**で、
  実エントリは `questPlus_0000`(接頭辞 `questPlus_` を補う)【事実】。

### 5.2 必須/任意の判定

| エントリ | 必須か | 根拠 |
|---|---|---|
| `.mib` | **必須** | 一覧(`vq` 等)にも実体にも入っている。ID・全定義の唯一の入れ物 |
| `.gmd` | **必須** | `.mib +0xE3` が `<id>_jpn` を指す。無いと名前が空になる |
| `.qdl` | **必須** | 15 資源の名前解決表。無いと `.sem/.esl/.rem/.sup/.qdp` を開けない |
| `.sem`×1〜5 | **実質必須** | `.qdl` の slot 0–4 が必ず名前を持つ(ダミー `b_m00em000_00` でも実体が必要) |
| `.esl`×1〜3 | **実質必須** | slot 5–7 |
| `.rem`×1〜5 | **実質必須** | slot 8–12(`rem_000000` ダミーでも実体が必要) |
| `.sup` | **実質必須** | slot 13 |
| `.qdp` | **実質必須** | slot 14 |

* 「`.mib`+`.gmd` だけで 1 本の ARC として成立する」ことは `vq/gq/gq2/tq` が証明している【事実】。
  ただしそれは**一覧用**であって、**受注には `.qdl` 以下の実体が要る**【推定・高】。
* ダミー資源は 1 本の `.arc` に 1 回しか入らない(同じ名前を複数枠が指しても実体は 1 つ)【事実】。
  最頻のダミー: `b_m00em000_00`(6,600 枠)/ `z_m00d_000`(4,314 枠)/ `rem_000000`(4,306 枠)。

### 5.3 例外: クエストではない 4 本【事実】

`gq.arc` / `gq2.arc` / `vq.arc` / `tq.arc` は `.mib`+`.gmd` のみ。
これらの `.mib +0x0C` は「先頭の 1 件の ID」であり、ファイル名とは一致しない
(`gq`=120006, `gq2`=111405, `tq`=90300, `vq`=30298)。
**ファイル名と中身の ID が食い違うのはこの 4 本だけ**(`q#######.arc` の 1,855 本は全件一致)【事実】。

## 9. 実装への提案(mhnxeditor / mhnx-core)

1. **「一覧に載っているか」を検査項目に追加する**(最重要)。
   `vq/gq/gq2/tq.arc` の `.mib` ID 集合を作り、対象クエストが入っていなければ
   `not-in-quest-list`(エラー)を出す。配信なら 205 表との照合で `not-in-catalog`。
   現状の `mib-id-mismatch` だけでは「ファイルは正しいが一覧に出ない」を見逃す。
2. **配信クエストのカタログ表を実装に取り込む**。
   `205 表 (id, catalog_no)` を定数として持ち、`catalog_no - 577 = k` から
   ビット番号 `k`(k<45)/ `64+(k-45)`(k>=45)を計算できる。
   → `docs/dlc_layout.md` の「カタログ順は復元不可」を撤回し、**読み取り専用の照合機能**を実装できる。
   書き込みは引き続き行わない(ビットは元から立っている)。
3. **集約 .arc の編集機能(将来)**。
   `vq/gq/gq2/tq.arc` は通常の ARC v17 なので、既存の `arc_save` 実装でそのまま書ける。
   「一覧に無いクエストを一覧に載せる」機能は exe 改造なしで実現できる見込み。
   まずは**読み取り専用の一覧ビューア**から入れるのが安全。
4. **`quest_kind` の 6/8 を扱えるようにする**。
   `oq_syu` の 7 値では表現できず、Quedixx 経由の保存で壊れる恐れ。
   値 0〜8 をそのまま保持し、未知値は「不明(kind=N)」と表示して**無変更で温存**する。
5. **`+0x58〜+0x63` は引き続き不透明バイトとして温存**(37 パターン)。
   既に `reserved: [u8;12]` で保持しているなら正しい。**書き換え禁止**を明記する。
6. **検査の追加候補**: `rem3 == 255`(19 件)を「未使用」として警告しない。
   `cond1 == 0x2F`(1 人限定)の既存検査は維持。
7. **ドキュメント修正**:
   - `quest_format_spec.md` §1.8「141 件」→「1,855 件。141 は再梱包サンプル」
   - `dlc_layout.md`「カタログの並び順は復元不可」→ 復元手順を追記
   - `review_quest_injection.md` U3 → 解決済みと注記
