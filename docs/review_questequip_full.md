## 2. 【最重要】942 B ペイロードの真の構造

### 2.1 レイアウト（算術と境界の両方で一致）

```
payload +0x00  u32   quest_id            (= 枠ヘッダの値と一致)
payload +0x04  u32   h1 \  h1..h6 は「形式定数」だが 4 種ある（§4）
payload +0x08  u32   h2
payload +0x0C  u32   h3
payload +0x10  u32   h4   = 38400 (0x9600)  全 40 枠で同一
payload +0x14  u32   h5   = 25600 (0x6400)  全 40 枠で同一
payload +0x18  u32   h6   = 12800 (0x3200)  全 40 枠で同一
payload +0x1C  u8    0                      ← ヘッダ末尾（29 B 目）
payload +0x1D  ---- 5 × ブロック（182 B, 以下）----
   block i = payload + 0x1D + 182*i        (i = 0..4)
     +0x00  u8   mWeaponType  (EQUIPMENT_TYPES インデックス)
     +0x01  u8   X            (1..10)
     +0x02  u8   Y            (2..128)
     +0x03  ---  179 B ボディ（下表）
payload +0x3AB 3 B   トレーラ（40 枠中 35 枠が 0, 5 枠が非ゼロ）
合計 29 + 5*182 + 3 = 942
```

**境界の実測根拠**: ボディ +0x9B の弾/ビン 8 枠（24 B）の終端が
`0x20 + 182*i + 179 = 0x1D + 182*(i+1)` と**厳密に一致**する（5 ブロック × 28 枠で成立）。
旧レポートの読み（ブロック先頭 0x20 起点）では各ブロック末尾に 3 B の未説明領域が残っていたが、
ブロック先頭を 0x1D に取ると端数が消える。

### 2.2 ボディのフィールドマップ（旧レポートの表と同じ絶対オフセット）

ボディ = `payload + 0x20 + 182*i`（= block + 3）。オフセットはボディ先頭基準。

| ボディ内 | 長さ | 型 | 実測（母数） | 意味 |
|---|---|---|---|---|
| +0x00 | 1 | u8 | 0 のみ（140/140） | 不明（予約） |
| +0x01 | 6 | u16 ×3 | 0 または装飾品 ID（2646..2807 を実測、旧レポートは 2642..2837） | 武器の装飾品 3 枠【推測】 |
| +0x07 | 1 | u8 | {0:131, 2:8, 3:1}（旧レポート 140 本集計） | 不明 |
| +0x08 | 1 | u8 | 0..3（0:?, 1:?, 2:?, 3:?。実測で 0..3 のみ） | 不明 |
| +0x09 | 20 | u16 ×10 | 0 が多い。非ゼロは 1..64359（2991 以上が 10 種） | **不明**（アイテム ID 空間ではない） |
| +0x1D | 45 | 9 B ×5 | `{u16 a: 216..478, u8 b: 0..15, u16 c,d,e: 0 または装飾品 ID}` | 防具 5 部位＋装飾品【推測】(§7) |
| +0x4A | 9 | u8 + 8 B | +0x4A のみ非 0（{0:多数, 2:数, 8:数}）、残り 8 B は 0 | 不明 |
| +0x53 | 72 | 3 B ×24 | `{u16 item: 1..1728, u8 count: 1..99}` 固定 24 枠 | **支給品BOX**（§3） |
| +0x9B | 24 | 3 B ×8 | `{u16 item: 101..126 または 208..217, u8 count}` 固定 8 枠 | **弾/ビン**（§3） |
| 合計 | 179 | | 1+6+1+1+20+45+9+72+24 = 179 | |

「固定配列＋ゼロ埋め」は再確認済み: 24 枠・8 枠それぞれで
**「0 の後ろに非ゼロ」は 0 回**（A 24 枠 × 140 ブロック = 3,360 枠、B 8 枠 × 140 = 1,120 枠）。

### 2.3 武器種が 14/14 で「記述文と順序まで一致」する（決定的証拠）

クエスト .arc の `questData_<id>_jpn` の依頼内容に「武器種：…」の列挙がある。
これを読んで、セーブの 5 つの武器種（`payload+0x1D+182*i`）と**順序込みで比較**した。

| クエスト | 依頼内容の武器種 | セーブの 5 値 | 一致 |
|---|---|---|---|
| 1020001 | 太刀 狩猟笛 盾斧 ランス ライトボウガン | 14,19,21,10,13 | ✓ |
| 1020002 | 大剣 ハンマー 操虫棍 剣斧 弓 | 7,9,20,15,17 | ✓ |
| 1020003 | 太刀 狩猟笛 剣斧 ガンランス ヘビィボウガン | 14,19,15,16,11 | ✓ |
| 1020004 | 片手剣 ランス 盾斧 操虫棍 弓 | 8,10,21,20,17 | ✓ |
| …（1020005〜1020014 も同様） | | | ✓ |

**一致 14 / 母数 14**（1020015〜1020029 は依頼内容が「武器種：●●…」と伏字のため比較不能）。
「件数が一致する」ではなく **5 要素の順序付き完全一致**である点が重要。
（武器種番号は `EQUIPMENT_TYPES`: 7=大剣, 8=片手剣, 9=ハンマー, 10=ランス, 11=ヘビィ, 13=ライト, 14=太刀,
15=剣斧, 16=ガンランス, 17=弓, 18=双剣, 19=狩猟笛, 20=操虫棍, 21=盾斧）

→ **1 ペイロード = 5 つの武器別ロードアウト**。i 番目のブロックが i 番目の武器の装備＋支給品。

## 4. ヘッダの 6 × u32 は「一定」ではなかった（旧レポートの誤り）

40 枠すべてで 6 値を集計した結果、**4 種類**に分かれた。

| 変種 | h1 | h2 | h3 | h4 | h5 | h6 | 枠数 |
|---|---|---|---|---|---|---|---|
| A | 0x1A402 (107522) | 0x34800 (215040) | 0x70800 (460800) | 0x9600 | 0x6400 | 0x3200 | 31 |
| B | 0x38402 (230402) | 0x5DC00 (384000) | 0x96000 (614400) | 0x9600 | 0x6400 | 0x3200 | 5 |
| C | 0x25802 (153602) | 0x4B000 (307200) | 0x83400 (537600) | 0x9600 | 0x6400 | 0x3200 | 2 |
| D | 0x2D002 (184322) | 0x5DC00 (384000) | 0x96000 (614400) | 0x9600 | 0x6400 | 0x3200 | 2 |

* **h4/h5/h6 は 40/40 で同一**（38400 = 150×256, 25600 = 100×256, 12800 = 50×256）。
* h1..h3 は 4 変種。h1 は必ず `≡ 2 (mod 4)`、h2/h3 は 256 の倍数。
  (h1−2)/1536, h2/1536, h3/1536 は A=(70,140,300), B=(150,250,400), C=(100,200,350), D=(120,250,400) と
  小さい整数になるが、**意味は特定できていない**（§9）。
* 変種とクエスト種別（1020/1120）・使用武器種に相関は見えない（A は 1020/1120 混在）。

**これを「全枠で同値」と書いた旧レポートの記述は誤り。** おそらく一部の枠だけを比較している。

**否定した仮説**: 「h1..h6 はイメージ／romfs に静的データとして存在する」
→ `u32 107522` は **out_update/image 0 件・out_base/image 0 件**、24 B 並びも 0 件。
romfs の `arc/quest`・`table`・`system`（3,043 ファイル / 74.7 MB）でも**0 件**。
したがってこの 24 B は静的データではなく、コードが組み立てているか、
ランタイム構造のコピーである（§6.4）。

## 5. 否定した仮説（旧レポートの記述のうち 3 点）

| # | 旧記述 | 判定 | 根拠（実測） |
|---|---|---|---|
| 1 | 「+0xB3 は（そのレコードの）武器種」 | **否定（帰属が 3 B ずれ）** | ボディは 179 B で +0x9B の 8 枠（24 B）がブロック末尾に**ちょうど収まる**。旧 +0xB3 は次のブロックの先頭 3 B = `{wt,X,Y}`。実際、旧 +0xB3 が 0 の「レコード 4」は弾/ビン 8 枠を持ち、そのブロックの wt はブロック先頭の 0x0D(13=ライトボウガン) で整合する |
| 2 | 「レコード 4 は武器種を持たず共通ポーチ」 | **否定** | レコード 4 = 5 番目のロードアウト（武器種はブロック先頭）。武器種が常に遠隔（11/13/17）で、弾/ビン 8 枠を持つ 28/28 と一致 |
| 3 | 「ヘッダ 6 定数は 40/40 同値」 | **否定** | §4 の 4 変種 |
| 4 | 「+0x1C は 4 B のゼロ領域」 | **否定** | +0x1C は 0 だが +0x1D..+0x1F はブロック 0 の `{wt,X,Y}`（例: 0x0E 0x02 0x3A） |
| 5 | 「5 × 9 B は 5 部位（頭胴腕腰脚）」 | **未確定だが否定的** | 5 個の u16 が**全一致**するブロックが 86/140。5 部位が同 ID になるのは不自然（§9） |
| 6 | 「セーブ層がフィールドを解釈して読み書きする」 | **否定** | セーブ入出力は `0x16800` を**丸ごとコピー**するだけ（§6.2） |

### 6.2 セーブ入出力はこの 0x16800 B を「不透明な塊」として扱う

逆コンパイル結果（`FUN_00036268` = 書き出し / `FUN_00036490` = 読み込み、VA 0x36268 / 0x36490）:

  セーブロード／セーブ処理そのもの。ポインタが NULL のときは 0 埋めで書く（＝空でも 92,160 B を消費）。
* 同セクションには 0x1400 単位の配列（160 枠 / 45 枠）も同居する。45 × 0x1400 = 0x38400 も実在。

```c
FUN_0082D168(auStack_40, *(int *)(*piVar19 + 0xfb0) + uVar41*0x800 + 8, 0x800, 2);
FUN_0081C2AC(&local_7d0, auStack_40, 0x80000, 0x1000);
FUN_00349468(local_3f8, &local_7d0);                                  // 中身を書く
uVar33 = FUN_0081CB14(&local_7d0);
*(undefined4 *)(*(int *)(iVar35 + 0xfb0) + uVar41*0x800 + 4) = uVar33; // 枠 +0x04 = 長さ
*(uint *)(iVar35 + 0xf80 + (uVar41>>5)*4) |= 1 << (uVar41 & 0x1f);     // 枠 +0xF80 のビット
```

* ベースポインタ `obj+0xFB0`、ストライド `0x800`（`lsl #11` を 3 箇所で実測）、
  **+0x00 = ID / +0x04 = 長さ / +0x08 = データ**、使用ビットは `obj+0xF80`。**セーブの 45 枠と同型**。
* ただしこの関数が扱う ID は `uVar40 + 0xF6B44`（= 1,010,500 + 連番）で、セーブの 1020001/1120001 とは
  **一致しない**。別 ID 空間（リソース番号）である可能性が高い【推測】。
  → 「この関数がまさに装備枠を書く」とまでは断定できない（§9）。
* 同関数内に、u16 の ID を **45 件（0x2D）** と **205 件（0xCD）** の 8 B レコード表
  （`+4 が u16` をキーに `+0 の u32` を引く）で引くループがある。これは §1 のカタログ
  （{questId, nameIdx}）と件数・形式が一致する（= 名前インデックス → クエスト ID の変換）。

## 7. 1120xxx（訓練ネコ）形式の実測

* 169 = 29 + 5 × 28（端数なし）。ブロックは `payload + 0x1D + 28*i`。
* ブロック先頭は `{u16, u8=0}` の 3 B グループ（1020 の `{wt,X,Y}` と同じ「3 B ヘッダ」）。
* 実測例（slot 14 = 1120001, block 0）:
  `79 00 00 | 89 00 00 | 89 00 00 | 19 00 00 | 18 15 0f 00 | 00 00 00 00 | 1b 1e 02 00 | 00 00 00 00`
* 先頭 4 つの u16 は 106..190（slot 14..19 の下位グループ）と 306..350（slot 35..40 の上位グループ）に分かれ、
  2 番目と 3 番目が**同値**になる例が多い（例 0x89,0x89 / 0x54,0x54）。
  otWeaponData_jpn.gmd（1,018 文字列）・otArmorData_jpn.gmd（2,108 文字列）のインデックス空間と
  値域が重なるため、**オトモ武器／オトモ防具の ID** である可能性が高い【推測】。
* 12 ブロック × 5 = 60 本すべてで「+0x02 / +0x05 / +0x08 が 0」等、旧レポートの観測は再現した。
* 意味の確定には otWeaponData/otArmorData の ID 対応表が必要（今回は未実施）。

## 8. 実装への提案

### 8.1 書き換えてよい範囲（ゲームが読む可能性が高い＝データだけの部分）

| フィールド | 変更の安全性 | 理由 |
|---|---|---|
| ボディ +0x53（24 枠 ×3 B）**支給品** | **安全（推奨）** | 純データ。サイズ・他構造に影響しない。空きは 0 で埋める規約も自明（非ゼロ残骸 0 件） |
| ボディ +0x9B（8 枠 ×3 B）弾/ビン | **安全** | 同上。ただし i=4（遠隔）ブロックのみ意味を持つ |
| 個数（count） | 安全 | 実測 1..99。0 にすれば「空き」 |
| ボディ +0x1D の防具 5 件 | 中（意味未確定） | a は防具 ID 空間に見えるが、5 件同値 86/140 の理由が不明。**変えるなら 5 件まとめて** |
| ブロック先頭 +0x00 武器種 | **危険** | メニューの武器選択と実データが食い違う。単独変更は非推奨 |
| ブロック先頭 +0x01/+0x02（X, Y） | 危険 | 意味不明（スタイル／技／武器レベル候補） |
| ヘッダ +0x04..+0x1B（6 × u32） | **触らない** | 意味不明。4 変種があり、検証値の可能性を否定できない |
| ヘッダ +0x1C / トレーラ +0x3AB | **触らない** | 0 が既定。5 枠だけ非ゼロで規則不明 |
| 枠 +0x04（長さ 942/169） | **触らない** | 長さと中身が食い違うとローダが壊れる可能性 |
| 枠 +0x00（クエスト ID） | **触らない** | カタログ順・マスクと連動 |
| 導入マスク DLC+0x4C のビット 0..44 | **触らない** | 使用枠と 1:1。増減するならカタログ知識が必須 |

### 8.2 「支給アイテムを差し替える」最小手順（確定）

```text
slot_base   = 36 + 0xB280 + 0x1049F4 + slot*0x800          # slot = 0..44
payload     = slot_base + 8
block(i)    = payload + 0x1D + 182*i                       # i = 0..4（武器の並び順）
body        = block(i) + 3
A[k]        = body + 0x53 + 3*k                            # k = 0..23  支給品BOX
B[k]        = body + 0x9B + 3*k                            # k = 0..7   弾/ビン
書く値      = u16 itemId (LE) + u8 count
```

* 例: slot 0 (1020001) / i=0（太刀）/ 先頭の支給品 → 絶対 **1,113,363** の 3 バイト。
  現在値 `BC 06 02` = 1724 支給専用秘薬 ×2。ここを `B0 06 05`（1712 相当＋×5）等に差し替える。
* 変更後にやること: **それ以外のバイトは 1 バイトも触らない**（サイズ・長さ・マスクは不変）。
* 差し替え先の制約: itemId は実測 1..1728 の範囲（ITEM_NAME_LIST の範囲内）。
  個数は 1..99。**同じブロック内で「0 の後ろに非ゼロ」を作らない**（空きは 0）。

### 8.3 検証用に追加したいコマンド（提案）

```text
mhnx equip-trial <save>                 # 45 枠 → 5 ブロック × {武器種, X, Y, 防具5, 支給品24, 弾8}
mhnx equip-trial-set <save> --slot 0 --weapon 14 --list A --index 0 --item 1712 --count 5
```
実装時は以下を**アサート**する（すべて本レポートで母数を確認済み）:
1. `枠+4` が 942 か 169 のどちらか。
2. `枠+8+len` 以降が全ゼロ。
3. A/B の空きは 0 で、0 の後ろに非ゼロが無い。
4. 武器種が 7..21（12 を除く）。
5. itemId < 3000、count ≤ 99。
