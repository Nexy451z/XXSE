## 0. 結論（先に要点）

1. **討伐数・捕獲数・狩猟サイズの 3 テーブルはスロット内に 1 組だけ存在する。**
   0x5EA6 / 0x5FB8 / 0x60CA。**同一内容のコピーはスロット内のどこにも無い**
   （137×u16 の完全一致スコアは自分自身の 129/137 を除くと最大 6/137）。
2. 参照実装が扱っていない**大きな未マップ領域が 4 つ**あった:
   (a) **0x208CE 装備マイセット 52×136 B**（名称つき・9 件使用）、
   (b) **0x2C400–0x38700 zlib 圧縮レコード列**（150 件、各 6,328 B に展開）、
   (c) **0x813D0–0x104F00 クエスト束 0x1400 B ブロック列**（スロットの 46%）、
   (d) **0xCD940–0xCF600 DLC アイテムセット名 + 配信オトモのプロフィール**。
3. セーブは**部分的に zlib 圧縮**されている（スロット 0 で有効な zlib ストリーム **1,176 本**）。
   既存ドキュメントにこの記載は無い。
4. 参照実装の MANUAL_SHOUTOUT_OFFSETS = 0x11D629 / Size 60 の "Size 60" は
   **ブロック長ではなくレコード長**。実測は 60 B レコード × 48 件 = 2,880 B。
5. **このセーブの 3 スロットは独立標本ではない**（スロット 1 と 2 は全 1,172,928 B が完全一致、
   スロット 0 も討伐数・シャウト・オトモが一致）。3 キャラ比較は「別キャラの裏取り」には使えない。

## 4. 個別領域（項目 / オフセット / 型 / 実測値 / 根拠）

### 4.1 ★ モンスター討伐数 137 × u16 — 断定できる

| 項目 | オフセット | 型 | 実測値（スロット 0） | 根拠 |
|---|---|---|---|---|
| 討伐数テーブル | **0x5EA6** | u16 × 137 | 非ゼロ 129 件 / 137、最大 **893**、合計 8,236 | 参照実装 MONSTERHUNT_OFFSETS と一致。0x5EA6+274 = 0x5FB8 に捕獲数が続く整数関係 |

先頭 10 件（index 順、モンスター ID との対応は未確定）:
```
idx  0..9 : 24, 11, 18, 31, 24, 7, 18, 21, 14, 7
idx 10..19: 4, 24, 28, 19, 4, 30, 26, 16, 17, 27

```

**「討伐数らしさ」を件数以外で裏づける反証可能な特徴（実測）**

1. **値域**: 非ゼロ 129 個すべてが 1..999。最大 893。
2. **分布**: 中央値 20、平均 63.8、98/129 が 50 以下、100 超は 23 件。
   「大半が小さく一部が大きい」右裾分布で、討伐数として自然。ID 列やフラグならここまで滑らかな右裾にならない。
3. **一意性（最も強い）**: スロット全体を 2 B 窓で走査し
   「窓内の非ゼロ u16 が 100 個以上あり、その非ゼロ値の **100%** が 1..999 に入る」
   条件を満たす 256 B 窓は **0x5EA0 の 1 か所だけ**（次点 0.554、3 位以下 0.28）。
   このテーブルは値域の点でスロット内で特異。
4. **重複が無い**: 137×u16 の完全一致スキャン（全オフセット・両アラインメント）で、
   自分自身（129/137）以外のスコアは最大 6/137。**同一テーブルのコピーは存在しない**
   → 「別の場所にも討伐数がある」という仮説は否定できる。

**未確定**: 137 個の index → モンスター ID の対応。ID 昇順と推定しているが、
モンスター名表と突き合わせていないので断定しない。

### 4.3 狩猟サイズ 137 ×（u16 min, u16 max）

| 項目 | オフセット | 型 | 実測値 | 根拠 |
|---|---|---|---|---|
| サイズ | **0x60CA** | (u16,u16) × 137 = 548 B | 非ゼロ 78 件 / 137。**全 137 件で min <= max**（違反 0） | MONSTERSIZE_OFFSETS と一致。0x60CA+548 = 0x62EE = 装備BOX 先頭 |

先頭 10 件（min, max）:
```
(88,120) (25,122) (96,110) (91,122) (95,125) (96,110) (92,113) (92,123) (94,124) (96,124)
最小値の範囲 25..103 / 最大値の範囲 108..160（非ゼロ 78 件）。max/min 中央値 1.304
```

解釈（**推測**）: 参照実装は「4 バイト/匹」としか書いていないが、実データは **2 つの u16 のペア**で、
しかも 137/137 で min<=max が成立する。偶然この不等式が全件成立する確率は 2^-137 なので、
ペア構造は偶然ではない。値域 88–125（1 件だけ 150）は「基準サイズに対する百分率」に見える。

**注意**: 非ゼロは 78 件しかないのに討伐数は 129 件非ゼロ。サイズ未記録のモンスターが 51 匹いる。
「サイズは初狩猟時に登録される」と考えるのが自然だが、これは推測で 1 サンプルでは検証できない。

### 4.5 ★ アイテムセット 8 × 170 B

| 項目 | オフセット | 型 | 実測値 | 根拠 |
|---|---|---|---|---|
| アイテムセット | **0x17CF** | 170 B × 8 | 1 件目のみ実データ、以降は名前 －－－ | 170×n で名前位置が一致（0x17CF, 0x1C75 の 2 点） |

- 0x17CF = 0x278 + 5,463（アイテムBOX の直後）。
- rec0: 名前 剣士(汎用)、+0x2A から **16 組の (u16 item id, u16 個数)**:
```
(9,10) (10,10) (28,2) (29,1) (31,3) (32,2) (40,1) (41,1)
(42,1) (56,20) (70,99) (71,5) (73,8) (83,1) (84,1) (303,10)
```
- 参照実装のコメント行 ITEM_SET_OFFSET = 0x0EDE (1360, 8 × 170) は **0x0EDE ではなく 0x17CF** が実データ位置。
  0x0EDE はアイテムBOX の内側で、そこにセット名は無い（コメントアウトされたまま放置された痕跡）。

### 4.6 ★ zlib 圧縮レコード列 0x2C400–0x38700

| 項目 | オフセット | 型 | 実測値 | 根拠 |
|---|---|---|---|---|
| 圧縮レコード | **0x2C400** 〜 | [40 B hdr][u32 圧縮長][zlib] | **150 件**、いずれも展開後 **6,328 B ちょうど** | zlib 展開成功 150/150。レコード長 = 44 + 圧縮長 |

- 実例: 0x2C6C1 のストリームは 1,607 B → 6,328 B。次のレコードは 0x2CD34（= 0x2C6C1 + 1,651 = 44 + 1,607）。
- 尾部だけのレコードは 73 B（44 + 29）。**0x0C9BA0 の 73 B レコード列と同型**
  （0x0C9BA0 から 0x49 間隔で 50 件前後、1 本 6,328 B に展開）。
- 展開後の内容: RGBA 色（ff ff ff ff, fa f5 e6 ff, c8 89 52 ff, 0xFF3E363D など）と
  **オトモのセリフ**（例: 狙った素材は逃がさないニャ）、小さな ID 群。6,328 B 中 非ゼロは 1,958 B。
- **推測**: オトモ（配信/雇用候補）のプロフィール（名前・色・セリフ）を 1 件 6.3 KB 固定長で持ち、
  保存時に zlib で潰している。確証は無い。
- スロット 0 と 1 の一致率 99.9%。**キャラ固有データではなさそう**。

**重要な但し書き（実測）**: スロット 1 と 2 は **全 1,172,928 B がバイト一致**（sha1 ed17f795…、
スロット 0 は 7acd28a9…）。さらにスロット 0 は討伐数・捕獲数・サイズ・シャウト・オトモで
スロット 1 と完全一致している。**独立な 3 キャラのサンプルではなく、1 キャラを複製して
一部の値だけ書き換えた状態**と考えるのが自然（推測）。したがって
「3 キャラで同じ位置に同じ種類のデータが入っているか」の答えは
**「討伐数・捕獲数・サイズ・シャウトは 3 スロットで完全に同位置・同内容」**だが、
それは**意味の裏づけにはならない**（複製の可能性が高いため）。
この 1 ファイルで「キャラごとに独立に伸びるカウンタ」を実証することはできない。

## 6. 未確定・反証できなかったこと

1. **137 index → モンスター ID の対応表**。モンスター名テーブルとの照合をしていない。
2. **サイズの単位**。u16 が百分率なのか、0.01 単位の cm なのか。
   min<=max は全件成立するのでペア構造は確実だが、意味は未確定。
3. **0x5E3E の定数島**（63/609/333/10000、16×99、16×9999）の意味。
4. **0x1C7F–0x5E3E のビット配列**（何のフラグか）。
5. **0x2C400 の 6,328 B レコード**が「オトモのプロフィール」という推定は、
   セリフと RGBA が入っているというだけの状況証拠。ヘッダ 40 B の意味も不明。
6. **クエスト束の意味**。「クエストのリソースキャッシュ」は推定。
   スロット 0 だけ中央に 0x1D0B0 B の穴がある理由も不明。
7. **参照実装の内部矛盾**: PALICO_OFFSET = 0x23BB6 / 84 × 324 = 27,216 B は 0x2A426 で終わるが、
   その範囲に HR_POINTS 0x280B（実測 4,100,000）と FUNDS_OFFSET2 0x280F
   （実測 9,997,199 = 0x24 と同値）が入ってしまう。どちらかが誤り。
   本解析ではオトモの内部構造を追っていないので**判定しない**。
8. **討伐数テーブルが 137 件で正しいか**の独立検証。0x5EA6+274 = 0x5FB8、
   0x5FB8+274 = 0x60CA、0x60CA+548 = 0x62EE という**整数の連鎖**は強いが、
   「137 匹」という主張そのものは参照実装由来。
9. 0x2C400 以降の zlib レコードの**再圧縮**がゲームに受理されるかは未検証（書き込み禁止のため）。

## 7. 実装提案

### 7.1 すぐ入れる価値がある（根拠が強い）

1. **討伐数・捕獲数・サイズの編集 UI**（0x5EA6 / 0x5FB8 / 0x60CA）。
   サイズは (u16 min, u16 max) のペアとして読み書きし、**書き込み時に min<=max を強制**する。
   現在の Offsets.cs のコメント「4 bytes per monster」だけでは型が決まらないので、
   「2 × u16」と明記すべき。
2. **テストに「値域」アサーションを入れる**（件数一致は根拠にならない、という指摘への対応）:
   - hunts: 非ゼロ数 == 129、max == 893、全要素 <= 999
   - captures: 非ゼロ数 == 47、max == 598
   - sizes: 全 137 件で min <= max、非ゼロ数 == 78
   - 「非ゼロ u16 が 100 個以上ある 256 B 窓のうち、非ゼロ値が全部 1..999 なのは 0x5EA0 だけ」
     という一意性テスト（本レポートの主張を回帰テストにする）
3. **シャウトのオフセット修正**: 文字列位置 0x11D629 はそのまま使えるが、
   「Size 60」を「レコード長 60、ブロックは 48 レコード = 2,880 B」に直す。
   自動側も 0x11E169 は文字列位置で、基点は 0x11E158。
4. **アイテムセットの正しいオフセット**: 0x0EDE ではなく **0x17CF（8 × 170 B）**。
   レイアウトは「名称 32 B + 16 組の (u16 id, u16 qty)」。

### 7.2 新機能として追加できる（構造は取れたが意味は推定）

5. **装備マイセット（0x208CE, 52 × 136 B）**: 名称 32 B + ID 列 + RGBA 5 個。
   ID 列の意味（部位順か）が未確定なので、**読み取り専用のビューアから**始める。
   書き込みは「名称だけ」に限定すればリスクが低い。
6. **DLC アイテムセット／配信オトモの表示（0xCD940–0xCF600）**: スロット 0 にしかデータが無いので、
   「このキャラは DLC 配布物を受け取っている」判定に使える。

### 7.3 触らない方がよい

7. **クエスト束（0x813D0 以降）と zlib 圧縮レコード（0x2C400 以降）は書き込み対象にしない。**
   再圧縮の互換性（zlib レベル・ヘッダ 40 B の意味）が未検証で、壊したときの影響が読めない。
   読み取り（展開して表示）だけなら安全。
8. **空き領域 0x18630–0x208C0（32.6 KB、3 スロット共通でゼロ）** は魅力的だが、
   ゲームが「未使用＝ゼロ」を前提にしている保証が無い。注入に使うなら
   **必ずバックアップ＋実機での読み込み確認**を前提条件にする。

### 7.4 ドキュメント修正

9. Offsets.cs のコメント行（0x0EDE のアイテムセット、PALICO 0x23BB6 + 27216 の重なり）を
   実測に合わせて更新、または「未検証」と明記。
10. 「zlib 圧縮されている」事実を save_layout 系ドキュメントに追記。
    「スロットは固定長構造体の連結」という前提は **0x2C400 以降では成り立たない**。
