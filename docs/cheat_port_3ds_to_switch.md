## 2. 移植できない理由（実測で証明）

3DS と Switch では**使われている命令そのものが違います**。

| | 3DS (1.4.0) | Switch |
|---|---|---|
| ビットフィールド抽出 | lsl r2,r2,#0x16 + lsr r2,r2,#0x1b | ubfx r2, r2, #0x13, #5 |
| ビットフィールド消去 | bic ip, ip, #0x3e0 | bfc sl, #0xd, #1 |
| cmp の直後 | nop (0xE320F000) が入る | nop が入らない |

これは CPU の世代の違いです。3DS は ARM11（ARMv6K）なので ubfx や bfc が無く、
コンパイラが lsl/lsr で代用します。Switch 版は ARMv7 以降を対象にビルドされているため、
最初から ubfx / bfc を使います。

### 実測した証拠

```text
(1) 「cmp rX,#0 ; nop ; beq」という並びを、
    「mov rX,#0 ; pop ; mov rX,#1 ; pop」の周辺で探した結果

      3DS   : 候補 38 箇所のうち 15 箇所が該当
              対象の 0x841A64 にも 2 つ存在（= 検出器は正常に動いている）
      Switch: 候補 28 箇所あるが、該当は 0 箇所

(2) 「and rX,rY,#0x1f」の近くに「bic rX,rY,#0x1f」がある箇所

      3DS   : あり
      Switch: 0 箇所（ubfx / bfc に置き換わっているため存在しない）
```

つまり **3DS の命令列をそのまま Switch で探す方針は原理的に成立しません。**
これは今回の 3 件だけでなく、今後の移植すべてに当てはまります。

## 3. どうすれば移植できるか

### 3.1 考え方

アドレスの対応ではなく、**同じ役割の関数を Switch 側で見つけ直す**必要があります。
使える手掛かりは 3 つです。

1. **データ構造**（両者で共通のはず）
   - BC の関数: 構造体 +0x3EC のポインタ、+0x198 の 16bit フラグ、
     境界値 20 (0x14) と 50 (0x32)
   - 入室の関数: ビットフィールドが bit5-9（マスク 0x3e0）と bit10-14（マスク 0x7c00）
2. **呼び出し関係**（アイテム使用処理、入室処理）
3. **動的解析**（実行中のメモリを見る）

### 3.2 最短の道: Ryujinx で動かしながら探す

このワークスペースには**すでに Ryujinx 用の解析ツール**が揃っています。

```text
C:\anyWorkspace\nx\tools\ryu_gdb.py       Ryujinx の GDB スタブ経由で読み書き
C:\anyWorkspace\nx\tools\mhxx_live.py     実行中のメモリ走査
C:\anyWorkspace\nx\tools\memscan.py       値の検索
C:\anyWorkspace\nx\tools\eden_gdb.py      別エミュレータ用
```

手順（BC の爆弾を例に）:

```text
1. Ryujinx で MHXX を起動し、ベースキャンプで爆弾を設置しようとする
2. 「0 か 1 を返して pop で終わる小さな関数」28 箇所それぞれに
   ブレークポイントを置き、設置操作で止まるものを選ぶ
3. 止まった関数のアドレスを記録する
4. その中の mov rX,#0 を mov rX,#1 に変えて挙動が変わるか確認する
5. 変われば、それが移植先
```

候補 28 箇所はすでに列挙済みです（@@tools/ret01.py@@ の出力）。

### 3.3 emulator のチート機能

Ryujinx は Atmosphere 形式のチートファイルを読みます。実機用と同じものが使えます。

```text
mods/contents/<タイトルID>/cheats/<ビルドID>.txt
```

ただし**書き換え位置の指定方法が実機と異なる**場合があります（実機は VA 基準、
エミュレータはモジュール相対のことが多い）。確定後に両方の書式を用意します。
