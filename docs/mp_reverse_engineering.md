# カスタムクエストのマルチプレイ制限を逆解析する

対象: MHXX (Nintendo Switch) main.bin / MHXX (3DS) 更新データ 1.4.0 exeFS .code

---

## 0. 結論（先に要点）

| 項目 | 状態 |
|---|---|
| 3DS 版チートコードの**検証** | **完了**。1.4.0 の実コードとバイト単位で一致 |
| 3DS 版チートが何をしているか | **判明**。クエストアーク読み込みの失敗判定を成功に固定している |
| Switch 版の対応箇所 | **未特定**。配信クエスト管理コードの領域までは絞り込めた |
| Switch 版でのチートコード | **未完成**（下記の理由により、安易に断定しない） |

---

## 1. 3DS のチートコードは本物だった

配布されていたチートコード:

```text
[カスタムクエストマルチプレイヤー修正]
004518E8 E3A06001
00451BE8 E3A00001
```

MHXX 更新データ 1.4.0 (JPN) の CIA から exeFS の .code を取り出して確認した結果:

| アドレス | 元の命令（実コード） | 書き換え後 |
|---|---|---|
| 0x004518E8 | @@movne r6, #0@@ (0x13A06000) | @@mov r6, #1@@ (0xE3A06001) |
| 0x00451BE8 | @@mov r0, r5@@ (0xE1A00005) | @@mov r0, #1@@ (0xE3A00001) |

**2 箇所とも実在し、命令の意味も一致しています。** この 2 つは同じ関数の中にあります。

- 関数の開始: **0x00451874**
- 関数の終了: 0x00451BF4 付近（@@add sp, sp, #0x2c@@ / @@pop {r4,r5,r6,r7,r8,sb,sl,fp,pc}@@）
- 2 箇所の距離: 0x300

### 読み込むアドレスの根拠

exheader の値（ctrtool で取得）:

```text
Code text address: 0x00100000     ← .code のロード先
Code text size:    0x00AF2438
Flags:             03 [compressed] [sd app]
```

ファイル内オフセット = VA - 0x00100000。伸長後の .code は 13,045,760 バイトで、
text + rodata + data の合計と一致します。

```text
0x004518E8 - 0x00100000 = 0x03518E8   → ファイル内 0x3518E8
```

## 2. この関数が何をしているか

逆アセンブリ（抜粋）:

```asm
0x00451874  push  {r0,r1,r4,r5,r6,r7,r8,sb,sl,fp,lr}
0x00451878  sub   sp, sp, #0x24
0x0045187C  add   r1, r1, r1, lsl #2      ; r1 = 添字 * 5
0x00451880  mov   r6, #1                  ; 成功フラグ
0x00451884  ldr   r0, [sp, #0x24]         ; 第5引数（クエスト配列の先頭）
0x00451888  ldr   r7, [pc, #0x364]
0x0045188C  ldr   r2, [pc, #0x364]
0x00451890  add   r0, r0, r1, lsl #10     ; r0 += 添字 * 0x1400  ★
0x00451894  add   r5, r0, #0x1000
0x00451898  add   r4, r0, #0x1c00
0x0045189C  add   sb, r0, #0x3000
0x004518A0  ldr   r8, [r5, #0xe90]
...
0x004518C8  mov   r0, #0x100
0x004518CC  str   r0, [sp]                ; バッファ長 0x100
0x004518D0  mov   r3, sb
0x004518D4  mov   r2, r8
0x004518D8  mov   r1, r4
0x004518DC  add   r0, sp, #8
0x004518E0  blx   #0x1181c4               ; パス文字列を組み立てる
0x004518E4  tst   r0, #0x80000000         ; 失敗したか？
0x004518E8  movne r6, #0                  ; ★ 失敗ならフラグを落とす（ここを書き換える）
0x004518EC  add   r0, sp, #8
0x004518F0  blx   #0x1183e4
...
0x00451908  cmp   r6, #0
0x0045190C  moveq r0, #0
0x00451910  beq   #0x451bec               ; 失敗なら 0 を返して終了
0x00451914  ldr   r7, [pc, #0x2e4]
0x00451918  mov   r1, #1
0x0045191C  add   r8, pc, #0x2e0          ; r8 = "nativeLite\arc\"
0x00451920  ldr   r0, [r7]
0x00451924  add   r0, r0, #0xe000
0x00451928  strb  r1, [r0, #0x4d8]
0x0045192C  mov   r0, r8
0x00451930  bl    #0x2e4344               ; そのパスで開く
...
0x00451BE0  mov   r0, #0
0x00451BE4  str   r0, [sp, #4]
0x00451BE8  mov   r0, r5                  ; ★ 戻り値（ここを書き換える）
0x00451BEC  add   sp, sp, #0x2c
0x00451BF0  pop   {r4,r5,r6,r7,r8,sb,sl,fp,pc}
```

### 読み取れること

1. **@@add r1, r1, r1, lsl #2@@ のあと @@add r0, r0, r1, lsl #10@@** = 添字 × 5 × 0x400 = **添字 × 0x1400**。
   0x1400 は**配信クエスト 1 件分のサイズ**（セーブの DLC 領域で確認済み）です。
2. 文字列 **@@nativeLite\arc\@@** をパスとして使っています。
3. 失敗すると 0 を返し、成功すると非 0 を返す関数です。
4. チートは **失敗判定を潰して必ず成功させる** ものです。

つまり「クエストのアークを読み込む／検証する処理」を無条件で通しています。
これがマルチプレイ時のクエスト検証を素通りさせる、というのが配布されていたコードの意味です。

> 注意: この関数は他にも呼ばれている可能性があり、副作用（本来読み込めないクエストを
> 読み込もうとする）があります。導線の全体像までは追えていません。

## 3. Switch 版の対応箇所（未特定・途中経過）

### わかったこと

- Switch 版 main.bin も **ARM32 (AArch32)** です。NPDM の ACI0 flags = 0x00000000 (is64bit=0)、
  ARM32 プロローグが 11,721 個、ARM64 プロローグは 0 個。
- 文字列 @@nativeLite\arc\@@ は Switch 版にも**存在します**（イメージ内 0x01589B18）。
- 配信クエストの配列（ストライド 0x1400）を扱うコードは Switch 版にもあります:
  - 0x00038960: @@add r6, r6, #0x1400@@ / @@cmp r3, #0xa0@@（160 件ループ）
  - 0x000388C4: @@add r6, r6, #0x1400@@ / @@cmp r3, #0x2d@@（45 件ループ）
  - 0x00038974 と 0x000389FC に **3DS とまったく同じ ×5 → ×0x400 の命令列**があります

### アドレス規約（重要・最初に間違えた点）

Switch 版 main.bin では:

```text
VA（仮想アドレス）= ファイルオフセット + 0x100
```

- @@strings.txt@@ に書かれているアドレスは **VA** です。ファイル上の実位置は **VA - 0x100**。
- .text 内のリテラルプールに入っているポインタ値も **VA** です。
- 逆アセンブルするときは必ずファイルオフセットで行うこと。

検証（strings.txt の先頭 4000 件が、そのアドレス位置に実在するか）:

```text
ファイルオフセットとして読む   :    0 / 4000 一致
VA - 0x100 として読む          : 3999 / 4000 一致
```

最初この規約を誤って「ファイルオフセット == VA」と仮定したため、
文字列ポインタの検索がすべて 0x100 ずれ、「参照は 0 件」という誤った結論を出しました。
修正後は参照が見つかっています（下記）。

### 修正後にわかったこと

VA を正しく計算し直すと、@@nativeLite\arc\@@ は **参照されています**。

```text
文字列 nativeLite\arc\  ファイル 0x01589B18 / VA 0x01589C18
   -> リテラルプール ファイル 0x02D102C (VA 0x02D112C)
   -> ロード命令     ファイル 0x02D0DD8
   -> このエントリは ID 0xd を持つ
```

ただしこの参照は**クエスト固有のコードではありません**。0x02D0DA8〜0x02D0E38 は
同じ形（ID をロード → 文字列テーブルを引く → 共通処理へ分岐 @@b #0x2D0E64@@）が
繰り返す**パス文字列テーブル＋汎用ローダ**です。

```asm
0x02D0DD8  ldr   r0, [pc, #0x24c]     ; "nativeLite\arc\"
0x02D0DDC  mov   r1, #0x10
0x02D0DE0  ldr   r0, [pc, r0]
0x02D0DE4  ldr   r6, [r0]
0x02D0DE8  mov   r0, #0x10
0x02D0DEC  bl    #0x495d4c
0x02D0DF0  mov   r1, r0
0x02D0DF4  ldr   r0, [pc, #0x234]
0x02D0DF8  mov   r2, #0x14
0x02D0DFC  mov   r3, #0xd             ; このパスの ID
0x02D0E00  ldr   r0, [pc, r0]
0x02D0E04  b     #0x2d0e64            ; 共通のディスパッチャへ
```

### 特定できていない理由

- 3DS 版の特徴的な即値（0x1000 / 0x1c00 / 0x3000 / 0xe90）は Switch 版にそのままは出てきません。
  データ構造が Switch 版で変わっているためと思われます。
- 3DS 版のエラー判定の形（@@tst rX,#0x80000000@@ の直後に @@movne rY,#0@@）は
  Switch 版のどこにもありません（0 件）。別の書き方にコンパイルされています。
- ファイルパスは**文字列テーブル + 汎用ローダ**方式なので、パスからクエスト固有の
  検証コードへ直接たどれません。ID（0xd など）から間接的に追う必要があります。

### 次にやるべきこと

1. Ghidra で 0x00038000〜0x00039000 を関数単位でデコンパイルし、
   配信クエスト管理クラスの構造を把握する。
2. そのクラスのメソッド一覧から「読み込み」「検証」に相当するものを特定する。
3. 3DS 版の関数（0x00451874）を Ghidra に読み込ませ、**関数のシグネチャ**（引数の数・型）で
   照合する。
4. 実機で「どの時点で弾かれるか」を観察し、チートで変えるべき値を絞る。

## 5. Switch 版には制限が無い可能性が高い

### 5.1 そう考える根拠

| # | 根拠 | 強さ |
|---|---|---|
| 1 | 掲示板で 3DS だけがマルチで弾かれ、投稿者は「マルチプレイの動作確認は Switch のみ」と明言している。つまり **Switch では動いた** | 中 |
| 2 | Switch 版の .text 全体に、3DS 版の判定の形 @@tst rX,#0x80000000@@ → @@movne rY,#0@@ が **1 つも無い**（0 件） | 中 |
| 3 | 3DS 版は「@@mov rX,#0@@ が 0x300 離れた 2 箇所」という形。Switch 版ではその形のペアが **0 組**（前後 3 命令一致の条件で） | 中 |
| 4 | 公開チートリストに 3DS 版の項目はあるが、**Switch 版の同種チートは見つからない** | 弱 |
| 5 | そもそも配信クエストは正規のゲーム機能で、改造クエストだけを弾く判定は 3DS 固有の事情（改造が広く普及していた）で入った可能性がある | 弱 |

弱い根拠も含みますが、**「Switch に無い」を支持する材料は複数あり、
「Switch にある」を支持する直接証拠は 1 つも無い**というのが現状です。

### 5.2 だから Switch 版のチートコードは作らない

根拠のないアドレスを書き換えると**ゲームが起動しなくなります**。
「たぶんここだろう」で実機に入れるべきではありません。

### 5.3 確かめ方（これで決着します）

**Switch 実機で、自作クエストをマルチプレイに貼ってみてください。**

```text
貼れた                      -> Switch 版に制限は無い。チートは不要。これで完了。
「クエストデータが正しくありません」 -> 制限が存在する。下の手順へ。
```

弾かれた場合の切り分け（重要）:

```text
(a) ソロで受注できるか
(b) ローカル通信の集会所で自分がホストとして貼れるか
(c) インターネット通信の集会所で貼れるか
(d) 他のプレイヤーが一覧で見られるか / 受注できるか
```

**(d) が見えない場合は「制限」ではなく「同期対象外」**です。その場合に直すべきは
送信側ではなくクエスト一覧の生成側になり、探す場所がまったく変わります。

## 6. 実機用チートファイルの書き方（3DS / Luma3DS）

```text
SD:/luma/titles/0004000E00197100/cheats.txt

[Custom Quest Multiplayer Fix]
004518E8 E3A06001
00451BE8 E3A00001
```

- タイトル ID @@0004000E00197100@@ は **更新データ 1.4.0** のものです。
  本体（ベースゲーム）のコードは別バイナリなので、このアドレスでは効きません。
- Luma の設定で「ゲームのチートを有効にする」を ON にしてください。
- **オンラインで使うとチート行為になります。自己責任で。**
