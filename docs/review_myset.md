## 1. アイテムセット配列 — slot+0x17CF、24 枠 × 170 B

### 1.1 領域の確定

| 項目 | 値 | 根拠（実測） |
|---|---|---|
| 基点 | **slot+0x17CF** | アイテム BOX `0x278 + 5,463 (0x1557)` の直後と一致（`0x278+0x1557 = 0x17CF`） |
| レコード長 | **170 B (0xAA)** | 名称の開始位置が 0x17CF, 0x1879, 0x1923, 0x19CD, 0x1A77 … と 0xAA 間隔（実測 24 点） |
| 枠数 | **24** | 24×170 = 4,080 B で `0x17CF + 0xFF0 = 0x27BF` に着地し、**0x27BF からビットパックされた別データ（先頭 `09 a0 50 00 05 00 00 38`）が始まる**。24 枠目まで名称 `－－－` が正しく初期化されている＝ゲーム自身が 24 枠として初期化している。参照実装 `Constants.cs:39` も `//TOTAL_ITEM_SETS = 24` |
| 終端 | slot+0x27BF（排他） | 上記。ここを越えて書くとビットマップ領域を壊す |
| 総バイト | 4,080 B | 24 × 170 |

> **旧説との差**: `Offsets.cs:84` のコメント `ITEM_SET_OFFSET = 0x0EDE; //Size 1360 (8 of them each 170 bytes long)` は
> オフセットも件数も実データと一致しない。0x0EDE はアイテム BOX (0x278..0x17CE) の内部であり、
> 170 というレコード長だけが正しかった。**件数は 8 ではなく 24**（ゲームが 24 枠分の名称を初期化しているため、
> 8 枠説は成立しない）。同じ参照実装でも `Constants.cs:39` は `TOTAL_ITEM_SETS = 24` であり、
> `Offsets.cs` の "8 of them" は同一実装内の定数と矛盾している（実測は 24 側）。

### 1.2 レコード構造（確定）

| 項目 | オフセット | 型 | 実測値（slot0 #0 / #7） | 根拠 |
|---|---|---|---|---|
| 名称 | **+0x000** | UTF-8, NUL 終端（領域 32 B） | `剣士(汎用)`（14 B） / `炭鉱`（6 B） | 全 24 枠が UTF-8 として解釈可能。未使用枠は `－－－`(EF BC 8D ×3, 9 B) |
| 予約 | **+0x020..+0x029** | 10 B | 全 72 レコード（24×3 スロット）で **全 0** | 非 0 は 1 件も無し。書かない |
| アイテム列 | **+0x02A..+0x0A9** | **32 × (u16 id, u16 個数) = 128 B** | #0: 16 件 / #7: 23 件。空きは (0,0) | 42 + 128 = 170 で過不足ゼロ。全 117 個の非空ペアが `1 ≤ id ≤ 2990`・`1 ≤ count ≤ 99` に収まる（不正 0 件）。**32 はポーチのスロット数と一致**（参照実装 `Constants.cs:40 INVENTORY_ITEM_SLOTS = 32`、`:43 SIZEOF_ITEMPOUCH = 72` = 32 × 18 bit） |

**ペアの並びは (id, 個数) の順で確定**。理由:

1. slot0 #0 と #7 の先頭 15 ペアが同じ並び（9,10 / 10,10 / 28,2 / 29,1 / 31,3 / 32,2 / 40,1 / 41,1 / 42,1 / 56,20 / 70,99 / 71,5 / 73,8 / 83,1 / 84,1）で、
   第 1 要素は **昇順**、第 2 要素は 1..99 の「個数」に見える。逆順（個数, id）で読むと第 1 要素が 10,10,5,2,1,3,… と昇順にならない。
2. 第 1 要素をアイテム名表で引くと、**狩猟用ロードアウトとして整合する**（下記 1.3）。
3. 装備 ID としては小さすぎる（装備は種類 + id で 900〜1900 帯、しかも種類コードが無い）。

→ **装備セットではない**。装備に関する値（装備 BOX 添字・装備 ID・カラー）は 170 B のどこにも存在しない。

### 1.4 未使用枠の判定

| 判定 | 内容 | 実測 |
|---|---|---|
| 名称 | `－－－`（EF BC 8D ×3 + NUL） | 22/24 枠（slot0） |
| 中身 | 名称以降すべて 0（+0x09..+0xA9） | **24×3 = 72 レコード中 66 件がこの正準形に完全一致**（残り 6 件＝使用中 2 枠×3 スロット） |

→ アイテムセットは **「名称が `－－－` かつ中身が全 0」= 未使用**。名称だけ／中身だけで判定しても本セーブでは一致する。
（ゲームは名称を強制的に `－－－` で初期化するので、**全 0 の空レコードは存在しない**点に注意。

### 1.5 名称フィールドの注意（実測）

slot0 #7「炭鉱」は NUL の後ろに **`83 88 30 38` というゴミ 4 B が残っている**（`+0x07..+0x0A`）。
UTF-8 として不正なバイト列で、**名称欄は NUL 終端だがゼロ埋めされない**ことを示す。
→ 書き込み時は「文字列 + NUL + 残りを 0 埋め」で上書きするのが安全（そのまま流用すると古い名前の尾が残る）。

### 2.3 「装備 BOX の添字」であることの証明（最重要）

* 装備 BOX（slot+0x62EE, 2000×36 B）は 36 B レコードで、`+0x00` の下位 5 bit = 種類（1..5 防具、6 護石、7..21 武器）、
  `+0x02` = 装備 id、`+0x06/+0x08/+0x0A` = 装飾品 3 枠。
* セットの 7 個の u16 は、**すべて BOX 添字として読むと種類が期待順に並ぶ**:
  * 使用 29 件のうち **21 件が [武器(7..21), 頭(1), 胴(2), 腕(3), 腰(4), 脚(5), 護石(6)] に完全一致**。
  * 残り 8 件は「頭の位置だけ種類 6（護石）」で、他は完全一致（§2.5）。
* 装備 **ID** として読むと破綻する（防具 id は 900〜1,200 帯、BOX 添字は 18/40..44/230..234 のような小さい値）。
* さらに、**現在装備ブロック（slot+0x10C〜）と一致する**: セット #3「太刀」= 太刀 id108 Lv4 / 隼刃の羽飾り(頭 id611 Lv9) / レウスＸメイル /
  Ｓ・ソルＺアーム / ゴアXRフォールド / GXミラルーツフット / 護石（装飾品 2669）。
  現在装備ブロック（`+0x110 / +0x13C / +0x168 / +0x194 / +0x1C0 / +0x1EC / +0x218`、44 B 間隔）は
  **同じ 7 部位を同じ順序で**持ち、値も一致する（武器 head `0x808E` = 種類 14 太刀 Lv4、id 108 / 頭 `0x0121` = 頭 Lv9 id 611 …）。
  → セットの 7 個が「部位順の BOX 添字」であることが独立に裏付けられる。
* 装飾品 7 組も BOX 側レコードの装飾品フィールドと一致（定期更新されるセットは 7/7 一致）。
  古いセットでは**登録時のスナップショットが残る**ため一致しないことがある（slot1/2 の多くのセット）→ 装飾品は「コピー」であり、書き換え時は BOX 側と揃えるのが望ましい。

### 2.5 例外: 「頭」スロットに護石が入っている 8 件（実測）

| セット | 頭スロットの BOX 添字 | その BOX レコードの種類 | 本来の護石欄 |
|---|---|---|---|
| slot0 #7 ヘビィ / #8 ライト | **1428**（共通） | kind 6 = 護石（Lv0, id 10, スキル 12/+7・30/+13, 3 スロット） | 1459 / 1447 |
| slot1・2 #5 片手剣 / #7 ヘビィ / #8 ライト | **349**（共通） | kind 6 = 護石 | 309 / 281 / 269 |

* 8 件すべてで「他の 4 部位（胴・腕・腰・脚）は正常」で、**頭の位置だけ種類 6**。
* 同じスロット内では**同じ添字**（slot0 は 1428、slot1/2 は 349）を指す。
* 該当セットの装飾品 3 連（頭の組）も、現在の BOX レコードの装飾品（0,0,0 等）と一致する＝
  データ自体は「その添字のレコード」と整合している。

**推測（未確定）**: セットは BOX 添字を保持するだけなので、**登録後に頭装備を売却/移動し、空いた BOX 枠が
護石（鑑定で追加される）に再利用された**結果、参照が別物を指したまま残った、と考えるのが最も自然。
同一スロット内の複数セットが同じ添字を指すのは「同じ頭装備を共有していた」ことと整合する。
ただし「ゲーム側が頭装備なしを 0xFFFF ではなく護石添字で書いた」可能性も否定できない（U4 の検証方法参照）。

→ **エディタは参照先レコードの種類を必ず検証し、種類が部位と合わないセットは『壊れたセット』として警告表示**すべき。

### 2.6 未使用枠の判定（強いマーカーあり）

| 判定材料 | 値 | 実測 |
|---|---|---|
| 名称 | `－－－` | 91/91 の未使用レコードで一致 |
| 装備 7 欄 | **+0x02A..+0x037 が 0xFF×14（= 0xFFFF ×7）** | 91/91 で一致。**「装備なし」の表現は 0xFFFF** |
| 残り | +0x009..+0x029 が 0、+0x038..+0x07C が 0、**+0x07D..+0x081 = 01×5、+0x082 = 0x06**、+0x083.. が 0 | 91/91 がこの正準形に**完全一致** |

```
未使用レコードの生バイト（slot0 #9、file 0x146D66+9*0x88）
+000 ef bc 8d ef bc 8d ef bc 8d 00 ... 00      "－－－"
+02A ff ff ff ff ff ff ff ff ff ff ff ff ff ff  装備 7 欄 = 0xFFFF
+038 00 ... 00 (〜+0x7C)
+07D 01 01 01 01 01 06 00 00 00 00 00           部位フラグらしき固定値
```

→ 未使用判定は「名称 = `－－－` **かつ** +0x02A..+0x037 = 0xFFFF×7」の二重チェックが最も安全。
**注意**: 使用中レコードでも 0x2A..0x37 の一部が 0xFFFF になる可能性が残る（本セーブでは該当なし）ので、
「0xFFFF = 装備なし部位」として個別に扱うのが正しい。

## 3. 0x21E0E の 24 枠 × 68 B ブロック（正体不明）

| 項目 | 値 |
|---|---|
| 位置 | slot+0x21E0E .. 0x2246E（1,632 B = 24 × 68） |
| 構造 | 名称 32 B（`－－－`）+ +0x020..+0x029 の 0（10 B）+ **+0x02A..+0x02F = FF×6** + **+0x030..+0x032 = 01 01 01** + 残り 0 |
| 実測 | **3 スロット × 24 = 72 レコードすべてが同一の「空」パターン（72/72 完全一致）**。使用例が 1 件も無い |
| 解釈候補（推測） | 68 = 名称 32 + 36 と、ちょうど装備 BOX 1 レコード分のデータ長。装備セットの別系統（例: 護石セット・履歴）の可能性があるが、**使用例ゼロのため断定不能** |
| 扱い | **読むだけ／書かない**。装備セットの配列（40 枠）と混同すると 136↔68 の取り違えで全データを破壊する |

旧レポートの「装備マイセット 52 × 136 B」は、40 枠 + この 68 B ブロック 24 枠を 136 B で読んだもの。
**0x208CE + 40×136 = 0x21E0E が真の境界**（実測）。

## 4. 両者の対応関係（1 セットに名前+中身が揃う構造か）

| 観点 | アイテムセット (0x17CF) | 装備マイセット (0x208CE) |
|---|---|---|
| 枠数 | 24 | 40 |
| レコード長 | 170 B | 136 B |
| 中身 | 32×(アイテム id, 個数) | 装備 BOX 添字 7 個 + 装飾品 7 組 + 色 5 個 |
| 相手を参照する欄 | **無し** | **無し** |
| 名前 | 自由（実測 `剣士(汎用)` `炭鉱`） | 自由（実測 `大剣` `太刀` `セット10`） |

* **完全に独立した 2 機能**。同一番号どうしに意味は無い（枠数が違うので 1:1 対応も不可能）。
* MHXX のゲーム内でも「アイテム BOX のアイテムセット」と「装備メニューのマイセット」は別物として扱われる。
  本セーブの実測（一方にしか無いフィールド）と整合する。
* 配信アイテムセット（0xCD940 付近）は `MHXX` マジック + UTF-8 名 + 別形式のアイテム列という**第 3 の構造**で、
  24 枠配列とは無関係（実測。混同禁止）。

## 6. 書き換えるときの安全な範囲

共通の前提:

* body（36 B ヘッダ以降）に**内容チェックサムは無い**（36 B ヘッダの +0x14 はファイル名 CRC、+0x1C は本体長のみ。
  `crc.rs` / `review_hunt_records.md` §10.1 の既存結論と同じ）。長さを変えなければチェックサム再計算は不要。
* 書き込み対象は必ず **36 + slot_base + 相対** で解決し、**配列境界を越えない**。

### 6.1 アイテムセット

| 書いてよい | 範囲 | 規則 |
|---|---|---|
| 名称 | `0x17CF + i*170 + 0x00 .. +0x1F` | UTF-8、最大 31 B + NUL。**残りは 0 埋め**（元のゴミを残さない） |
| アイテム | `0x17CF + i*170 + 0x2A .. +0xA9` | 32 × (u16 id, u16 個数)。`1 ≤ id ≤ 2990`、`1 ≤ 個数 ≤ 99`。空きは (0,0) |
| 書かない | `+0x20 .. +0x29` | 全 72 レコードで 0。意味不明の予約 |
| 触れてはいけない | `0x17CF + 24*170 = 0x27BF` 以降 | ビットパックされた別データ |

### 6.2 装備マイセット

| 書いてよい | 範囲 | 規則 |
|---|---|---|
| 名称 | `0x208CE + i*136 + 0x00 .. +0x1F` | 同上（0 埋め） |
| 装備 7 欄 | `+0x2A .. +0x37` | u16 ×7 = [武器, 頭, 胴, 腕, 腰, 脚, 護石]。**装備 BOX 添字 0..1999**、無しは `0xFFFF`。**種類の検証必須**（武器=7..21、頭=1、胴=2、腕=3、腰=4、脚=5、護石=6） |
| 装飾品 | `+0x38 .. +0x61` | 7 組 × (u16, u16, u16) を [武器, 頭, 胴, 腕, 腰, 脚, 護石] の順に。値は装飾品のアイテム id（2,667〜2,870 帯）または 0 |
| 防具カラー | `+0x64 .. +0x77` | 5 × RGBA u32（頭, 胴, 腕, 腰, 脚 と推測。現在装備ブロック +0x24C と同値） |
| 書かない | `+0x20..0x29`, `+0x62..0x63`, `+0x78..0x87` | 予約・不明。0x78.. は値の分布が一定せず意味不明 |
| 触れてはいけない | `0x208CE + 40*136 = 0x21E0E` 以降（68 B ブロック、意味不明） | — |

### 6.3 追加の安全則（実測から導けるもの）

1. **セットの BOX 添字を書いたら、同じ位置の装飾品 3 連も BOX 側レコードの +0x06/+0x08/+0x0A で上書きする**（一貫性）。
2. 部位の種類が合わない添字（例: 頭に護石）を**書かない**。読むときは警告。
3. 未使用枠を作るなら、**名称 `－－－` + 装備 7 欄 0xFFFF**（装備セット）、
   **名称 `－－－` + アイテム全 0**（アイテムセット）で「正準形」を再現する。
4. 3 スロットを一括で扱う場合、**slot1 と slot2 は同一内容**なので、片方だけ書き換えると差分が残る（意図した編集か確認する）。

## 8. 実装提案

### 8.1 コア（`crates/mhnx-core`）

```rust
// src/itemset.rs
pub const ITEM_SET_OFFSET: usize = 0x17CF;
pub const ITEM_SET_COUNT: usize = 24;
pub const ITEM_SET_RECORD: usize = 170;
pub const ITEM_SET_NAME: usize = 0x20;   // 32
pub const ITEM_SET_SLOTS: usize = 32;
pub const ITEM_SET_ITEMS: usize = 0x2A;  // 32 * (u16 id, u16 count)

// src/equipset.rs
pub const EQUIP_SET_OFFSET: usize = 0x208CE;
pub const EQUIP_SET_COUNT: usize = 40;   // ★52 ではない
pub const EQUIP_SET_RECORD: usize = 136;
pub const EQUIP_SET_NAME: usize = 0x20;
pub const EQUIP_SET_REFS: usize = 0x2A;  // u16 x7: 武器,頭,胴,腕,腰,脚,護石
pub const EQUIP_SET_DECOS: usize = 0x38; // 7 x (u16 x3)
pub const EQUIP_SET_COLOR: usize = 0x64; // 5 x RGBA
```

* 読み出し時に必ず「装備 BOX の種類」で 7 欄を検証し、`kind` が期待と違う場合は
  `SetIssue::KindMismatch{slot, expected, actual}` を返す（§2.5 の 8 件を正しく報告できる）。
* 書き込み API は「名称・アイテム 32 枠・装備 7 添字 + 装飾品・色」だけを受け付け、
  予約/不明フィールドは**元のバイトを保持**する（`charm.rs` の「触らない」方針を踏襲）。

### 8.2 CLI（`mhnx.exe`）

```
mhnx mysets <system> [slot]      # アイテムセット + 装備マイセットを両方表示（--json 可）
```

表示例:

```
[itemsets] 24 slots (0x17CF, 170B) — slot0: 2 used
  # 0  剣士(汎用)  16/32 items
       回復薬 x10 / 回復薬グレート x10 / 秘薬 x2 / ...
  # 7  炭鉱        23/32 items
[equipsets] 40 slots (0x208CE, 136B) — slot0: 9 used

  # 7  ヘビィ 王牙砲【震雷】 Lv2 / ★頭=護石(1428) ← 部位不一致
```

### 8.3 テスト

* **正準形テスト**: 未使用レコードが「名称 －－－ + 0x2A..0x37 = 0xFFFF×7 + 0x7D.. = 01×5,06」に一致することを
  3 スロット × 91 件で assert（本セーブで 91/91 一致を確認済み）。
* **境界テスト**: `0x17CF + 24*170 == 0x27BF`、`0x208CE + 40*136 == 0x21E0E`、
  `0x21E0E + 24*68 == 0x2246E` を定数で assert（読み取り位置の回帰検出器になる）。
* **整合性テスト（緩め）**: 使用中セットの装備 7 欄が 2000 未満、かつ武器 kind が 7..21。護石欄が kind 6。
* **装飾品ミラー**: 更新直後のセットは BOX 側の装飾品と一致することを assert（古いセットは除外）。

### 8.4 やらないほうがよいこと

* `Offsets.cs` の `0x0EDE`（アイテムセット）と `0x1B8A`（勲章）を流用する — 前者はアイテム BOX 内部、
  後者は本配列の内部（既存レポートで実証済み）。
* 0x21E0E の 68 B ブロックを 136 B として読む／書く（旧レポートの 52 枠説の原因）。
* 配置の不明な末尾 16 B（+0x78..+0x87）と +0x62 をゼロ埋めする（意味のある値が入っている可能性）。
