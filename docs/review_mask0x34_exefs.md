## 1. 分かったこと

### 1.1 3DS 側の一次実装がオフセットに名前を与えている（前提の修正）

本ワークスペースには MHXX/MHX の 3DS 用セーブツールの**ソース**が入っている
（`nx\mhxx\save_editor\mhxx_quetool\3DSに入れるもの\mhxx_data_manager\source\quest.c`,
Seth VanHeulen 作 / GPL / 3DS ホームブリュー）。ここに DLC セクションのレイアウトが `#define` で明記されている:

```c
#define QUEST_SIZE          0x1400
#define QUEST_OFFSET        0x45D4     /* MHX  */
#define XX_QUEST_OFFSET     0x45F4     /* MHXX */
#define INSTALLED_OFFSET    0x34       /* MHX  : 導入済みマスク 20 B */
#define XX_INSTALLED_OFFSET 0x4C       /* MHXX : 導入済みマスク 28 B */
#define EQUIP_SIZE          0x800
#define EQUIP_OFFSET        0xB35D4    /* MHX  */
#define XX_EQUIP_OFFSET     0x1049F4   /* MHXX */
```

同ファイルは導入マスクを書くとき `installed_bits[7] = {0xFFFFFFFF, ...}` を
`size = 20`（MHX）/ `size = 28`（MHXX）バイトだけ書く。つまり

* **`+0x4C`（28 B, 224 bit）は「導入済みクエスト」のビットマスク**（3DS 実装の命名）
* **`+0x34` は MHX の導入済みマスクの位置**。MHXX では**別の 24 バイト**が入っている

本プロジェクトの `dlc_layout.md` の `+0x4C` の解釈は 3DS 実装と一致している。
`+0x34` は「MHX のマスクが入っていた場所に MHXX が入れた新しい値」である。

### 1.2 MHXX の `+0x34..+0x67` は MHX の同じ 52 バイトの並べ替え（算術で確定）

上の `#define` から、ヘッダ末尾とクエスト配列先頭の距離を両機種で計算すると**完全に一致**する:

| 項目 | MHX | MHXX |
|---|---|---|
| 導入済みマスク | `0x34` .. `0x47`（20 B） | `0x4C` .. `0x67`（28 B） |
| マスク終端 → クエスト配列 | `0x45D4 - 0x48` = **0x458C** | `0x45F4 - 0x68` = **0x458C** |
| マスク開始の移動量 | — | `0x4C - 0x34` = **+0x18**（24） |
| マスク長の増加 | — | 20 → 28 = **+8** |
| クエスト配列の移動量 | — | `0x45F4 - 0x45D4` = **+0x20** = 24 + 8 ✔ |
| 装備配列の移動量 | — | `0x1049F4 - 0xB35D4` = **0x51420** = `205*0x1400 - 140*0x1400 + 0x20` ✔ |

**読み取れること（事実）**: DLC ヘッダは両機種とも `+0x00..+0x67` の 0x68 バイトで、
`+0x34..+0x67` の 52 バイトが「DLC 状態領域」。MHX はその 52 B を
「マスク 20 B + 未知 32 B」に、MHXX は「未知 24 B + マスク 28 B」に割り当てた。
マスクが 8 バイト伸びた分は、末尾の未知領域から削られている。

⇒ **「`+0x34` から 24 バイト」は「MHX のマスク位置」でも「任意の切れ目」でもなく、
MHXX が 52 バイト領域の先頭に置いた 24 バイト**、という位置づけになる。
前回レポートの「人為的な切れ目」という表現は半分当たり。左に 0x24 帯が続く点は変わらないが、
右端 `+0x4C` は**データ側ではなく構造上の境界**である可能性が高い（**推測**）。

### 1.3 exefs には DLC セクションの内部オフセットが存在しない（実測）

update main（展開後 0x186B03E、.text は VA `0x100`..`0x13E6618`）と base の全モジュールについて、
(a) 4 バイト境界の 32bit 語、(b) `movw`/`movt` の即値、の両方で探索した。

| 定数 | 意味 | main(update) | main(base) | sdk | subsdk0..4 |
|---|---|---|---|---|---|
| `0x45F4` | MHXX クエスト配列先頭 | **0 / 0** | **0 / 0** | 0 / 0 | 0 / 0 |
| `0x1049F4` | MHXX 装備配列先頭 | **0 / 0** | 0 / 0 | 0 / 0 | 0 / 0 |
| `0xB280` | DLC セクション先頭 | 0 / **1**（VA 0x1612268 = **.rodata**。コードではない） | 0 / 1（同様） | 0 / 0 | 0 / 0 |
| `0x11B1F4` | DLC セクション長 | 0 / 0 | 0 / 0 | 0 / 0 | 0 / 0 |
| `0x126474` / `0x244C34` / `0x3633F4` | キャラ枠先頭 | 0 / 0 | 0 / 0 | 0 / 0 | 0 / 0 |

（表の「語 / movw」= 32bit 語の一致数 / movw 即値の一致数）

補足:
* `movw #0x49F4` の 3 件（`0xC0128C` ほか）は**別物**。逆アセンブルすると
  `0x4930, 0x4934, 0x4950, ..., 0x4A10 ...` と 0xC0 刻みでテーブルを埋めるループで、DLC とは無関係（実測）。
* `movt #0x0010` の 149 件、`movt #0x0012` の 14 件等はすべて `0x10xxxxxx` 系のアドレス即値で無関係。
* `0x45F4` は byte 列 `F4 45 00 00` としても 0 件。
* **`0x481D88`（セーブボディ長）だけは大量に存在する**（main(update) 42 movw + 37 movt、base main 44+36）。

**⇒ `+0x4C` マスクを読む命令から「同じ構造体の +0x34」へ降りる、という今回の手順は原理的に空振りする。**
固定オフセットでこのセクションを触っているコードが**無い**ため。

> 限界の明示: これは「固定即値として存在しない」ことの証明であって、
> 「このセクションを触るコードが無い」ことの証明ではない。ポインタ経由（構造体メンバ）で
> アクセスしている可能性は排除できない。

### 1.4 コードが持っているセーブ定数は「ボディ全体長 0x481D88」だけ（逆アセンブル）

update main の `0x481D88` は 33 箇所すべてが VA `0x3DBF2C`..`0x3E4684` の一帯（約 0x87KB）に集中し、
すべて `movw rX,#0x1D88` + `movt rX,#0x48` の対で作られる。代表例（VA `0x3DBEE0` の関数）:

```asm
3dbf2c  movw r8, #0x1d88          ; r8 = 0x481D88 = 4,726,152 = セーブボディ長
3dbf34  movt r8, #0x48
...
3dbf98  ldr  r3, [r0, #0x1c]
3dbf9c  mov  r0, r6               ; ファイルハンドル
3dbfa0  mov  r1, r8               ; ★サイズ = 0x481D88
3dbfa4  mov  r2, #0x10
3dbfa8  blx  r5                   ; 仮想関数（確保）
3dbfac  str  r0, [r4, #0x28]      ; this->mBuffer
3dbfb0  movw r1, #0x1d88
3dbfb4  movt r1, #0x48
3dbfb8  bl   #0x13e46e4           ; memset 系
3dbfe4  bl   #0x86c310            ; 読み込み
3dbfe8  bl   #0x86d870
3dbff0  bl   #0x86c218            ; 検証 → 戻り値
3dc000  str  r0, [r4, #0x1c]      ; this->mResultCode
```

**読み取れること（事実）**:
* セーブは **1 個の連続バッファ（0x481D88 = 0x481BB4 + 0x54。0x481BB4 は「キャラ枠 3 つ分の終端」と一致）**として読み込まれる。
  → セーブ全体は「1 枚のフラットな構造体」としてメモリに載る。
* 3DS のセーブボディ長（`quest.c` の `SYSTEM_SIZE 0x481D88`）と**まったく同じ値**。
  Switch 版のセーブは 36 バイトのヘッダを付けただけで、**ボディは 3DS と同一レイアウト**。
* ゲームは「ボディ先頭 + 0xB280 + 0x34」のような絶対オフセットで触れるはずだが、その即値は存在しない（1.3）。
  ⇒ セクションはヘッダのオフセット表（body+0x0C）経由で、しかも構造体メンバとしてアクセスされている、
  と考えるのが自然（**推測**）。

### 1.5 `+0x00..+0x67` の実測（取り直した値）

対象: `...\0000000000000001\0\system`（セクション基点 = `0x24 + u32le(body,0x0C)`、body `[0x0C]` = `0xB280`）

```text
+00  00 7a 00 00 00 00 00 00      +08  00 00 00 fc 00 00 00 00
+10  0f 00 00 00 ff ff 9d ff      +18  ff ff ff 7f 1a 00 00 00
+20  1f 00 00 00 f0 ff ff ff      +28  ff ff ef ff 07 fc ff ff
+30  ff ff ff ff ff ff ff ff      +38  ff 7f 80 07 ff ff ff ff
+40  ff ff ff 1f 00 00 00 00      +48  00 00 00 00 ff ff ff fd
+50  ff 01 00 00 fd ff e7 df      +58  77 fb ff 7f fd ef b7 f7
+60  ff bf ff ff bf 7f 7f 00
```

| 範囲 | 長さ | 立っているビット | ゼロの位置（その範囲内） | 前回資料との関係 |
|---|---|---|---|---|
| `+0x14`..`+0x1B` | 8 B (64) | **60** | 17, 21, 22, 63 | 既知（非ゼロ 9 B の一部） |
| `+0x24`..`+0x33` | 16 B (128) | **116** | 0,1,2,3, 52, 67,68,69,70,71,72,73 | 前回「左境界が無い」帯の前半 |
| **`+0x34`..`+0x43`** | 16 B (128) | **112** | **47..54, 59..63, 125,126,127** | 前回の「112 ビット」はここ |
| `+0x44`..`+0x4B` | 8 B | 0 | 全部 | 既知 |
| `+0x4C`..`+0x67` | 28 B (224) | **175** | （導入済みマスク） | 既知 |

**新しい事実**:
1. **`+0x24`..`+0x43` を 1 枚の 256 ビットマスクとして読むと 228 ビットが立ち、ゼロは 28 個だけ**。
   ゼロ位置は `0,1,2,3` / `52` / `67..73` / `175..182` / `187..191` / `253,254,255`。
2. 前半 16 B は 116/128、後半（= 従来の「+0x34 24 B」の先頭 16 B）は 112/128。
   **両方とも「ほぼ全部 1 で、一部だけ 0」**という形をしている。
   ⇒ これは「まれにしか立たない疎なフラグ」ではなく、**「カタログの大半が該当し、少数だけ欠けている」集合**。
   前回の「空きビット 47-54 / 59-63」は、この読み方では「8 連続 + 5 連続の欠け」= **カテゴリ境界のパディング**に見える（**推測**）。
3. 24 バイトで切ると 192 ビット中 112 が立ち、ゼロ 80 個のうち 64 個は `+0x44..+0x4B` の 8 バイト（= 24 B 枠の外縁）。
   実効的に「128 ビット中の 16 個のゼロ」しか情報がない。

### 1.6 テンプレートセーブでは DLC ヘッダが全ゼロ（定数ではない）

手元にある 8 本のセーブで `+0x00..+0x67` を比較した（**すべて読み取りのみ**）:

| セーブ | 出自 | DLC ヘッダ 0x68 B | `+0x4C` ビット | クエスト枠 |
|---|---|---|---|---|
| `...\0\system`（実セーブ） | Ryujinx の現行 | 1.5 のとおり | 175 | 175 |
| `save_backups\_conv\system` | 3DS→Switch 変換直後 | **実セーブと完全一致** | 175 | 175 |
| `save_editor\analysis\rt\as_3ds.sav` | 3DS 用テンプレート | **全ゼロ** | 0 | 0 |
| `...\analysis\rt\demo\system` | 同上 | 全ゼロ | 0 | 0 |
| `...\back_to_switch.sav` / `switch_edited.sav` / `demo\SWITCH\system` / `READY_switch\system` | 変換ツール生成物 | 全ゼロ | 0 | 0 |

**読み取れること（事実）**:
* DLC ヘッダは**定数ではなく中身に応じて入る値**。空なら全ゼロ。
* **変換ツールはこのヘッダを一切加工していない**（`_conv` と現行がバイト一致）。
  ⇒ 現行セーブの `+0x24..+0x43` の値は **3DS 側で書かれたものがそのまま持ち込まれた**もの。
* したがって「クエストを 166→175 に増やしても `+0x34` が変わらない」という観測は、
  **「この領域を書いたのは（少なくとも最近は）3DS 側だけ」**という説明とも整合する（**推測**）。

### 1.7 セーブのボディヘッダは全セーブで同一（固定テンプレート）

8 本すべてで body `+0x00..+0x1F` が完全一致:

```text
c6000000 01000000 1c000000 80b20000 74641200 344c2400 f4333600 1f000000
```

* `+0x04..+0x06` = `01 01 01` = キャラ 3 スロット使用（3DS セーブエディタの
  `FIRST/SECOND/THIRD_CHAR_SLOT_USED` と一致）
* `+0x0C` = `0xB280`（DLC セクション先頭）, `+0x10/0x14/0x18` = キャラ枠先頭
* **この表はコードに即値として存在しない**（1.3）のに、全セーブで同じ値。
  ⇒ 一度どこかで書かれたテンプレートが引き継がれている。**ツールは絶対に触らない**のが正しい。

## 2. 根拠（手法と再現）

* 逆アセンブル: capstone 5.0.7 / `CS_ARCH_ARM, CS_MODE_ARM|LITTLE_ENDIAN`、**VA = ファイルオフセット + 0x100**
  （`mp_ghidra.md` §2.1 の規約を再確認。展開イメージ先頭 0x100 が MOD0 ヘッダ）
* 定数探索: 画像全体を u32 配列にして (a) 完全一致、(b) `movw`（`(w & 0x0FF00000)==0x03000000`）と
  `movt`（`==0x03400000`）の imm16 展開、の 2 系統。.text は VA `0x100`..`0x13E6618` に限定して判定。
* セクション参照の連鎖探索: `ldr rX,[rY,#0xc]`（25,857 箇所）→ 直後 26 命令内の `add rA,rY,rX` →
  その `rA` に対するメモリ参照（変位 `0x24/0x2c/0x34/0x3c/0x44/0x4c/0x54/0x5c/0x64`）を全数追跡。
  ヒット 35 件はすべて別構造体（配列インデックスや負変位 `[rX,#-0xc]`）で、セーブの DLC とは無関係と確認。
* ビット配列操作の全数抽出: `and rX,rY,#7` + `lsl` + `orr/bic` の系列 1,357 → 11 件に絞り、
  `and #0x1F` 系列（1,178）も確認。いずれもセーブの `+0x4C` を指すものは無し
  （`+0x100/+0x200/+0x224/+0x500` 等の別配列だった）。
* セーブ実測: Python で生バイトを直接読み（`struct.unpack_from`）、CLI は使っていない。

## 3. 前回レポートの方法論的修正（重要）

前回 `review_mask_0x34.md` §3 の表のうち、**次の 3 行は「否定」として使えない**（自明一致）。

| # | 内容 | 問題 |
|---|---|---|
| A1 | ビット i = クエスト枠 i | 実測ビットがすべて 0..124 にあり、枠 0..124 は全部使用中 → **恒真** |
| A3 | i 番目の導入クエスト（枠順） | 予測集合が 0..174。実測 112 ビットはすべて 0..124 ⊂ 0..174 → **必ず 112 一致**。`余剰 0` はその帰結 |
| A4 | i 番目の導入クエスト（ID 順） | 同上 |

前回の「偶然期待 102.1 に対し 112」という比較は、この 3 行では意味を持たない
（予測集合が実測を包んでしまうため）。**実際に反証として有効なのは
A2 / A6 / A7 / A10 / A11 / A12 / A13 / B / C / D / E / F / G / H / I**。

結論（＝導入状態ではない）自体は A6・A10・A11・A13・G・H で支えられているので変わらないが、
「20 パターン否定」のうち 3 つは数え直す必要がある。

また前回「ワード 3 が 29 ビット = 訓練 29 件」を「件数一致は証拠にしない」と棄却したのは正しい。
今回の 256 ビット読みでは、訓練 29 件に対応する位置（96..124）は**連続 29 ビット**であり、
他の境界（47..54 の 8 連続ゼロ等）とは形が違う。**この形の違いは手掛かりになりうる（推測）**。

## 4. 依頼された 5 項目への回答

### Q1. `+0x4C` を読む箇所から逆引きして、同じ構造体の `+0x34`/`+0x24` 付近へアクセスする命令を洗い出せたか

**洗い出せなかった。** 理由は「見つからなかった」ではなく **「その手順の前提が崩れている」**:

* `+0x4C` は固定変位としてコードに存在しない（`0x4C` という即値自体は 51,262 箇所にあるが、
  すべて他の構造体。連鎖探索で DLC セクションに到達するものは 0 件）。
* このセクションの**内部オフセットは 1 つもコードに無い**（§1.3）。コードが持つのは
  `0x481D88`（ボディ全体長）だけで、これは「丸ごと読む」ためのサイズ。

### Q2. `+0x24..+0x43` に相当するフィールドは何として使われているか

**不明。** 分かったのは形だけ:

* 32 バイト = **256 ビットで 228 ビットが立ち、ゼロは 28 個**（§1.5）。
* ゼロは `0..3`（先頭 4）、`52`（単独）、`67..73`（7 連続）、`175..182`（8 連続）、
  `187..191`（5 連続）、`253..255`（末尾 3）。
* 「8 連続ゼロ」「5 連続ゼロ」は**カテゴリ間パディング**の形（**推測**）。
  この読み方だと有効域は `0..46` / `55..58` / `64..124` の 3 ブロック（47 + 4 + 61 = 112）。
* 24 バイト枠（`+0x34`）で切ると「128 ビット中 112」で、ゼロは 47..54 / 59..63 / 125..127 の 16 個。

### Q3. 書き込み側はあるか（ゲームが管理する値か、読み取り専用の定数か）

* **定数ではない**（事実）: テンプレートセーブでは全ゼロ、実セーブでは非ゼロ（§1.6）。
* **exefs に書き込みコードを示す固定オフセットは無い**（事実）。
* **誰が書いたか**: 値は 3DS→Switch 変換でそのまま持ち込まれており（`_conv` と実セーブがバイト一致）、
  **Switch 版が書いた証拠は得られていない**。3DS 版（または 3DS 用ツール）が書いた、と考えるのが最も素直（**推測**）。
* 結論: **「ゲームが管理する値」と断定できない。少なくとも Switch 版 main は、この領域を
  固定オフセットでは一切読み書きしていない。** ツール側は従来どおり「触らない」が正しい。

### Q4. 購入状態・配信フラグ・受信済みフラグの候補と照合

* **購入状態**: 不成立。Switch 版の DLC 購入状態は eショップ側（`nn::ec`）の管理で、
  セーブに置く必然性が無い。exefs に `cDLCItemPackInfo` / `cDLCOtomoInfo` / `cDLCUpdateInfo`
  というクラス名（`0x1545E11` 付近）と `MtNetLocalTitleStorage\...` のパス群はあるが、
  これは**配信情報の取得（HTTP）側のクラス**で、セーブのビットマスクではない（実測: 文字列のみ、参照 0）。
* **配信フラグ**: 配信は全プレイヤー共通（サーバ側）なので、192/256 ビットの個人セーブに持つ理由が薄い。
* **受信済みフラグ**: `+0x4C`（175 ビット）がそれに相当する（3DS 実装の命名 = INSTALLED）。
  同じ意味の 2 枚目のマスクを `+0x24` に置く理由が説明できない。
* **残る候補（推測、証拠なし）**: 「クリア状況」「受注履歴」「配布物の受領履歴」。
  いずれも 1.5 の「ほぼ満杯（228/256）」という性質とは整合する（＝ 大半が該当、少数だけ未該当）。

### Q5. 同じ情報が romfs やセーブの他の場所に無いか

* **romfs には無い**: `base_romfs` の下は `nativeNX` だけで、`eventQuestList.bin` /
  `challengeQuestList.bin` は**ファイルとして存在しない**（文字列 `0x1546441` / `0x1546454` のみ）。
  → DLC クエスト一覧は**ダウンロードしてセーブに格納する方式**（`quest.c` の想定と一致）。
  カタログ順（＝マスクの索引順）を romfs から復元する道は閉じている。
* **セーブ内の他の場所**: DLC セクション以外に同じビット列は無い
  （8 本のセーブで `+0x34` の 16 バイト列を検索 → ヒットは当該位置のみ）。
* **メモリダンプ**: `nx\mhxx\scan\*.bin`（520MB × 4、2026-10-17）を
  `FF FF FF FF FF 7F 80 07 FF FF FF FF FF FF FF 1F` で検索 → **0 件**。
  この時点のダンプにはセーブの DLC セクションが載っていない（セーブ未ロード or 別状態）。
  **動的解析は未実施のまま。**

## 6. 実装への提案（`crates/mhnx-core/src/dlc.rs`）

1. **書き込み禁止域を 40 バイトに広げる**: 現在 `+0x34` を触らない方針だが、実体は
   `+0x24..+0x4B`（32 B の帯 + 8 B のゼロ）で連続している。
   **`+0x00..+0x4B` を不変条件として assert** する（書き込み対象は `+0x4C..+0x67` だけ）。
2. **ボディヘッダ `+0x00..+0x1F` も不変条件に含める**（全セーブで同一テンプレート = §1.7）。
   セクション丸ごとコピー機能を作る場合も、ヘッダはコピーせず保持する。
3. **`+0x24..+0x43` を 1 つの名前付き不透明領域として文書化**する
   （`+0x34` 起点の 24 バイトという表現は誤解を生む。少なくとも 16 B + 8 B に割らない）。
4. 回帰テストを 3 本追加:
   (a) 任意の編集操作の前後で `+0x00..+0x4B` がバイト一致、
   (b) ボディ長が `0x481D88` のまま、
   (c) `dlc_section_offset()` が `0xB280` のまま。
5. **調査用の診断コマンド**（`mhnx save-info dlc-header`）を追加し、`+0x00..+0x67` の 0x68 バイトと
   各マスクのビット数・ゼロ位置を表示する。今後の差分実験の前提になる。
