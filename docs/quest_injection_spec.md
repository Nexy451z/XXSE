# 改造クエストを Switch で使うための仕様

MHXX の改造クエスト導入について、MHX Data Manager（svanheulen 作の 3DS ホームブリュー）の
ソースコードと、日本語の解説記事を突き合わせて仕様を確定させたものです。

参考:
- MHX Data Manager: https://gitlab.com/svanheulen/mhx_data_manager (GPLv3)
- 解説記事「MHXX/GU Custom Quest Hack」: https://pkrg.blog.fc2.com/blog-entry-96.html

---

## 1. まず「MHXXSaveDataManager」について

その名前のツールは存在しません。該当するのは次の 2 つです。

| 名前 | 正体 |
|---|---|
| **MHX Data Manager** | svanheulen 作。3DS ホームブリュー。**セーブへのクエスト注入・吸出し**、キャラの地域間コピー、バックアップ |
| **mhxx data manager** | 上の記事で配布されている MHXX 版。やはり 3DS 側で動作する |

どちらも 3DS のホームブリューで、PC 用ではありません。

---

## 2. 最重要: 3DS の MHXX セーブは「SDカードの追加データ」にある

これが「JKSM などで機能しないことがある」原因です。

Capcom の公式マニュアルに明記されています。

```text
モンスターハンターダブルクロスは【SDカードの追加データ】に
全てのセーブデータが保存されます。
```

MHX Data Manager のソースもこれを裏づけます。引数が savedata ではなく **extdata** です。

```c
int select_game(const char* description, const char* info,
                FS_Archive* extdata, Handle* system, int allow_write) {
    int path_data[3] = {MEDIATYPE_SD, 0x1554, 0};   // MHX JPN の extdata ID
    FS_Path path = {PATH_BINARY, 0xC, (char*) path_data};
    FSUSER_OpenArchive(extdata, ARCHIVE_EXTDATA, path);
    FSUSER_OpenFile(system, *extdata,
                    fsMakePath(PATH_ASCII, "/system"),
                    allow_write ? FS_OPEN_WRITE : FS_OPEN_READ, 0);
}
```

つまり 3DS 側のセーブはここにあります。

```text
/extdata/00000000/<extdata ID>/system
```

| ゲーム | extdata ID |
|---|---|
| MHX (JPN) | 0x1554 |
| MHGen (EUR) | 0x185B |
| MHGen (USA) | 0x1870 |

**JKSM には「セーブデータ」と「追加データ（ExtData）」の 2 つのモードがあります。**
MHXX のセーブは後者なので、セーブデータ側を Export しても中身が入っていません。
これが「機能しないことがある」の正体です。

Checkpoint など ExtData に対応したツールを使うか、JKSM の ExtData モードを選ぶ必要があります。

### Switch では違う

Switch 版は通常のセーブ領域に置かれます。

```text
bis/user/save/0000000000000001/0/system          本体
bis/user/save/0000000000000001/0/system_backup   予備
```

**つまり Switch では JKSM のようなツールは不要**です。ファイルを直接書けます。
我々の mhnxeditor がやっているのはこれです。

## 3. クエストデータの構造

### 3.1 位置

```text
body + 0x0C                   u32  DLC セクションのオフセット (section)
section + 0x34                20 バイト   用途不明のビット列（MHX 互換ではない。112 bit が立つ）
section + 0x45D4              MHX のクエスト配列（140 スロット）
section + 0x4C                28 バイト   導入ビットマスク（MHXX、205 bit）
section + 0x45F4              MHXX のクエスト配列（205 スロット）
section + 0x1049F4            45 スロット x 0x800  クエスト装備
```

配列の終端がちょうど最初のキャラクタスロット **0x126474** に一致することで確認できます。

```text
0xB280 + 0x45F4 + 205 * 0x1400 + 45 * 0x800 = 0x126474   OK
```

**MHX と MHXX でオフセットが違います**（0x34 / 0x45D4 と 0x4C / 0x45F4）。
MHX の数値を MHXX のセーブに当てると意味のない値が出ます（実測で確認済み）。

### 3.2 1 レコードの形式

```text
+0x00  s32   クエスト ID（0 なら空きスロット）
+0x04  s32   データ長
+0x08  u8[]  arc の中身（データ長ぶん）
```

**自己記述型**なので、ID とサイズを読めば安全に走査できます。
実セーブの 175 件すべてが ARC マジックで始まり、サイズも上限内であることを確認しました。

MHX Data Manager は 1 レコードを 0x1400（小）と 0x1C00（大）の 2 通りで扱います。
MHXX の実セーブは 175 件すべて 0x1400 に収まっています（最大 3453 バイト）。

### 3.3 導入ビットマスク（スロット番号ではない）

section + 0x4C の 28 バイト（224 bit）が「導入済み」の一覧です。

**これはスロット番号で引く表ではありません。** 当初「ビット i = スロット i」と推測しましたが、
実セーブで反証されました。

決定的な証拠:

```text
クエスト配列のスロット数          205（0..204）
ビットが立っている最大位置        214
```

**ビット 205, 206, 208〜214 が立っています。** スロット 204 までしか無いので、
ビット番号がスロット番号であることはあり得ません。

一致数による反証:

```text
レコードのあるスロット   175
ビットが立っている数     175（うち 205 未満は 166）
両者の一致               140
```

一見 140 件も一致して「ほぼ対応している」ように見えますが、これは偶然です。
166 個のビットが 205 スロットに散らばるときの期待一致数は
166 x 175 / 205 = 141.7 で、140 以上一致する確率は 0.87 です。**証拠になりません。**

### 正しい解釈: カタログ番号で引く

ビットは**クエストのカタログ上の位置**を指します。

- ビット 0〜40 はクエスト装備のカタログ（45 件）と 41/41 で完全一致する
- 残りの 135 ビットは 135 件のイベントクエストと 1 対 1 で対応する
- 175 ビットと 175 レコードが過不足なく対応する

つまり**ビットは「どのクエストか」を表し、「どのスロットか」ではありません。**
スロット番号からビット番号を求めるにはカタログが要ります。

### 編集への影響

**すでに入っているクエストの差し替えは、ビットを一切触る必要がありません。**
そのクエストのビットは最初から立っているからです。

したがって本ツールは**ビットマスクを書き換えません**。
空きスロットへの新規追加は、必要なビットが分からないため拒否します。

## 4. 正しい導入手順（記事の方式）

記事にはっきり書かれています。

```text
b.クエストIDを整合させる
   フリーズするのはクエストのIDを変更した時
   ...
   置き換える予定の場所のIDを一致させないとフリーズ
```

**改造クエストは「新規追加」ではなく「既存スロットの上書き」**です。

```text
1. 既存の q<ID>.arc を取り出す
2. Quedixx で中身を編集する
3. 同じ ID のままセーブの同じスロットへ書き戻す
```

ID を変えるとフリーズします。gmd / sup / qdl が ID を参照しているためです。

### その他の制約（記事より）

| 項目 | 内容 |
|---|---|
| フィールドとモンスターの整合 | 出現位置とフィールドが合っていないと出現しない。千里眼の薬でフリーズ（Switch） |
| クエスト種類 | 大連続以外で複数モンスターを設定しても 1 匹目しか出ない |
| 1人限定の解除 | mib の +0x1A が 2F だと 1 人限定。Quedixx は保存時に書き戻すので、最後にバイナリエディタで直す |
| マルチプレイ | **改造クエストをマルチで遊べるのは Switch のみ**（3DS は不可） |

## 5. 我々の実装の修正点

この仕様と突き合わせて、mhnxeditor に次の修正を入れました。

### 5.1 ビットマスクの扱い（2 段階で修正）

第 1 段階では「導入時に 28 バイト全部を 0xFF にする」処理がありました。
224 個すべてが導入済みだとゲームに思わせるため危険でした。

第 2 段階でスロット単位の書き換えに直しましたが、**それも誤りでした**（3.3 節）。
レビューで「ビットはスロット番号ではない」ことが実証されたため、
**ビットマスクを一切書かない**方式に変更しました。

- 差し替えでは何も書かない（対象ビットは元から立っている）
- enable_all / clear_all / set_quest_bit / quest_bit は削除
- quest_bit に対応する読み取り専用の installed_bit_count だけ残した

### 5.2 同じ ID は上書きするようにした

以前は常に空きスロットを探して追加していました。
記事の方式に合わせ、**同じ ID が既にあればそのスロットを上書き**するようにしました。
スロットも ID も動かないので、フリーズの原因になりません。

### 5.2.1 空きスロットへの新規追加（2026/10 追記・実装済み）

この文書の初版では「空きスロットへの新規追加は拒否します」と書いていましたが、
**現在の実装は追加できます**。2026/10 にカタログ表を確定させたためです。

| 関数 | 役割 |
|---|---|
| `dlc::install_quest` | 既に一覧にある ID の中身を差し替える（従来どおり） |
| `dlc::add_quest` | 一覧に無い ID を空きスロットへ追加し、カタログビットも立てる |

- `bit_for_quest(id)` がカタログ上のビット位置を返します（例: 1010002 → 65、1111009 → 223）
- CLI は `mhnx add-quest <system> <in.arc> <out>` です（**入力セーブは書き換えません**）
- 実測: 実セーブで 175 → 189 件に増加、ビットも同時に立ちました

**ただし romfs のクエストはそのままでは入りません。** 33KB のうち約31KBは
`0x8000` までのゼロパディングで、実データは 1〜3KB です。
`mhnx arc-compact` でパディングを除去すると枠（5,112バイト）に収まります。
再圧縮は不要で、zlib のストリームはそのまま移動するだけです。

**入れても動かないクエストがあります。** romfs の 223 件のうち 34 件は
依頼内容が `Invalid Message`、成功条件が `dummy` の空雛形（予備枠）です。

### 5.3 お守りの新規作成キーを分けた

Y は「選択中のお守りを編集」、L は「空きスロットに新規作成」に分けました。
以前は一覧が空のときしか新規作成できませんでした。

### 5.4 明るさの範囲が狭すぎた（バグ）

0 から 31 で丸めていたため、実セーブの値 **48** が 31 に化けていました。
バイト全域（0 から 255）に広げました。

## 6. 実機での使い方（まとめ）

```text
1. mhnxeditor で q1010165.arc などを開く（.arc を開く）
2. 中身を編集して上書き保存
3. セーブを開き、クエストタブから「セーブに導入」
   -> すでに入っている同じ ID のスロットを上書きします（新規追加はできません）
4. 「Switch 用 (system 2 ファイル)」で書き出す
5. Ryujinx なら 0 と 1 の system / system_backup に配置
```

**3DS も JKSM も mhxx data manager も要りません。** Switch のセーブを直接書けます。

### 注意

- **必ずバックアップを取る**。改造クエストはフリーズ要因になり得ます
- **他人のセーブには入れない**。ID の不一致はフリーズの直接原因です
- **オンラインで使うのはチート行為**です。個人または同意した相手とのみ
- 1 人限定の解除は自己責任で（mhnx check / mhnx fix-oneplayer が使えます）
