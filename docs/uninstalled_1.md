## 2. 判定の根拠になった共通の実測事実

### 2.1 romfs の q*.arc は 0x8000 パディングで水増しされている【実測・重要】

依頼文の前提「romfs のファイルは 33 KB 前後なので、このままでは入らない／再圧縮が必要」は、
**実データの中身と合わない**。.arc を自前でパースして確認した結果は次のとおり。

* エントリテーブルは `12 + 80 * entryCount` バイト（アラインメント 32）。
* しかし **実データの開始オフセットは、例外なく 0x8000 = 32,768 バイト**。
* テーブル末尾から 0x8000 までの隙間 **約 31〜32 KB は全バイト 0**（q1010002 で 31,616 バイト中、非ゼロ 0 バイト）。

```
q1010002.arc  35,258 B の内訳（実測）
  ヘッダ        12 B
  エントリ表    14 x 80 = 1,120 B
  0 埋め         20 B（32 バイト境界合わせ）
  ─────────────────────────
  パディング   31,616 B  ← 全部 0
  実データ      2,490 B  ← zlib 圧縮済みの 14 エントリ
```

対象を広げて **romfs のクエスト .arc 1,903 ファイル**（arcs\village + arcs\event + arcs\uninstalled）を走査したところ、
**1,903/1,903 が「先頭データオフセット = 0x8000、隙間は全 0」**、ファイルサイズは 33,036〜35,924 B だった。
つまり 33 KB というサイズは romfs のアラインメント都合であって、クエストの実体ではない。

**実データは 1.0〜3.0 KB しかない。**（§5 で再構成して実測）

### 2.2 固定サイズのエントリは「量産データ」の証拠にならない【実測】

.arc のエントリ表にある 4 バイト値（`arc-list` が「hash」と表示する列）は
**内容ハッシュではなく型 ID**である。同じ拡張子なら中身が違っても同じ値になる。

| 表示 | 実体 | 全クエスト共通のサイズ |
|---|---|---|
| 0x2553701D | .sem の型 | 32 B |
| 0x32CA92F8 | .esl の型 | 可変（64〜1,400 B） |
| 0x5B3C302D | .rem の型 | 184 B |
| 0x54539AEE | .sup の型 | 168 B |
| 0x26BEC21C | .qdp の型 | 25 B |
| 0x00E0BB1C | .qdl の型 | 308 B |
| 0x242BB29A | .gmd の型 | 可変 |
| 0x1BBFD18E | .mib の型 | 249 B |

確認: 村クエスト q0010701.arc も、既配信イベント q1010101.arc も、.sem は 32 B、.rem は 184 B、.mib は 249 B。
**「33,786 バイトが複数ある」「.sem が全部 32 B」は量産データの証拠にならない。**
実際に量産かどうかは、エントリを**展開して中身を比較**して判断した（§4.1）。

### 2.3 .mib の quest_kind は mhnx のラベルが誤っている【実測】

`arc-mib` は quest_kind を「大連続 (3)」のように表示するが、これは**別の enum を当てている表示バグ**。
配信版 .arc 141 本で「quest_kind の生値」と「ターゲット種類 tt1」の同時分布を取ると次のとおり。

| kind 生値 | 件数 | 同時に現れた tt1 | 解釈 |
|---:|---:|---|---|
| 0 | 66 | 狩猟/討伐(1) 60 / 部位破壊(8) 6 | 狩猟 |
| 1 | 36 | 狩猟/討伐(1) 33 / 討伐合計(4) 3 | 討伐 |
| 2 | 1 | 捕獲(2) 1 | 捕獲 |
| 3 | 8 | 納品(5) 6 / RRP納品(6) 2 | 納品 |
| 4 | 4 | 狩猟/討伐(1) 3 / ネコタク(7) 1 | 連続狩猟 |
| 5 | 26 | 大連続(3) 25 / 狩猟/討伐(1) 1 | 大連続狩猟 |

したがって正しい並びは
`["狩猟","討伐","捕獲","納品","連続狩猟","大連続狩猟","不明"]`（7 項目）。
本レポートの「mib の quest_kind」列はこの解釈で書いた。
根拠の補強: q1010002 は生値 3 で成功条件が「竜の卵３個の納品」、q1010117 は生値 5 で 3 体の連続狩猟。
どちらも上の表と一致する。

| 項目 | 実測値 |

## 4. 特筆すべき発見

### 4.1 「同サイズ・同内容の量産データ」の実体【実測】

担当 12 件の中では、**q1010006 と q1010007 が完全な量産ペア**だった（§3.3）。
サイズ 33,786 B で一致するだけでなく、展開後の 9 エントリ中 7 エントリが**バイト完全一致**、残り 2 エントリの差も計 4 バイト。
「サイズが同じ」ではなく「中身が同じ」ことを確認したうえでの判定である。

一方、依頼文にあった 33,789 / 33,790 バイトの連番ファイル（q1011045〜q1011053 など）は**本担当の範囲外**（他担当分）。
本担当 12 件には、その手の同サイズ連番は 1010006 / 1010007 の 1 組しか無い。

### 4.2 mhnx の表示バグ（quest_kind）

`arc-mib` の quest_kind ラベルが誤っている（§2.3）。141 本で統計的に裏づけた。
ツールを直すなら `questfields.rs` の `quest_kind` の enum_name を 7 項目版に差し替える必要がある。
※ 本件は「データの性質」ではなく「表示」の問題なので、判定には影響しない（生値で判断した）。

### 4.3 カタログに載っている ≠ 配信された

* 1010007: カタログ外 → 一覧に出す枠が無い。**確定的に没データ**。
* 1010006: カタログ内（位置 196）だが中身は空の予備。
* 1010160: カタログ内（位置 108）だが中身は「未使用」でクエストとして動かない。

「カタログにあるから実クエスト」とは言えない、という反例が 2 件（1010006 / 1010160）取れた。
既存の解析メモ（`docs/review_catalogue.md` §4.3）は 1010160 を「実クエスト（配信版 .arc が無いだけ）」に分類しているが、
**中身を読む限りこれは誤り**だと考えた方がよい（少なくとも「実クエスト」と呼べる状態ではない）。

### 4.4 マップ ID とリソース名の整合性は強い判定材料になる【推測を含む】

正常な 9 件はすべて、`b_m<2桁>em...` と `z_m<2桁>d_...` の **2 桁の数字が .mib の map_id と一致**していた。

| 1010002 | 1 | 01 | 01 | ○ |

## 5. 導入可否

### 5.1 サイズ: 再圧縮は不要。「0x8000 パディングを外して再構築」すればよい【実測】

romfs の .arc からエントリを展開し、パディングを詰めて**自前で組み直した実測値**は次のとおり（zlib 再圧縮込み）。

| ID | romfs 実ファイル | 再構築後（パディング除去） | 枠上限 5,112 との余裕 |
|---|---:|---:|---:|
| 1010002 | 35,258 | **3,653** | 1,459 |
| 1010006 | 33,786 | **1,761** | 3,351 |
| 1010007 | 33,786 | **1,761** | 3,351 |
| 1010116 | 34,519 | **2,926** | 2,186 |
| 1010117 | 33,744 | **2,147** | 2,965 |
| 1010126 | 34,284 | **2,713** | 2,399 |
| 1010132 | 34,250 | **2,580** | 2,532 |
| 1010136 | 34,582 | **2,994** | 2,118 |
| 1010139 | 34,399 | **2,812** | 2,300 |
| 1010160 | 33,123 | **1,035** | 4,077 |
| 1010162 | 34,369 | **2,772** | 2,340 |
| 1010169 | 34,434 | **2,834** | 2,278 |

**12 件すべて 5,112 バイト以下**（最大 3,653 B = 上限の 71%）。
既存セーブの導入済み記録が 1,733〜3,453 B であることとも整合する。

**検算**: 上記の再構築を q1010002 で行うと **3,653 B** になり、公式配信版 `q1010002.arc` の **3,653 B と一致**した
（圧縮ストリームは実装差でバイト一致しないが、サイズと展開後の内容は一致）。
さらに 1010002 / 1010116 / 1010117 / 1010169 の 4 件は、配信版 .arc と
**14 エントリすべて展開後バイト一致**することを確認済み。

> ただし `mhnx arc-repack` は現状このパディングを保持したまま出力する（q1010002 で 35,258 B のまま）。
> 実装を足すなら「先頭データオフセットを align32(12+80n) に詰める」処理が必要。

### 5.2 ID の制約: 1 件だけ導入できない

`mhnx install` は DLC カタログに無い ID を拒否する実装になっている（`dlc.rs`: "quest id is not in the DLC catalogue"）。

* **1010007 はカタログ外のため、この経路では導入できない**（枠が存在しない）。
* 残り 11 件はカタログ内なので、サイズ条件さえ満たせば枠に書ける。

### 5.3 判定まとめ

| 区分 | 件数 | ID | 導入する価値 |
|---|---:|---|---|
| 導入可・遊べる見込み | 9 | 1010002, 1010116, 1010117, 1010169（配信版と内容一致）<br>1010126, 1010132, 1010136, 1010139, 1010162（内容は完全・配信版は手元に無し） | 通常のイベントクエストとして遊べる |
| 導入可だが価値なし | 2 | 1010006, 1010160 | カタログ枠はあるが中身が空。導入しても開始できない／意味がない |
| 導入不可 | 1 | 1010007 | DLC カタログに ID が無く、枠が存在しない |

合計 12 件（9 + 2 + 1）。サイズ条件（§5.1）は 12 件すべて満たすので、
「入らない」のは 1010007 のみ（理由はサイズではなく ID）。

### 5.4 実機検証は未実施

ここまでの判断は**すべて静的データの実測**に基づく。実際にセーブへ書き込んでゲームが起動するかは確認していない。
workdir の既存メモ（`docs/review_catalogue.md` §4.4）でも「実機/エミュレータでの確認」が未解決事項として残っている。

## 6. 判定できなかったこと（不明）

1. **「配信されたか」の最終確認**（1010126 / 1010132 / 1010136 / 1010139 / 1010162 の 5 件）
   romfs のデータは完全だが、配信版 .arc もセーブの導入記録も手元に無い。
   外部攻略サイトで 4 件（132/136/139/162）はイベントクエストとして存在を確認できたが、
   **1010126「アイルー村・雪山からのＳＯＳ」は外部でも確認できなかった**（近い名前の「雪山からの救援要請」は別クエスト）。
2. **1010160 が「配信されなかった」のか「配信されたが romfs 側は予備のまま」なのか**
   romfs のデータだけでは区別できない（§3.10 の注意書き）。
3. **.mib の rem1 / rem2 / rem3（報酬枠番号）と 255 の意味**
   11 件中 5 件で rem3 = 255、2 件で rem2 = 2。正常クエストにも 255 が出るため、
   異常値なのか「未使用」を表す既定値なのか決められなかった。
4. **com0 の上位バイト（版タグ）の厳密な意味**
   「com0 = (版 << 8) | モンスター番号」と読むと .sem 名と全件整合するが、逆コンパイルでの確認はしていない（推測）。
5. **1010006 / 1010007 の .esl が map 02 のものになっている理由**
   複製元テンプレートの名残と推測したが、根拠は命名規則の一致だけ。
